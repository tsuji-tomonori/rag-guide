# Real-time Layerで検索する

Real-time Layerでは、認証済みの利用者Contextと質問からQuery・Filterを作り、根拠候補を取得します。検索と生成を分けて測れるよう、まず候補の取得結果でRetrieval品質を評価します。

![Real-time Layerで認証済み質問から根拠候補を取得する流れ](../../assets/images/v4/49-aws-realtime-search-flow.png)

**図10-7 Real-time Layerの検索フロー**

## APIを選ぶ

| API | 担当する範囲 | 選ぶ主な条件 |
|---|---|---|
| `Retrieve` | KBから候補・Location・Metadata・Scoreを取得 | 検索後処理と生成を分離する |
| `AgenticRetrieveStream` | 質問分解、反復検索、十分性判断 | Managed KBで複雑な質問を扱う |
| `RetrieveAndGenerate` | 検索、任意のRerank、生成、Citation | Customer-managed KBの標準経路 |
| Store直接API | S3 VectorsまたはOpenSearchを直接検索 | Schema、Query、複数Indexを制御する |
| `Converse` | Evidenceから回答を生成 | Prompt、Model、回答保留を分離する |

**表10-7 Real-time APIの使い分け**

`Retrieve`はManaged / Customer-managed Knowledge Baseで使えます。`AgenticRetrieveStream`はManaged Knowledge Base専用です。`RetrieveAndGenerate`とStreaming版はCustomer-managed Knowledge Baseで使います。S3 Vectorsの`QueryVectors`やOpenSearch Query APIを直接使う場合、Query Embedding、Location復元、Index schema、Queryを利用者が管理します。

APIの境界は[`Retrieve`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_Retrieve.html)、[`AgenticRetrieveStream`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_AgenticRetrieveStream.html)、[`RetrieveAndGenerate`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_RetrieveAndGenerate.html)、[`QueryVectors`](https://docs.aws.amazon.com/AmazonS3/latest/API/API_S3VectorBuckets_QueryVectors.html)、[`Converse`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html)を参照します（確認日：2026年8月22日）。

## 検索方式を選ぶ

- **Semantic Search**：意味が近い別表現を探します。S3 Vectors、Knowledge Bases、OpenSearchのVector検索が担当します。
- **Keyword Search**：型番、条文番号、固有語、Error codeを語彙一致で探します。OpenSearchが担当します。
- **Hybrid Search**：KeywordとVectorを組み合わせます。Managed KBのサービス側Hybrid、Customer-managed KB＋対応OpenSearch構成、またはOpenSearchのSearch Pipelineを比較します。

S3 Vectors連携は`SEMANTIC`です。Customer-managed Knowledge Baseで`HYBRID`を上書きできるのは、filterable text fieldを持つ対応Storeに限られます。方式の優劣を先に決めず、意味の言い換え、型番、条文、誤字、短い質問を含む同じ評価データで比較します。

## 検索設定を評価する

### 候補数

`numberOfResults`やTop-kは、生成へ渡す最終件数ではなく、最初に拾う候補数です。少なすぎるとRecallを失い、多すぎるとRerank、Token、Latency、費用を増やします。複数のkを比較し、質問型別に必要数を決めます。

Hierarchical Chunkingでは、複数のChild候補が同じParentへ置換され、返却件数が指定値を下回る場合があります。件数不足と検索失敗を分け、Child単位のRecallとParent返却後のContext量を確認します。

### Score

Retrieval Scoreは候補の並べ替えと観測に使えますが、異なるStore、Model、Query方式のScoreを同じ尺度として直接比較しません。回答保留の閾値へ使う場合は、正例と難しい負例を含む評価データから校正します。

### Metadata FilterとUser Context

Metadata Filterには、`tenant`、`department`、`role`、`status`、`version`、`valid_from`、`valid_to`など、検索前に除外すべき条件を使います。利用者入力をそのまま採用せず、認証済みIdentityのClaimからアプリケーションが構築します。

`implicitFilterConfiguration`やManaged KBのACL awarenessも認証の代替ではありません。許可するFieldとOperatorを限定し、漏れと過剰除外をAllow/Denyテストで確認します。[Knowledge Base retrieval configuration](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-config.html)と[ACL awareness](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-retrieve-acl.html)を参照します（確認日：2026年8月22日）。

## AWS標準から分離する条件

次の要件がある処理だけを、Lambda、ECS、EKSまたはAgentCore Runtimeへ分離します。

- **Standalone Query化・Query rewriting**：会話の省略、略語、期間、表記揺れを補う
- **HyDE・Query2doc**：短い質問と文書表現の隔たりを補う
- **複数KB・IndexへのRouting**：Domain、Tenant、機密区分で検索先を分ける
- **独自Fusion・RRF**：複数Retrieverの順位を独自規則で統合する

各処理は、追加前後でRecall、Latency、費用、Trace可能性を比較します。検索を高度化しても、権限外候補や古い版を取得してよいことにはなりません。
