# 10.5 Generation構成

Generationでは、選別した根拠から回答を作り、回答中の主張を出典へ結びます。
modelだけでなく、API方式、prompt、推論パラメータ、引用、session、安全制御を一つの構成として決めます。

## 10.5.1 対応するAWSサービス

**Bedrock Agent Runtimeの`RetrieveAndGenerate` API**は、Knowledge Baseの検索とfoundation modelの呼び出しを結合し、回答、引用、session IDを返します。

**Amazon Bedrock foundation models**は、取得した根拠と質問から回答を生成します。
本章では東京リージョンで利用できるAnthropic Claude Haiku 4.5を使います。

**Bedrockの`Converse`または`ConverseStream` API**は、アプリケーションが取得・整形したcontextを自分でmessageへ組み込む場合に使います。
検索と生成を分離し、独自Post-retrievalを完全に制御できます。

**Amazon Bedrock Guardrails**は、有害content、denied topic、機密情報などに対する入出力制御を追加します。
根拠の正しさや引用の完全性を保証する機能ではありません。

**Amazon CloudWatch**は、latency、error、throttling、token使用量、回答保留率を監視します。
CloudTrailと合わせてmodelや設定の管理操作を追跡します。

## 10.5.2 生成APIの選び方

**`RetrieveAndGenerate`を選ぶ条件**

- Knowledge Baseの検索から回答と引用までを一つのAPIで実行したい場合
- Bedrockの既定promptまたは対応するcustom promptで要件を満たせる場合
- 取得結果の独自加工が少なく、Bedrockのcitation形式を利用したい場合

**`Retrieve`と`Converse`を分ける条件**

- Lambdaで重複排除、複数検索のfusion、厳密なcontext packingを行う場合
- promptのmessage構造、tool use、streaming、会話memoryをアプリケーションで制御する場合
- 検索候補と生成へ渡した根拠を同一request traceで厳密に保存する場合

本章では最小構成のため`RetrieveAndGenerate`を使います。
10.3の`Retrieve`は検索診断用で、10.5の`RetrieveAndGenerate`とは別のAPI requestです。
最終回答が利用した根拠は、`RetrieveAndGenerate`応答の`citations`で確認します。

## 10.5.3 generation modelの選び方

modelは次の軸で比較します。

- 日本語とdomain用語での回答正確性
- 複数根拠の統合、矛盾検出、回答保留の能力
- context windowと最大output token
- p50、p95 latencyと同時実行時のquota
- input token、output token当たりの費用
- 利用region、inference profile、data residency

Claude Haiku 4.5は、単純なサポート回答でlatencyと費用を抑えるbaselineとして選びます。
長い規程の比較や複雑な推論が必要なら、より高性能なmodelを同じ評価setで比較します。
modelを大きくする前に、正解根拠がcontextへ入っていることを確認します。

model ID、region、Knowledge Basesへの対応は[Claude Haiku 4.5 model card](https://docs.aws.amazon.com/bedrock/latest/userguide/model-card-anthropic-claude-haiku-4-5.html)で確認できます。

## 10.5.4 promptの選び方

Bedrockの既定promptでbaselineを作り、次の失敗がある場合だけcustom promptへ進みます。

- 根拠にない情報を補ってしまう
- 根拠が不足しても断定する
- 回答形式、言語、長さが業務要件と合わない
- 複数資料の矛盾を明示しない

Knowledge Base用のcustom generation promptには`$search_results$`が必要です。
Bedrock形式のcitationを返すには`$output_format_instructions$`も残します。

```text
あなたは製品サポート担当者です。
<search_results>
$search_results$
</search_results>

質問: $query$

検索結果だけを根拠に日本語で回答してください。
必要な情報が検索結果にない場合は、確認できないと回答してください。
資料が矛盾する場合は、矛盾する条件と出典を分けて示してください。
回答は結論、条件、問い合わせ方法の順に簡潔に書いてください。

$output_format_instructions$
```

promptに例を追加しすぎると、例の製品名や回答を出力へ混ぜることがあります。
短いinstructionから始め、失敗例に対応する変更だけを加えます。
placeholderの仕様は[Knowledge Baseのqueryとresponse generation設定](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-config.html)で確認できます。

## 10.5.5 推論パラメータの決め方

根拠付き業務回答では、表現の多様性より再現性を優先し、temperatureを低くします。
低いtemperatureでも同一出力を保証するわけではありません。

最初に比較する設定は次のとおりです。

```yaml
generation:
  model_id: anthropic.claude-haiku-4-5-20251001-v1:0
  temperature: 0
  max_tokens: 800
  stop_sequences: []
retrieval:
  number_of_results: 5
  search_type: SEMANTIC
```

`max_tokens=800`は短いサポート回答の開始値です。
途中で回答が切れる場合はoutput長を測って増やし、長すぎる場合はpromptの形式と上限を調整します。
temperatureとtop-pを同時に細かく動かさず、一項目ずつ比較します。

APIでは`generationConfiguration`へ設定します。

```python
"generationConfiguration": {
    "inferenceConfig": {
        "textInferenceConfig": {
            "temperature": 0,
            "maxTokens": 800,
        }
    },
    "promptTemplate": {
        "textPromptTemplate": PROMPT_TEMPLATE
    },
}
```

baselineの付属クライアントはBedrockの既定promptとmodel既定の推論parameterを使います。
まず回答とcitationを確認し、その後で上記の明示設定を追加して比較します。

## 10.5.6 Guardrailsの選び方

Guardrailsは、アプリケーションの利用者入力と生成outputに対する追加防御として使います。

- denied topicで対象外の助言を制限します。
- sensitive information filterで個人情報や認証情報の出力を制限します。
- word filterやcontent filterを用途のriskに合わせます。

GuardrailsはKnowledge Baseから取得したreference本文には適用されません。
機密文書を取得させないためには、Pre-retrievalのdata分類、RetrievalのACL filter、Post-retrievalの再確認が必要です。

有効にする場合は、versionを固定してrequestへ指定します。

```python
"generationConfiguration": {
    "guardrailConfiguration": {
        "guardrailId": "YOUR_GUARDRAIL_ID",
        "guardrailVersion": "DRAFT_OR_NUMBER"
    }
}
```

block時の`guardrailAction`を監視し、利用者には内部policyを露出しない安全な案内を返します。

## 10.5.7 `RetrieveAndGenerate`を実行する

generation model ARNを設定します。

```bash
export GENERATION_MODEL_ARN=\
"arn:aws:bedrock:${AWS_REGION}::foundation-model/anthropic.claude-haiku-4-5-20251001-v1:0"
```

Anthropic modelを初めて使うAWSアカウントでは、Bedrock consoleのModel catalogから利用目的の登録を求められる場合があります。
アプリケーションroleには`RetrieveAndGenerate`と対象modelを使う権限が必要です。

代表質問をgenerationだけのmodeで送ります。

```bash
python \
  'docs/10.AWSで設計・実装する/samples/rag_api.py' \
  --mode generate \
  'スタンダードプランのサポート受付時間と問い合わせ方法を教えてください。' \
  | tee /tmp/rag-generation-result.json
```

結果を表示します。

```bash
jq '.generation' /tmp/rag-generation-result.json
```

応答は次の形です。回答文の表現は完全一致しなくても構いません。

```json
{
  "answer": "スタンダードプランのサポート受付時間は、祝日を除く平日の09:00から17:00までです。時刻は日本標準時です。問い合わせはWebフォームまたはメールで行えます。",
  "citations": [
    {
      "generated_text": "...",
      "source_uri": "s3://.../source/support-policy.md",
      "source_text": "..."
    }
  ],
  "session_id": "..."
}
```

次を確認します。

- 回答に平日09:00から17:00、日本標準時が含まれます。
- 回答にWebフォームまたはメールが含まれます。
- `citations`が1件以上あります。
- 引用の`source_uri`が`support-policy.md`を指します。
- `source_text`が回答内容を実際に支えています。
- `session_id`が返っています。

検索診断とgenerationを連続して確認する場合は、defaultの`both` modeも使えます。

```bash
python \
  'docs/10.AWSで設計・実装する/samples/rag_api.py' \
  'スタンダードプランのサポート受付時間と問い合わせ方法を教えてください。' \
  | tee /tmp/rag-end-to-end-result.json
```

## 10.5.8 sessionの扱い

最初の`RetrieveAndGenerate` requestでは`sessionId`を指定せず、応答で発行された値を受け取ります。
同じ会話を続けるrequestだけ、その値を再利用します。

別利用者、別会話、長時間経過後のrequestへ同じsession IDを共有しません。
アプリケーションではsession IDを利用者sessionへ結び、logやURLへ不用意に露出させないようにします。

会話履歴が検索queryを曖昧にする場合は、会話を独立したqueryへ書き換えた結果も記録し、単発質問のRetrieval評価と分けます。

## 10.5.9 回答と引用を評価する

評価は少なくとも次を分けます。

- **回答正確性**：受付時間と問い合わせ方法が原文と一致するか
- **根拠性**：回答中の各主張を取得したsource textが支持するか
- **citation correctness**：引用先が主張を実際に支えるか
- **citation completeness**：検証可能な主張に引用が付くか
- **回答保留**：根拠がない質問で推測せず保留できるか
- **安全性**：prompt injectionや機密情報の抽出要求に方針どおり応答するか

回答が正しく見えても、引用先が別文書なら完了ではありません。
逆に、正しいchunkが引用されても、回答が条件や例外を落としていればGenerationの設定を見直します。

## 10.5.10 よくあるエラー

**`ResourceNotFoundException`**では、`AWS_REGION`と`KB_ID`が同じリージョンのKnowledge Baseを指すか確認します。

```bash
aws bedrock-agent get-knowledge-base \
  --knowledge-base-id "$KB_ID" \
  --region "$AWS_REGION"
```

**`AccessDeniedException`**では、APIを呼ぶidentityとKnowledge Base service roleを分けて確認します。
前者にはAgent Runtimeとgeneration model、後者にはS3、embedding、vector indexの権限が必要です。

**Managed Knowledge Baseに関する`ValidationException`**では、`RetrieveAndGenerate`を使える標準Knowledge Baseか確認します。

**API operationがSDKにない場合**は、virtual environmentを有効にしてboto3を更新します。

```bash
source .venv-rag-handson/bin/activate
python -m pip install --upgrade boto3
```

**回答は返るが引用が空の場合**は、`Retrieve`上位だけで質問へ答えられるか、custom promptに`$search_results$`と`$output_format_instructions$`があるか、model ARNが有効かを確認します。

## 10.5.11 ハンズオンの完了判定

- [ ] `Retrieve`で期待文書と本文を確認しました。
- [ ] Post-retrieval後も正解chunkが残っています。
- [ ] `RetrieveAndGenerate`が正しい回答を返しました。
- [ ] citationが回答の各条件を支持しています。
- [ ] 根拠がない質問での動作を確認しました。
- [ ] 利用したmodel、prompt、検索設定を特定できます。

## 10.5.12 検証用リソースを片付ける

AWSリソースには費用が発生し得ます。
Knowledge Base ID、vector bucket名、vector index名、S3原文bucket名が記録と一致することを確認してから、依存関係の逆順で削除します。

1. Amazon Bedrock consoleで`rag-four-elements-kb`を削除します。data deletion policyが`Delete`か`Retain`かを確認します。
2. S3 Vectorsのindexとvector bucketが残っているか確認します。残っている場合はindexを先に削除し、次にvector bucketを削除します。
3. S3 consoleで原文bucketを**Empty**にします。versioningを有効にしたため、current objectだけでなく全versionとdelete markerが対象であることを確認します。
4. 空になった原文bucketを削除します。
5. 自動作成されたKnowledge Base service roleが他用途で使われていないことを確認し、専用roleなら削除します。

S3 Vectorsを手動で削除する場合は、対象を先に表示します。

```bash
export VECTOR_BUCKET=YOUR_VECTOR_BUCKET_NAME
export VECTOR_INDEX=YOUR_VECTOR_INDEX_NAME

aws s3vectors get-index \
  --vector-bucket-name "$VECTOR_BUCKET" \
  --index-name "$VECTOR_INDEX" \
  --region "$AWS_REGION"
```

名前が記録と一致した場合だけ削除します。

```bash
aws s3vectors delete-index \
  --vector-bucket-name "$VECTOR_BUCKET" \
  --index-name "$VECTOR_INDEX" \
  --region "$AWS_REGION"

aws s3vectors delete-vector-bucket \
  --vector-bucket-name "$VECTOR_BUCKET" \
  --region "$AWS_REGION"
```

最後に、Knowledge Base、vector index、vector bucket、原文bucket、専用service roleが残っていないことを確認します。
共有roleか判断できない場合は削除せず、AWS管理者へ確認します。
