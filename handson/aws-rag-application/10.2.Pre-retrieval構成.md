# 10.2 Pre-retrieval構成

Pre-retrievalでは、原文を検索可能なchunkへ変換します。
data source、parser、chunking、embedding、vector storeの選択は、後段の検索品質と変更コストを決めます。

## 10.2.1 対応するAWSサービス

**Amazon S3**は原文を保存します。
version、所有者、更新経路が分かる正本を置き、公開アクセスを遮断します。

**Amazon Bedrock Knowledge Basesのdata sourceとingestion job**は、S3から文書を読み、解析、chunking、embedding、indexingを順に実行します。
同期結果から処理件数と失敗理由を確認できます。

**Amazon Titan Text Embeddings V2**は、文書chunkと質問を同じvector空間へ変換します。
256、512、1024次元のfloat embeddingを選べます。

**Amazon S3 Vectors**はembeddingとmetadataを保存し、近傍検索を行います。
本章ではKnowledge Base作成時のQuick createを使います。

**IAMとAWS KMS**は、Knowledge BaseがS3、embedding model、vector indexを利用する権限と暗号鍵を制御します。

## 10.2.2 data sourceとparserの選び方

原文がS3にあり、batch同期でよければS3 data sourceを選びます。
Confluence、SharePoint、Google Driveなどに正本がある場合は、複製運用を作る前にKnowledge Basesの対応connectorと同期仕様を確認します。
databaseの列や関係をそのまま検索条件へ使う場合は、非構造文書のS3取り込みではなくstructured data storeまたは独自検索を検討します。

parserは文書の構造で選びます。

- **Default parser**：プレーンテキスト、Markdown、単純なPDFなど、本文抽出だけで足りる場合に使います。
- **Bedrock Data Automation parser**：表、図、ページ構造を含む文書から、視覚要素も含めて取り出す場合に検討します。
- **foundation model parser**：文書構造をモデルで解釈したい場合に使います。model利用料、latency、対応regionを確認します。
- **custom transformation**：定型ヘッダーの除去、独自section分割、業務metadataの付与など、決定的な変換が必要な場合にAWS Lambdaを使います。

parserを高度化する前に、検索に必要な本文がDefault parserの出力へ残るかを少数文書で確認します。
画像中の文字、複雑な表、段組みが重要なら、目視できる原文と抽出結果を比較します。

## 10.2.3 chunkingの選び方

chunkは、小さすぎると回答条件が分断され、大きすぎると無関係な記述を一緒に取得します。
質問に答えるために同時に必要な範囲を基準にします。

- **Default chunking**は約300 tokenで文境界を保ちます。短いFAQ、手順書、最初のbaselineに向きます。
- **Fixed-size chunking**は最大token数とoverlap率を明示します。文書の段落長が揃い、比較実験を再現したい場合に向きます。
- **Hierarchical chunking**は小さなchildで検索し、広いparentを返します。局所的な語で探し、周辺説明も生成へ渡したい場合に使います。
- **Semantic chunking**は意味の変わり目で分割します。節の長さが不均一な文書で候補になりますが、追加の処理時間と費用を評価します。
- **No chunking**は、上流で一ファイル一検索単位へ分割済みの場合に使います。

最初はDefault chunkingを使い、検索評価で「条件の後半が別chunkへ落ちる」「一つのchunkに複数主題が混ざる」と分かったときに変更します。
Fixed-sizeを比較するなら、たとえば`512 token / 20% overlap`を一つの候補にし、DefaultとのRecall@k、重複率、生成input tokenを比較します。

chunking strategyはdata source接続後に変更できません。
変更時は新しいdata sourceを作り、同じ評価質問で再ingestionした結果を比較します。
詳細は[Knowledge Basesのchunking](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html)で確認できます。

## 10.2.4 embedding modelと次元数の選び方

embedding modelは、文書と質問の言語、domain、vector storeの対応、latency、費用で選びます。

本章では東京リージョンで利用でき、Knowledge BasesとS3 Vectorsに対応する`amazon.titan-embed-text-v2:0`を選びます。
1024次元は情報量を優先するbaselineです。
512または256次元はstorageと転送量を減らせますが、変更前後で検索品質を測ります。

日本語文書を日本語で検索する場合も、代表質問と正解chunkを用意して評価します。
複数言語間で検索する場合は、Cohere Embed Multilingualなどの候補も同じデータで比較します。
model名だけで多言語品質を判断しません。

embedding model、次元数、vector typeはvector indexのschemaと一致させます。
既存indexの次元数は後から変更できないため、modelまたは次元数を変える場合は新しいindexへ再ingestionします。
対応するmodelと次元数は[Knowledge Basesの対応embedding model](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-supported.html)で確認できます。

## 10.2.5 vector storeの選び方

**S3 Vectors**は、運用するserverを増やさず、耐久性とstorage costを重視するsemantic searchに向きます。
Knowledge Basesとの組み合わせではfloat vectorのみで、hybrid searchには対応しません。
custom metadataはvector当たり1 KB、35 keyまでなので、filter用の小さな属性だけを保存します。

**Amazon OpenSearch Serverless**は、semanticとkeywordを組み合わせたhybrid search、全文検索、検索分析が必要な場合に候補になります。
型番、error code、条文番号の完全一致が重要なら、S3 Vectorsだけで調整を続けるよりhybrid searchを比較します。

**Amazon Aurora PostgreSQLとpgvector**は、既存のrelational data、transaction、SQL条件とvector検索を同じdatabaseで扱う場合に候補になります。
connection、index、vacuum、capacityを含むdatabase運用が必要です。

**Amazon Neptune Analytics**は、entity間の関係や経路を検索するGraphRAGを構築する場合に候補になります。
単純な文書近傍検索だけなら最初から追加しません。

本章は、semantic searchだけで要件を満たす小規模検証なのでS3 Vectorsを選びます。
S3 Vectorsの特性と制約は[S3 VectorsとKnowledge Basesの統合](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-bedrock-kb.html)で確認できます。

## 10.2.6 採用する設定値

```yaml
source:
  service: s3
  prefix: source/
  block_public_access: true
  versioning: enabled
  encryption: SSE-S3
ingestion:
  parser: default
  chunking: default
embedding:
  model_id: amazon.titan-embed-text-v2:0
  dimensions: 1024
  vector_type: float
vector_store:
  service: s3_vectors
  creation: quick_create
  search_capability: semantic
```

検証データにはSSE-S3を使います。
customer managed KMS keyが必要な場合は、key policyにKnowledge Base service roleを追加し、S3原文とvector bucketの暗号設定を揃えて確認します。

## 10.2.7 S3へ原文を配置する

リポジトリのルートで、サンプル文書とAWS identityを確認します。

```bash
pwd
test -f 'docs/10.AWSで設計・実装する/samples/data/support-policy.md'
aws sts get-caller-identity
```

一意なbucket名を作り、東京リージョンへ作成します。

```bash
export ACCOUNT_ID="$(aws sts get-caller-identity --query Account --output text)"
export LAB_SUFFIX="$(date +%Y%m%d%H%M%S)"
export DOC_BUCKET="rag-four-elements-${ACCOUNT_ID}-${LAB_SUFFIX}"

aws s3api create-bucket \
  --bucket "$DOC_BUCKET" \
  --region "$AWS_REGION" \
  --create-bucket-configuration LocationConstraint="$AWS_REGION"
```

Public Access、versioning、server-side encryptionを明示します。

```bash
aws s3api put-public-access-block \
  --bucket "$DOC_BUCKET" \
  --public-access-block-configuration \
'BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true'

aws s3api put-bucket-versioning \
  --bucket "$DOC_BUCKET" \
  --versioning-configuration Status=Enabled

aws s3api put-bucket-encryption \
  --bucket "$DOC_BUCKET" \
  --server-side-encryption-configuration \
'{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'
```

Markdownを`source/`へuploadします。

```bash
aws s3 cp \
  'docs/10.AWSで設計・実装する/samples/data/' \
  "s3://${DOC_BUCKET}/source/" \
  --recursive \
  --exclude '*' \
  --include '*.md'

aws s3 ls "s3://${DOC_BUCKET}/source/" --recursive
```

`product-overview.md`、`security-guide.md`、`support-policy.md`の3件だけが表示されることを確認します。

## 10.2.8 metadataを設計する場合

検索時にtenant、department、公開状態、版で絞るなら、ingestion前にfilter用metadataを決めます。
たとえば`support-policy.md.metadata.json`を同じprefixへ置きます。

```json
{
  "metadataAttributes": {
    "department": "support",
    "status": "published",
    "version": 3
  }
}
```

filterに使わない長い説明文をmetadataへ入れません。
S3 Vectorsではmetadataの容量とkey数に上限があります。
属性をembeddingへ含めるかも選べるため、部署名や製品名を意味検索へ反映したい場合だけ`includeForEmbedding`を検討します。
形式は[S3 data sourceのmetadata設定](https://docs.aws.amazon.com/bedrock/latest/userguide/s3-data-source-connector.html)に合わせます。

このハンズオンではmetadata filterを使わないため、追加ファイルは作りません。

## 10.2.9 Knowledge Baseを作成して同期する

Amazon Bedrock consoleを東京リージョンで開き、vector storeへ接続する標準Knowledge Baseを作ります。

1. Knowledge Base名を`rag-four-elements-kb`にします。
2. IAM service roleは**Create and use a new service role**を選びます。
3. data sourceはAmazon S3、名前は`rag-four-elements-source`にします。
4. S3 URIへ`s3://${DOC_BUCKET}/source/`を指定します。
5. parsing strategyはDefault parserを選びます。
6. chunking strategyはDefault chunkingを選びます。
7. embedding modelはTitan Text Embeddings V2、dimensionsは`1024`、vector typeは`Float`を選びます。
8. vector storeは**Quick create a new vector store**からS3 vector bucketを選びます。
9. 暗号化は検証用の既定値を使い、Knowledge Baseを作成します。

重要な組み合わせは次のとおりです。

```text
Standard Knowledge Base
  + S3 data source
  + Default parser / Default chunking
  + Titan Text Embeddings V2 / 1024 / float
  + S3 Vectors / Quick create
```

作成後、Knowledge Base ID、data source ID、service role、vector bucket、vector indexを記録します。

```bash
aws bedrock-agent list-knowledge-bases \
  --region "$AWS_REGION" \
  --query \
"knowledgeBaseSummaries[?name=='rag-four-elements-kb'].[name,knowledgeBaseId,status]" \
  --output table

export KB_ID=YOUR_KB_ID
```

Knowledge Baseの詳細画面でdata sourceを選び、**Sync**を実行します。
完了後に3文書が処理され、failed documentsが0件であることを確認します。

CLIからdata sourceを確認する場合は次を実行します。

```bash
aws bedrock-agent list-data-sources \
  --knowledge-base-id "$KB_ID" \
  --region "$AWS_REGION" \
  --query 'dataSourceSummaries[].[name,dataSourceId,status]' \
  --output table
```

## 10.2.10 完了判定と調整順序

- [ ] S3の`source/`にMarkdownが3件あります。
- [ ] Public Accessが遮断され、versioningとencryptionが有効です。
- [ ] Knowledge Baseは`ACTIVE`です。
- [ ] 最新の同期は`COMPLETE`で、失敗文書は0件です。
- [ ] Knowledge Base IDと自動作成されたリソース名を記録しました。

同期に失敗した場合は、S3 URI、service roleのS3権限、embedding modelの権限、vector indexの次元数を順に確認します。
文書を更新した後は再同期が必要です。
検索品質を調整するときは、まず抽出本文、次にchunking、最後にembedding modelとvector storeの順で比較すると、原因を絞りやすくなります。
