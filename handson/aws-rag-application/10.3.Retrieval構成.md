# 10.3 Retrieval構成

Retrievalでは、質問を検索queryへ変換し、回答に必要なchunkを候補集合として取得します。
検索方式、metadata filter、取得件数をこの工程で決め、生成品質とは分けて評価します。

## 10.3.1 対応するAWSサービス

**Bedrock Agent Runtimeの`Retrieve` API**は、Knowledge Base ID、質問、検索設定を受け取り、関連chunkを順位付きで返します。
応答には本文、metadata、location、scoreが含まれます。

**Amazon Bedrock Knowledge Bases**は、Pre-retrievalで選んだembedding modelを質問にも適用し、vector storeへの検索を仲介します。

**Amazon S3 Vectors**は、質問vectorに近い文書vectorを検索します。
本章の構成ではsemantic searchだけを使います。

**Amazon OpenSearch Serverless**は、keywordとvectorを組み合わせたhybrid searchが必要な場合の候補です。
Knowledge Baseにfilterable text fieldを設定した構成で`HYBRID`を選べます。

## 10.3.2 `Retrieve`と直接検索の選び方

Knowledge Basesでingestionした文書を検索し、本文、metadata、出典を統一した形式で受け取りたい場合は`Retrieve`を使います。
embeddingの呼び出し、vector query、locationの復元をアプリケーションで個別実装せずに済みます。

S3 Vectorsの`QueryVectors`やOpenSearch APIを直接呼ぶ構成は、次の場合に選びます。

- 独自のembedding pipelineとindex schemaを使う場合
- 複数indexを検索して独自にfusionする場合
- Knowledge Basesが公開しないvector store固有機能を使う場合
- 取得結果のschemaとpagingをアプリケーション側で管理できる場合

本章では、Pre-retrievalと設定を揃えやすい`Retrieve`を使います。

## 10.3.3 search typeの選び方

**Semantic search**は、質問と本文で使う語が異なっても意味の近さで探します。
自然文のFAQ、言い換えの多い問い合わせ、説明文の検索に向きます。

**Hybrid search**はsemantic searchとkeyword searchを組み合わせます。
型番、error code、固有名詞、条文番号の完全一致と自然文検索を両立したい場合に比較します。

S3 Vectorsはsemantic searchのみです。
`overrideSearchType="HYBRID"`を指定しても利用できないため、hybridが要件ならOpenSearch Serverlessなど対応するvector storeを選び直します。
APIの対応条件は[`KnowledgeBaseVectorSearchConfiguration`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_KnowledgeBaseVectorSearchConfiguration.html)で確認できます。

## 10.3.4 metadata filterの選び方

metadata filterは、類似度を計算した後の表示処理ではなく、検索対象を限定する条件として設定します。

filterに向く属性は次のとおりです。

- `tenant_id`、`access_group`など、検索してよい範囲
- `status=published`など、公開状態
- `product`、`language`、`department`など、対象領域
- `valid_from`、`version`など、有効期間と版

文書ACLがある場合は、利用者の権限からfilterをserver sideで組み立てます。
利用者が送った任意の`tenant_id`をそのまま信用しません。
Post-retrievalでも権限を再確認できますが、権限外chunkを最初から取得しないことが基本です。

`support`部門の公開文書だけへ絞る例は次の形です。

```python
"filter": {
    "andAll": [
        {"equals": {"key": "department", "value": "support"}},
        {"equals": {"key": "status", "value": "published"}},
    ]
}
```

filterを厳しくしすぎると正解文書が0件になります。
filterなしの結果と比較し、属性値の欠損、型、表記揺れを確認します。

## 10.3.5 取得件数の選び方

`numberOfResults`は最終回答に使う件数ではなく、Retrievalが返す候補数です。
値は1から100まで指定できます。

小さすぎると正解chunkを取り逃がし、大きすぎるとlatency、reranking費用、生成contextが増えます。
最初は5件で順位を観察します。
rerankerを使う場合は候補を20件へ広げ、Post-retrievalで5件へ絞る構成を一つの比較対象にします。

件数は次の順に決めます。

1. 正解chunkを持つ評価質問を用意します。
2. `k=5`、`10`、`20`でRecall@kとlatencyを測ります。
3. 正解を十分に含む最小のkを選びます。
4. reranker後の採用件数とgeneration tokenも合わせて測ります。

`score`は正答確率ではなく、異なるmodelやindex間で同じ意味を持つ値でもありません。
score thresholdを使う場合は、同じ構成の評価データで「答えられる質問」と「根拠がない質問」の分布を測って決めます。

## 10.3.6 採用する設定値

```yaml
api: bedrock-agent-runtime.Retrieve
search_type: SEMANTIC
number_of_results: 5
filter: none
query_transformation: none
reranking: none
response_fields:
  - content.text
  - metadata
  - location
  - score
```

質問書き換えやquery decompositionは、baselineで取り逃しの種類を確認した後に追加します。
会話の省略が原因ならstandalone queryへの書き換え、複数論点が原因ならsubquery分割を検討します。

## 10.3.7 API実行環境を用意する

Python 3.11以降を確認し、ハンズオン専用のvirtual environmentへboto3を入れます。

```bash
python3 --version
python3 -m venv .venv-rag-handson
source .venv-rag-handson/bin/activate
python -m pip install --upgrade pip boto3
python -c 'import boto3; print(boto3.__version__)'
```

Knowledge Base IDを設定します。

```bash
export AWS_REGION=ap-northeast-1
export AWS_DEFAULT_REGION="$AWS_REGION"
export KB_ID=YOUR_KB_ID
```

`YOUR_KB_ID`は、10.2で作成した実際のIDへ置き換えます。

## 10.3.8 `Retrieve`を実行する

代表質問を検索だけのmodeで送ります。

```bash
python \
  'docs/10.AWSで設計・実装する/samples/rag_api.py' \
  --mode retrieve \
  'スタンダードプランのサポート受付時間と問い合わせ方法を教えてください。' \
  | tee /tmp/rag-retrieval-result.json
```

検索結果を表示します。

```bash
jq '.retrieval' /tmp/rag-retrieval-result.json
```

応答は次の形です。scoreは実行結果を使い、例の数値を期待値にしません。

```json
{
  "requested_results": 5,
  "returned_results": 3,
  "results": [
    {
      "rank": 1,
      "score": 0.72,
      "text": "# Example Support Cloud サポートポリシー ...",
      "source_uri": "s3://.../source/support-policy.md"
    }
  ]
}
```

次を確認します。

- `support-policy.md`が1位です。
- 1位の本文に、平日、09:00、17:00、Webフォーム、メールが含まれます。
- `source_uri`から原文へ戻れます。
- `returned_results`が5未満でも、登録chunk数が少ないことと矛盾しません。

質問を変え、順位も変わることを確認します。

```bash
python \
  'docs/10.AWSで設計・実装する/samples/rag_api.py' \
  --mode retrieve \
  '保存データと通信はどの方式で暗号化されますか。' \
  | tee /tmp/rag-security-retrieval.json

jq '.retrieval.results[] | {rank, score, source_uri}' \
  /tmp/rag-security-retrieval.json
```

この質問では`security-guide.md`が1位になることを確認します。

## 10.3.9 API設定の実装

付属クライアントの中心部分は次の設定です。

```python
response = client.retrieve(
    knowledgeBaseId=KNOWLEDGE_BASE_ID,
    retrievalQuery={"text": question},
    retrievalConfiguration={
        "vectorSearchConfiguration": {
            "numberOfResults": 5,
            "overrideSearchType": "SEMANTIC",
        }
    },
)
```

本番ではAPI timeoutとretryをSDKで設定し、throttlingと一時障害だけを指数backoffでretryします。
権限不足、無効なfilter、存在しないKnowledge Baseを無条件にretryしません。
