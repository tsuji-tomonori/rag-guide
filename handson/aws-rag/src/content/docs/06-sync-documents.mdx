同期の成功は「APIが受け付けた」だけでは判定しません。job終端状態、statistics、文書単位の状態、vector indexの4層で確認します。また、ingestion開始前にKnowledge Baseが利用するservice roleとembedding model呼び出し権限を再確認し、IAM不足を同期処理の途中まで持ち越さないようにします。

<CloudShellStep number="6.1" title="ingestion前提を検証してjobを開始する">

まず、Knowledge Baseが4章で作成したservice roleを使っていることと、そのroleにTitan Text Embeddings V2への`bedrock:InvokeModel`が付与されていることを確認します。

<Command title="Knowledge Baseのroleとembedding model権限をpreflight">

```bash
export RAG_EXPECTED_EMBED_MODEL_ARN="arn:aws:bedrock:${AWS_REGION}::foundation-model/${RAG_EMBED_MODEL_ID}"

export RAG_KB_ROLE_ARN="$(aws bedrock-agent get-knowledge-base \
  --knowledge-base-id "$RAG_KB_ID" \
  --query 'knowledgeBase.roleArn' \
  --output text)"

test "$RAG_KB_ROLE_ARN" = "$RAG_ROLE_ARN"

aws iam get-role-policy \
  --role-name "$RAG_ROLE_NAME" \
  --policy-name "$RAG_POLICY_NAME" \
  --query 'PolicyDocument' \
  --output json \
  | tee "$RAG_WORK_DIR/bedrock-kb-policy-readback.json" >/dev/null

jq -e --arg modelArn "$RAG_EXPECTED_EMBED_MODEL_ARN" '
  any(.Statement[];
    .Effect == "Allow"
    and ((.Action | if type == "array" then . else [.] end) | index("bedrock:InvokeModel") != null)
    and (.Resource == $modelArn)
  )
' "$RAG_WORK_DIR/bedrock-kb-policy-readback.json" >/dev/null
```

</Command>

<ExpectedResult>

すべてのコマンドが終了コード`0`で完了します。特に最後の`jq -e`が成功すれば、Knowledge Baseが利用するroleに、東京リージョンの`amazon.titan-embed-text-v2:0`を呼び出すidentity-based policyが存在します。

</ExpectedResult>

<Aside type="caution" title="bedrock:InvokeModel の検証で失敗した場合">
  ingestion jobを開始する前に4章のpermissions policyを再適用してください。`aws iam put-role-policy --role-name "$RAG_ROLE_NAME" --policy-name "$RAG_POLICY_NAME" --policy-document "file://$RAG_WORK_DIR/bedrock-kb-permissions.json"`を実行し、このpreflightをもう一度実行します。`bedrock:InvokeModel`がないまま`start-ingestion-job`を実行すると、embedding時に403の`ValidationException`で失敗します。
</Aside>

<Command title="ingestion jobを開始">

```bash
aws bedrock-agent start-ingestion-job \
  --knowledge-base-id "$RAG_KB_ID" \
  --data-source-id "$RAG_DS_ID" \
  --description "Initial sync for RAG hands-on $RAG_RUN_ID" \
  | tee "$RAG_WORK_DIR/start-ingestion-output.json"

export RAG_INGESTION_JOB_ID="$(jq -r '.ingestionJob.ingestionJobId' "$RAG_WORK_DIR/start-ingestion-output.json")"
test "${#RAG_INGESTION_JOB_ID}" -eq 10
```

</Command>

<ExpectedResult>

10文字のingestion job IDを取得できます。直後のstatusは`STARTING`または`IN_PROGRESS`です。

</ExpectedResult>

</CloudShellStep>

<CloudShellStep number="6.2" title="終端状態まで監視する">

<Command>

```bash
for attempt in {1..80}; do
  RAG_INGESTION_STATUS="$(aws bedrock-agent get-ingestion-job \
    --knowledge-base-id "$RAG_KB_ID" \
    --data-source-id "$RAG_DS_ID" \
    --ingestion-job-id "$RAG_INGESTION_JOB_ID" \
    --query 'ingestionJob.status' \
    --output text)"
  printf '[%02d/80] ingestion status: %s\n' "$attempt" "$RAG_INGESTION_STATUS"
  case "$RAG_INGESTION_STATUS" in
    COMPLETE) break ;;
    FAILED|STOPPED)
      aws bedrock-agent get-ingestion-job \
        --knowledge-base-id "$RAG_KB_ID" \
        --data-source-id "$RAG_DS_ID" \
        --ingestion-job-id "$RAG_INGESTION_JOB_ID"
      exit 1
      ;;
  esac
  sleep 15
done

test "$RAG_INGESTION_STATUS" = "COMPLETE"
```

</Command>

<ExpectedResult>

複数ページのPDFを解析・chunk化・embeddingするため、小さなtxt fileより時間がかかります。20分経っても終わらない場合は、無限に待たず[トラブルシューティング](/rag-guide/troubleshooting/)を確認します。

</ExpectedResult>

</CloudShellStep>

<CloudShellStep number="6.3" title="同期結果を多層で検証する">

<Command title="job統計を確認">

```bash
aws bedrock-agent get-ingestion-job \
  --knowledge-base-id "$RAG_KB_ID" \
  --data-source-id "$RAG_DS_ID" \
  --ingestion-job-id "$RAG_INGESTION_JOB_ID" \
  --query 'ingestionJob.{status:status,statistics:statistics,failures:failureReasons}' \
  --output yaml
```

</Command>

<Command title="文書単位の状態を確認">

```bash
aws bedrock-agent list-knowledge-base-documents \
  --knowledge-base-id "$RAG_KB_ID" \
  --data-source-id "$RAG_DS_ID" \
  --query 'documentDetails[].{status:status,uri:identifier.s3.uri,reason:statusReason}' \
  --output table

test "$(aws bedrock-agent list-knowledge-base-documents \
  --knowledge-base-id "$RAG_KB_ID" \
  --data-source-id "$RAG_DS_ID" \
  --query 'length(documentDetails)' \
  --output text)" = "1"
```

</Command>

<Command title="vectorが登録されたことを確認">

```bash
aws s3vectors list-vectors \
  --index-arn "$RAG_INDEX_ARN" \
  --max-items 20 \
  --return-metadata \
  --query '{count:length(vectors),keys:vectors[].key}' \
  --output json
```

</Command>

<ExpectedResult>

- jobは`COMPLETE`で、failure reasonがありません。
- Well-Architected Framework PDFが`INDEXED`です。`.metadata.json`は元文書のsidecarであり、独立文書として数えません。
- vector countは`1`以上です。文書数とvector数はchunkingによって一致しない場合があります。

</ExpectedResult>

<Aside type="note" title="1 PDF = 1 vectorではありません">
  Knowledge Basesは長いPDFを多数のchunkへ分割してからembeddingします。同期確認では「vector数が文書数と同じ」を条件にせず、document status、job statistics、vectorの存在を分けて検証します。`list-vectors --max-items 20`の`count`は全vector数ではなく、取得した先頭pageの件数です。
</Aside>

</CloudShellStep>

<Checkpoint>

- Knowledge Baseが4章で作成したservice roleを使用している
- service roleにTitan Text Embeddings V2への`bedrock:InvokeModel`がある
- ingestion jobは`COMPLETE`である
- failure reasonがない
- Well-Architected Framework PDFが`INDEXED`である
- vector indexに1件以上のvectorがある

</Checkpoint>
