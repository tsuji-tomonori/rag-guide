# 6.2. 回答形式設計

回答形式は、見栄えではなく利用者が次に行う作業から決めます。自由文、表、手順、比較、JSONでは、必要な情報、検証方法、失敗時の扱いが異なります。

## 6.2.1. 業務taskに合わせて人が読む回答形式を選ぶ

説明や要約には短い文章、複数候補の比較には表、操作手順には番号付き手順を使います。質問の形式をそのまま真似るのではなく、結論、適用条件、例外、引用を利用者が確認しやすい形を選びます。長い回答では、最初に結論と適用範囲を示し、その後に根拠、例外、詳細を配置します。根拠が一部しかない場合は、形式を埋めるために推測せず、未確認のfieldや項目を明示します。

Markdown回答では、見出しを増やしすぎず、質問の論点ごとに段落をまとめます。箇条書きは並列な条件や選択肢、番号付き手順は順序と前提がある操作に使います。表は列の意味が安定し、各cellへ根拠を対応付けられる場合に使います。比較回答では比較軸を先に固定し、資料ごとに異なる版や期間を同じ行へ混ぜません。手順回答では前提条件、実行順序、確認方法、失敗時の戻し方を分けます。引用は回答末尾へ一括配置するだけでなく、対応する主張の近くに置きます。

## 6.2.2. structured outputとformat validation

API連携ではJSONなどのstructured outputを使い、field、型、enum、必須・任意、nullの意味をschemaで定義します。生成後にparseできたことだけで成功とせず、各fieldがEvidence Setに支えられているかを検証します。

schema違反時に自由文へ黙ってfallbackすると、下流systemが誤った値を実行するおそれがあります。再生成回数を制限し、修復できない場合はerrorまたは回答保留を返します。schemaとpromptは同じrelease単位でversion管理します。

## 6.2.3. 最小のJSON Schema

次のschemaは、完全回答、部分回答、回答保留を同じ契約で返す最小例です。`status`、`answer`、`reason`、`claims`、`warnings`を常に必須とし、値がないこととfieldの欠落を区別します。回答保留では`answer`を`null`、`claims`を空配列にします。完全回答と部分回答では、各claimにEvidence Set内のcitation IDを一件以上付けます。

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "$id": "https://example.invalid/rag-answer-v1.schema.json",
  "type": "object",
  "additionalProperties": false,
  "required": [
    "schema_version",
    "status",
    "answer",
    "reason",
    "claims",
    "warnings"
  ],
  "properties": {
    "schema_version": {"const": "1.0"},
    "status": {
      "enum": ["answerable", "partial", "abstained"]
    },
    "answer": {"type": ["string", "null"]},
    "reason": {
      "enum": [
        "sufficient_evidence",
        "partial_evidence",
        "insufficient_evidence",
        "conflicting_evidence",
        "unauthorized",
        "out_of_scope"
      ]
    },
    "claims": {
      "type": "array",
      "items": {
        "type": "object",
        "additionalProperties": false,
        "required": ["claim_id", "text", "citation_ids"],
        "properties": {
          "claim_id": {"type": "string", "pattern": "^C[0-9]+$"},
          "text": {"type": "string", "minLength": 1},
          "citation_ids": {
            "type": "array",
            "minItems": 1,
            "uniqueItems": true,
            "items": {"type": "string", "pattern": "^E[0-9]+$"}
          }
        }
      }
    },
    "warnings": {
      "type": "array",
      "uniqueItems": true,
      "items": {"type": "string"}
    }
  },
  "allOf": [
    {
      "if": {"properties": {"status": {"const": "abstained"}}},
      "then": {
        "properties": {
          "answer": {"type": "null"},
          "claims": {"maxItems": 0}
        }
      },
      "else": {
        "properties": {
          "answer": {"type": "string", "minLength": 1},
          "claims": {"minItems": 1}
        }
      }
    }
  ]
}
```

schema検証だけでは、citation IDが実在するか、claimを根拠が支持するか、必要な論点を覆ったかは分かりません。生成後に、ID存在、支持関係、網羅性を別々に検査します。違反時は、検証errorと元のEvidence Setだけを渡して一回まで再生成します。再び違反した場合は、壊れたJSONを下流へ渡さず、アプリケーションが`abstained`形式を作ります。

## 6.2.4. 完全回答・部分回答・回答保留

三つの例では、質問を「スタンダードプランの受付時間と緊急連絡先は何ですか」に固定し、Evidence Setが覆う論点だけを変えます。これにより、文章表現の差ではなく、根拠の十分性による状態遷移を確認できます。

完全回答では、E01が受付時間、E02が例示用の緊急連絡先`03-0000-0000`を支えます。

```json
{
  "schema_version": "1.0",
  "status": "answerable",
  "answer": "受付時間は平日9時から17時です。緊急連絡先は03-0000-0000です。",
  "reason": "sufficient_evidence",
  "claims": [
    {
      "claim_id": "C1",
      "text": "受付時間は平日9時から17時です。",
      "citation_ids": ["E01"]
    },
    {
      "claim_id": "C2",
      "text": "緊急連絡先は03-0000-0000です。",
      "citation_ids": ["E02"]
    }
  ],
  "warnings": []
}
```

部分回答ではE01だけがあり、緊急連絡先を推測しません。

```json
{
  "schema_version": "1.0",
  "status": "partial",
  "answer": "受付時間は平日9時から17時です。緊急連絡先は確認できません。",
  "reason": "partial_evidence",
  "claims": [
    {
      "claim_id": "C1",
      "text": "受付時間は平日9時から17時です。",
      "citation_ids": ["E01"]
    }
  ],
  "warnings": ["緊急連絡先を支える根拠がありません。"]
}
```

回答保留では、受付時間にも緊急連絡先にも利用可能な根拠がありません。

```json
{
  "schema_version": "1.0",
  "status": "abstained",
  "answer": null,
  "reason": "insufficient_evidence",
  "claims": [],
  "warnings": ["質問の二つの論点を支える根拠がありません。"]
}
```

表6-1は、同じ部分回答を四つの軸で分けて判定する例です。一つの軸が合格でも、ほかの軸の合格を意味しません。

**表6-1　部分回答を四つの軸で判定する例**

| 評価軸 | 判定対象 | この例の判定 |
|---|---|---|
| 根拠の十分性 | 質問の全論点をEvidence Setが支えるか | 不合格。緊急連絡先がありません |
| 根拠忠実性 | 出力したclaimがEvidence Setを超えないか | 合格。受付時間だけを断定しています |
| 引用の正しさ | E01がC1を実際に支持するか | 合格。E01の原文と一致します |
| 引用の網羅性 | 根拠が必要なclaimに引用があるか | 合格。C1にE01があります |
