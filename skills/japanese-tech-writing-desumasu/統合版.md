# 日本語技術文書の文章規範（です・ます調）

日本語の技術文書を作成または推敲するときは、本文を中立的な「です・ます調」で統一し、以下の規範に従う。

## 適用範囲と優先順位

- 本文、注記、図表の説明、手順の説明には、原則として「です・ます調」を使用する。
- 見出し、ボタン名、メニュー名、コード、コマンド、ログ、設定値、エラーメッセージ、引用文は、文体統一の対象外とする。原文や実際の表示を改変しない。
- 利用者が別の文体、表記規則、テンプレート、用語集を指定した場合は、その指定を優先する。
- 文体の統一より、技術的な正確さ、出典への忠実さ、条件と例外の明示を優先する。
- 既存文書をリライトするときは、事実、数値、固有名、用語、条件、否定、確度を保持する。文体を整えるために意味を追加、削除、強化しない。
- 学会、投稿先、規格、法令、組織のテンプレート、用語集、スタイルガイドがある場合は、それらを優先する。投稿先が「だ・である調」を指定している場合は、本規範より投稿規定を優先する。
- 理科系文書では、文体の滑らかさや物語的な演出より、技術的正確さ、再現または追跡の可能性、根拠の明示、安全性を優先する。
- 科学的な結果や重要な条件を、驚きや山場を作るために意図的に伏せない。要約、結論先行、図表による早期提示が文書の目的に適する場合は、主要な結果を早めに示す。
- 本規範内の簡潔さ、演出、見出し、読者負荷に関する規則と、科学的な正確さ、検証可能性、再現・追跡可能性に関する規則が競合する場合は、後者を優先する。

## です・ます調の必須規則

- 完結した地の文は、「です」「ます」とその活用形で終える。
- 同じ本文内で「だ・である調」と混在させない。引用、コード、UI文字列、書名、規格上の定型句は例外とする。
- 動詞述語は「〜します」、名詞述語と形容動詞述語は「〜です」を基本とする。
- 否定は「〜しません」「〜ではありません」、過去は「〜しました」「〜でした」とする。
- 推量、可能性、推定を断定に変えない。「〜かもしれません」「〜可能性があります」「〜と考えられます」を根拠の強さに応じて使い分ける。
- 文末の連続を避けるために「だ・である調」、体言止め、未完の従属節へ逃げない。必要なら文の構造、主語、情報の順序を変える。
- 文末が「ます」で続くこと自体は誤りではない。機械的な言い換えより、意味と読みやすさを優先する。
- 技術文書では、接客用の過剰な敬語を使わない。「ございます」「させていただきます」は、対人関係上の理由がある場合に限る。「いただけますでしょうか」のような二重に婉曲な依頼は使わない。

## 文末と文中の活用

- 「です・ます調」が支配するのは、原則として主節の文末である。文中のすべての動詞を敬体へ変換しない。
- 連体修飾では、「作成したファイルを開きます」のように普通形を使う。「作成しましたファイル」のような不自然な形にしない。
- 条件節では、「エラーが発生した場合は、処理を中止します」のように書く。「発生しました場合」のように機械変換しない。
- 引用内容や命題を表す従属節では、「設定が有効であることを確認します」のように普通形が現れる場合がある。これは文末の文体混在とは区別する。
- 「〜ますので」「〜ますが」は文法的に使えるが、連続すると会話的または接客的になる。技術説明では、因果を「〜するため」、対比を「〜する一方で」などに置き換えられるか確認する。
- 文中の活用を変えるときも、時制、否定、条件、確度を保持する。

## 文末と機能の対応

| 伝える機能 | 推奨する表現 | 区別する表現 |
|---|---|---|
| 事実・仕様 | 「〜です」「〜します」 | 推測を事実として書かない |
| 過去の事実 | 「〜でした」「〜しました」 | 現在の仕様と混同しない |
| 能力・実現可能性 | 「〜できます」 | 許可や推奨の意味で使わない |
| 許可 | 「〜してもかまいません」「〜して差し支えありません」 | 能力の説明と区別する |
| 必須条件 | 「〜する必要があります」「〜しなければなりません」 | 推奨へ弱めない |
| 推奨 | 「〜することを推奨します」「通常は〜します」 | 必須条件へ強めない |
| 禁止・危険回避 | 「〜しないでください」「〜してはいけません」 | 婉曲表現で危険をぼかさない |
| 推定 | 「〜と考えられます」「〜可能性があります」 | 根拠がない断定を避ける |
| 読者の操作 | 「〜を選択します」「〜してください」 | システムの動作と区別する |
| システムの動作 | 「システムは〜します」 | 読者への依頼形にしない |

## 手順文の書き方

- 手順は、読者が実行する操作を時系列に並べる。
- 番号付き手順では、「設定画面を開きます」「［保存］を選択します」のような操作記述を基本とする。
- 読者に直接の注意や確認を求める場合だけ、「〜してください」を使う。
- 一つの手順には、原則として一つの主要操作を置く。操作後の結果確認は、同じ手順の二文目または次の手順に分ける。
- 前提条件は手順より前に示す。途中で初めて必要条件を追加しない。
- 任意の操作は「必要に応じて」「任意で」と明示する。
- 操作対象、入力値、期待結果を区別する。実際のUI文字列は `［］`、コードやコマンドはコード記法で示す。
- 危険な操作では、警告、影響、回避方法の順に示す。敬語で危険度を弱めない。

悪い例：

> 設定ファイルを変更し、サービスを再起動して、起動ログを確認してください。

良い例：

> 1. 設定ファイルを開きます。
> 2. `timeout` の値を変更して保存します。
> 3. サービスを再起動します。
> 4. 起動ログにエラーがないことを確認してください。

## 要件・仕様・推奨の書き分け

- 「できます」は能力、「してもかまいません」は許可、「推奨します」は推奨、「必要があります」は必須条件を表す。相互に置き換えない。
- 規格語の MUST、SHOULD、MAY を扱う場合は、原語または定義済みの日本語を併記し、文書全体で対応を固定する。
- システム要件では、主体を明示する。「利用者が〜します」「サーバーは〜を返します」「クライアントは〜を保存しなければなりません」のように書く。
- 「〜すること」とだけ書く規定文は、文書の様式として指定されている場合に限る。通常の解説文では「〜する必要があります」とする。
- 「原則として」「通常は」「場合があります」には、適用条件または例外を添える。便利な逃げ道として使わない。
- 保証範囲を超えて「必ず」「完全に」「すべて」と書かない。成立条件を示せる場合だけ使う。

## 敬語と冗長表現の抑制

- 「〜となります」は、変化または結果を表す場合だけ使う。単なる同定には「〜です」を使う。
- 「〜になります」は、状態の変化を表す場合だけ使う。値や名称の説明には「〜です」を使う。
- 「〜することができます」は、原則として「〜できます」に縮める。
- 「〜させていただきます」は、相手の許可または恩恵を受けて行う行為に限る。技術説明の進行には使わない。
- 「ご確認いただけますでしょうか」のような二重に婉曲な依頼は使わない。手順では「確認してください」、説明では「確認します」とする。
- 「思います」「感じます」を、根拠の代わりに使わない。事実、推定、提案のどれかを明示する。
- 「〜のほう」「〜という形」「〜といったところ」のような、意味を増やさない緩衝語を削る。
- 「〜になりますので」「〜となっておりますので」を接続の定型句にしない。因果関係をそのまま書く。

## 文末の単調さを避ける方法

文体を混在させず、次の方法で文章のリズムを整える。

- 客観的な因果や仕様上の理由には「〜ためです」「〜ことによります」を基本とする。「〜からです」も使用できるが、会話的な響きや書き手の判断理由を伴う場合があるため、文書の調子と因果の性質を確認する。
- 定義では「〜を指します」「〜という仕組みです」を使う。
- 条件を先に置き、「〜の場合は、処理を中止します」のように情報順序を変える。
- 密接な二文は、主従関係が明確な場合に限り一文へまとめる。
- 見出しや箇条書きのラベルは名詞句にし、本文の文末変化を無理に増やさない。
- 同じ主語を繰り返す場合は、省略しても参照先が一意に決まるときだけ省く。

## 接続詞と接続表現

接続詞は、前後の文または段落の論理関係を読者に予告する標識である。
語感や文章の勢いではなく、実際の論理関係に基づいて選ぶ。
接続詞を置くだけで、欠けている因果、比較軸、根拠、例外が補われるわけではない。

### 基本原則

- 接続詞を選ぶ前に、前後の関係を「原因と結果」「根拠と結論」「対比」「例外」「補足」「言換え」「例示」「順序」のように言語化する。
- 接続詞は、関係が誤読される可能性がある場合に使う。すべての文や段落の先頭に置かない。
- 一つの接続表現には、原則として一つの主な論理機能を担わせる。「しかし一方で」「またさらに」「したがって、そのため」のような重ね方は、二つの機能が本当に必要な場合に限る。
- 接続詞を削除しても関係が明白で、読みやすさが下がらない場合は削る。接続詞の代わりに、主語、対象語、トピックセンテンスを明示した方がよい場合もある。
- 前件から後件が導けない場合は、「したがって」「このことから」を置かない。必要な論拠または判断基準を補う。
- 接続詞の指す範囲が一文前だけなのか、段落全体なのかを明確にする。離れた内容を受ける場合は、「以上の結果から」「この二つの条件を踏まえると」のように受ける範囲を明示する。
- 文頭の接続詞の後には、原則として読点を置く（「しかし、」「したがって、」「なお、」「ただし、」）。投稿規定や組織の表記規則がある場合は、その規則に従う。
- 接続詞は仮名書きを基本とし、「さらに」「しかし」「したがって」「ただし」「また」と書く。法令調または指定様式でない限り、「及び」「又は」より「および」「または」を用いる方が読みやすい。

### 論理関係ごとの使い分け

| 論理関係 | 主な表現 | 適する場面 | 注意点 |
|---|---|---|---|
| 論理的な帰結 | 「したがって」「よって」「ゆえに」 | 前件の前提から後件が論理的に導かれる場合 | 単なる時間的な順序や著者の希望には使わない。「ゆえに」「よって」は数式・証明・規格文で有効だが、一般向け解説では硬くなりやすい |
| 因果による結果 | 「そのため」「このため」 | 原因や条件によって結果が生じる場合 | 因果が未確認なら「関連している可能性があります」などに弱める |
| 状況を受けた対応 | 「そこで」 | 状況を受け、書き手や主体が調査、操作、判断を行う場合 | 自然現象や自動的な結果には通常使わない |
| データからの推論 | 「このことから」「以上の結果から」 | 観察値や複数の結果から解釈・結論を導く場合 | 推論の範囲、前提、代替説明を確認する |
| 理由の後置 | 「理由は〜ためです」「なぜなら」「というのも」 | 結論を先に示し、その根拠を後から説明する場合 | 「なぜなら」だけを置いて理由を回収しない文にしない。簡潔に書ける場合は「理由は〜ためです」を優先する |
| 逆接 | 「しかし」「しかしながら」 | 前件から通常予想される内容と異なる内容を示す場合 | ただの話題転換や追加に使わない。「しかしながら」は重くなるため多用しない |
| 対比 | 「一方で」「これに対して」「他方」 | 同じ比較軸で二つの対象・条件・結果を比較する場合 | 比較する対象と軸を明示する。単独の追加情報には使わない |
| 譲歩 | 「それでも」「にもかかわらず」「とはいえ」 | 不利な条件を認めても後件が成立する場合 | 何を認め、何がなお成立するのかを明示する |
| 条件・例外 | 「ただし」 | 直前の規則、主張、適用範囲を狭める条件や例外を示す場合 | 一般的な逆接や補足には使わない。適用対象の近くに置く |
| 補足 | 「なお」 | 本筋を変えない付随情報、参照先、運用上の補足を示す場合 | 適用条件や例外を示すなら「ただし」を使う。本筋に不可欠な情報を「なお」に逃がさない |
| 同格の追加 | 「また」 | 同じ階層の事実、要件、特徴を追加する場合 | 連続する文のすべてを「また」で始めない。列挙なら箇条書きを検討する |
| 累加・段階的追加 | 「さらに」「加えて」 | 前件に情報、効果、根拠を積み増す場合 | 単なる同格追加なら「また」で足りる。「さらに」「加えて」の連打を避ける |
| 動作の連続 | 「そして」「続いて」「その後」 | 時間順または処理順に動作が続く場合 | 論理的帰結の代わりに使わない。手順では番号付きリストを優先する |
| 言換え・定義 | 「すなわち」「言い換えると」「つまり」 | 前件を別表現で示す場合 | 「すなわち」は同値・定義に使う。「言い換えると」は近似的な説明にも使える。「つまり」は要約的で会話的になりやすい |
| 例示 | 「例えば」「具体的には」 | 一般的な説明を具体例で示す場合 | 一例だけで一般命題を証明したことにしない。例外や代表性を確認する |
| 列挙・順序 | 「まず」「次に」「最後に」「第一に」「第二に」 | 並列する論点や手順の順序を示す場合 | 文法形式と粒度を揃え、番号を飛ばさない。「まず」に対応する後続を置く |
| 選択 | 「または」「あるいは」 | 複数の選択肢を示す場合 | 包含的選言か排他的選言かが要件に影響する場合は、「少なくとも一方」「いずれか一方だけ」と明記する |

### 主要な接続詞の境界

- **「したがって」と「そのため」と「そこで」**を区別する。「したがって」は論理的な帰結、「そのため」は因果的な結果、「そこで」は状況を受けた主体の対応を示す。
- **「ただし」と「なお」**を区別する。「ただし」を削ると規則の適用範囲が変わる。「なお」を削っても主たる結論や適用範囲は変わらない。
- **「しかし」と「一方で」**を区別する。「しかし」は予想に反する転換を示し、「一方で」は同じ軸に沿った比較を示す。
- **「また」と「さらに」**を区別する。「また」は同格の追加であり、「さらに」は程度、範囲、根拠などを積み増す。
- **「すなわち」と「言い換えると」**を区別する。厳密な同値でない説明に「すなわち」を使わない。
- **「および」と「または」**が入れ子になる要件では、読点だけに頼らず、箇条書き、括弧、条件式で結合範囲を明示する。

### 並列・選択条件の階層

仕様、規格、契約、試験条件などで語の結合範囲が結果を変える場合は、自然な読みやすさより、論理構造の一意性を優先する。

- 同一階層の要素をすべて満たす列挙には、原則として「および」を使う（「A、BおよびC」）。一般向け文書では仮名書きを基本とし、法令、規格、契約、引用では指定表記を保持する。
- 「および」で結んだ群を、さらに大きな階層で併合する場合は「ならびに」を使える（「AおよびA'ならびにB」）。ただし、一般的な解説文で法令調の階層表現を無理に使わず、箇条書きや括弧の方が明確ならそちらを選ぶ。
- 選択肢が一階層だけなら「または」を使う。選択肢の内部をさらに細分する場合は、内側に「もしくは」、外側に「または」を使える（「AもしくはA'またはB」）。
- 「かつ」は、二つ以上の条件を同時に満たす必要がある場合に使う。単なる名詞の列挙を硬く見せる目的では使わない。
- 「や」「など」は、列挙が例示的で、ほかの要素もあり得ることを示す。要件を網羅的に列挙する箇所では使わない。
- 「および／または」「及び／又は」は、読み手が包含的選言の範囲を誤解し得る。規格または指定様式で必要な場合を除き、「AとBの両方、またはいずれか一方」「AおよびBの少なくとも一方」のように許される組合せを明示する。
- 三階層以上の条件、否定を含む条件、優先順位がある条件は、接続詞だけで表さない。括弧、番号付き箇条書き、真理値表、決定表、論理式を用いる。
- 読点だけで結合範囲を示さない。列挙の階層、修飾先、否定の作用域を、文の構造から一意に判定できるようにする。

悪い例：

> 管理者および開発者または監査者が承認する必要があります。

「管理者」と「開発者または監査者」の組合せなのか、「管理者および開発者」と「監査者」の選択なのかが不明である。

良い例：

> 次のいずれかを満たす必要があります。
>
> - 管理者と開発者の両方が承認します。
> - 監査者が承認します。

### 接続詞の誤用例

悪い例：

> 温度が上昇しました。そこで、抵抗値が増加しました。

「そこで」は主体の対応を示すため、自然な因果には適さない。

良い例：

> 温度が上昇しました。そのため、抵抗値が増加しました。

悪い例：

> この方式は処理速度が高いです。ただし、消費電力も小さいです。

後件は例外ではなく追加の利点である。

良い例：

> この方式は処理速度が高いです。また、消費電力も小さいです。

悪い例：

> 測定値が増加しました。したがって、装置を交換しました。

測定値の増加から交換判断が直接には導かれない。

良い例：

> 測定値が許容上限を超えました。この装置は上限超過時に交換する運用であるため、装置を交換しました。

### 接続助詞と文の長さ

- 接続助詞の「が」は、実質的な対比または逆接がある場合に使う。「設定を変更しますが、次に再起動します」のような、単なる文のつなぎには使わない。
- 「ので」「から」「ため」を連ねて一文を長くしない。原因、判断、結果を分けた方が明確な場合は、二文以上に分ける。
- 原因・理由を表す「から」を学術文書で一律に禁止しない。「から」「ので」「ため」「ことから」は、主観性・客観性、前件と後件の関係、文の焦点、分野の慣用、投稿規定を踏まえて選ぶ。理科系の報告では「ため」が多く使われるが、出現頻度だけを根拠に機械置換しない。
- 連用形の中止法（「測定し、解析し、比較し、評価しました」）を長く連ねない。処理の段階が重要なら、文または番号付き手順に分ける。
- 読点で長文を救済しようとしない。主語、述語、条件、結果が遠くなる場合は文を分ける。

## 箇条書き、表、見出しの文体

- 箇条書きは、すべて完全な文にするか、すべて名詞句にする。混在させない。
- 完全な文の箇条書きには句点を付け、「です・ます調」で統一する。
- 名詞句の箇条書きには、原則として句点を付けない。
- 表の同じ列では、語の粒度と文法形式を揃える。名詞句と完全な文を無計画に混ぜない。
- 見出しは、原則として内容を特定する名詞句または簡潔な疑問形にする。「〜します」のような本文調の見出しを連続させない。
- 注記が完全な文なら「です・ます調」にする。ラベルだけの「注」「警告」「例」は文体統一の対象外とする。

## コード、UI文字列、引用の扱い

- コード、識別子、コマンド、パス、設定キーは、文体に合わせて改変しない。
- UI文字列、エラーメッセージ、ログは、実際の表示を正確に転記する。
- 引用文は原文の文体を保持する。引用の前後に置く説明文だけを「です・ます調」にする。
- コードコメントは、対象プロジェクトの規約を優先する。本文の文体を機械的に持ち込まない。
- 英語の規格語や製品固有の表記は、公式表記を優先する。

## 理科系文書としての基本原則

理科系文書では、読み手が「何を事実として確認できるか」「どの条件で得られたか」「どこからが解釈か」「どの範囲まで結論できるか」を追跡できるように書く。
説明の簡潔さは重要であるが、再現または監査に必要な条件を省略してはならない。

### 科学的記述の優先順位

- 事実、観察、計算結果、推論、主張、提案を区別する。
- 主張には、データ、原資料、引用文献、定義、計算、論理のいずれかの根拠を対応させる。
- 根拠から主張へ進むために暗黙の前提が必要な場合は、その前提または論拠を明示する。
- 文書の結論は、対象、条件、期間、試料、バージョン、母集団など、根拠が支える範囲に限定する。
- 読み手に不利な結果、反例、失敗条件、限界を、結論を弱めるという理由で省略しない。
- 「明らかです」「証明しました」「完全です」のような強い表現は、証拠の強さと分野の用法が支える場合だけ使う。経験的な結果では、「示しました」「支持します」「示唆されます」などを根拠の強さに応じて選ぶ。

### 事実、観察、推論、考察の分離

- **観察・結果**には、測定値、計算値、検出結果、ログ、統計量、目視した現象を書く。原因や価値判断を混ぜない。
- **推論・考察**には、結果の解釈、仮説や理論との比較、代替説明、誤差要因、限界、応用可能性を書く。
- 「結果が増加しました。これはアルゴリズムが優れているためです」のように、観察と原因解釈を無根拠に直結させない。比較対象、評価指標、統計的または実務的な差、機構を示す。
- 「検出されませんでした」を「存在しませんでした」と言い換えない。検出限界、観測範囲、試料数を考慮する。
- 「相関がありました」を「原因でした」と言い換えない。因果を主張するには、設計、時間順序、交絡要因、機構などの根拠が必要である。
- 「統計的に有意ではありませんでした」を「差がありませんでした」「同等でした」と言い換えない。同等性を述べる場合は、同等性の基準と適切な分析を示す。
- 予想と異なる結果も記録する。事後的に立てた説明を、実験前からの仮説であったかのように書かない。

### 再現可能性と追跡可能性

- 読み手が方法を追跡できるように、対象、材料、装置、ソフトウェア、バージョン、設定値、初期条件、環境、試料数、選定基準、前処理、解析方法を必要な範囲で示す。
- 装置の型番、ライブラリの版、データセットの版、乱数シードなどが結果に影響する場合は記載する。
- 標準的な方法を引用だけで済ませる場合も、変更点、適用条件、主要なパラメーターは本文に示す。
- 計画した方法から逸脱した場合、欠測、除外、失敗試行、再測定が結果に影響し得る場合は、その事実と処理方法を示す。
- 実際に行った操作は過去形で書き、現在の仕様、一般法則、図表が示す内容は現在形で書く。予定しただけの操作を実施済みの過去形にしない。
- ここでいう再現可能性は、手順と条件を追跡できる一般的な意味で用いる。計量学上の「反復性」「再現性」などを扱う場合は、その分野の定義を優先する。

### 目的、方法、結果、考察の役割

- **目的・背景**では、対象、未解決の問い、重要性、文書で明らかにする範囲を示す。
- **理論・前提**では、用いる原理、モデル、仮定、適用範囲、記号を定義する。
- **方法**では、結果を得るために何をどの条件で行ったかを示す。結果や考察を先取りしない。
- **結果**では、データと解析結果を整理して示す。図表に記載した全数値を本文で繰り返さず、主要な傾向、差、異常値を述べる。
- **考察**では、結果が何を意味するかを説明し、仮説、理論、文献値、基準値と比較する。結果をそのまま言い直すだけにしない。
- **限界**では、測定範囲、標本、仮定、装置、解析、外的妥当性など、結論の適用範囲を制約する要因を示す。
- **結論**では、目的への回答を根拠の範囲内で示す。新しいデータや未説明の主張を初めて持ち込まない。
- 要約は、目的、方法、主要結果、結論を自立して理解できる形にする。本文にない数値や結論を追加しない。

### 比較、統計、因果

- 比較では、比較対象、対照群、基準値、変更した要因を明示する。比較したい要因以外の条件は、可能な範囲でそろえるか、差があることを記載する。
- ベンチマークでは、ハードウェア、OS、ランタイム、ライブラリ、コンパイラー、設定、入力データ、ウォームアップ、キャッシュ、並列度、反復回数、集計方法を必要な範囲で示す。
- `n` が何を数えるかを定義する。独立した試料・被験対象・実験単位と、同一対象の反復測定や技術反復を混同しない。
- 平均値だけで結論を示さず、データの分布、ばらつき、外れ値、欠測、反復間の差を必要に応じて示す。代表例だけを示す場合は、選定基準を明記する。
- 統計的検定を用いる場合は、検定名、片側・両側、前提、サンプルサイズ、有意水準、多重比較の処理を必要に応じて示す。`p` 値だけでなく、効果量と信頼区間または不確かさも検討する。
- 統計的有意性と、実務的・工学的な重要性を区別する。差が小さくても有意になる場合と、差が大きくても不確かさが大きい場合がある。
- 確証的な解析と探索的な解析を区別する。データを見た後で選んだ仮説、指標、除外条件、解析方法を、事前に定めたものとして記載しない。
- 因果を主張する場合は、介入、時間順序、対照、交絡への対処、機構など、因果解釈を支える設計と根拠を示す。観察研究や単純な前後比較だけから因果を断定しない。

### 数値、単位、有効数字、不確かさ

- 数値には、必要な単位、基準、分母、条件を付ける。「20増加しました」ではなく「平均処理時間が20 ms増加しました」のように書く。
- 物理量は、原則としてSI単位または分野で合意された単位で示す。非SI単位を使う場合は、必要に応じてSIとの対応または換算条件を示す。
- SIの表記では、数値と単位記号の間に半角空白を置く（`25 °C`、`10 kPa`、`5.0 m/s`）。平面角の `30°` など、規則上の例外や投稿規定がある場合は、それに従う。
- 単位記号は立体で書き、複数形や省略のピリオドを付けない。大文字と小文字を区別する（`m` と `M`、`Pa` と `pA` など）。
- 量記号と単位記号を区別する。数式では量記号を斜体、単位記号を立体にすることを基本とする。Markdownや出力媒体で表現できない場合も、記号の定義を一貫させる。
- 測定や解析が支える桁数を超えて表示しない。有効数字、丸め、平均値と不確かさの桁を整合させる。
- 「約」「およそ」「最大」「平均」「中央値」「範囲」を使い分ける。集計値には、対象数 `n` と、必要に応じて分散、標準偏差、信頼区間、不確かさを示す。
- パーセントには分母を示す。母数や除外条件が異なる割合を、そのまま比較しない。
- 誤差、不確かさ、ばらつき、偏りを同じ意味で使わない。分野の定義を示し、エラーバーが何を表すかを明記する。
- 「文献値と一致しました」と書く場合は、許容差、不確かさ、比較基準を示す。見た目が近いだけで一致としない。

### 数式、変数、記号

- 変数、定数、添字、演算子、略号を初出で定義する。
- 数式の前提、境界条件、適用範囲、近似条件を示す。
- 厳密な等号 `=`、近似 `≈`、比例 `∝` を区別する。丸めた値を厳密な等号でつながない。
- 本文から参照する式には番号を付ける。式番号、図番号、表番号の参照先を一致させる。
- 導出は、読者が検証できるだけの中間過程を示す。周知の変形をすべて列挙する必要はないが、仮定の導入や近似の箇所を省略しない。
- 同じ記号を別の意味で再利用しない。似た字形（`l`、`1`、`I`、`O`、`0`）による誤読を避ける。

### 図と表

- 図表は本文中で番号を付けて参照し、本文から孤立させない。
- 図の軸、表の列見出しには、量名または記号と単位を示す。凡例、記号、略語、色、線種を定義する。
- キャプションだけで、対象、条件、主要な処理、エラーバーの意味がある程度分かるようにする。
- 生データ、処理後データ、モデル、近似曲線、予測値を区別する。
- 図表の数値と本文の数値を照合する。同じデータを図、表、本文に完全重複させず、本文では重要な特徴を説明する。
- 表の小数点位置、有効数字、欠測記号を揃える。`-`、`0`、空欄、`N/A`を同じ意味で使わない。
- 色だけに意味を依存させず、線種、記号、ラベルも併用する。縮小、白黒印刷、画面読み上げでも識別できるようにする。
- 視覚的な誇張を避ける。軸の切断、対数軸、正規化、平滑化を用いた場合は明示する。

### 引用、出典、研究上の誠実さ

- 他者の主張、数値、図表、定義、方法を用いる場合は出典を示す。
- 可能な範囲で一次資料、原著論文、規格、公式文書を確認する。二次資料しか確認していない場合は、一次資料を読んだかのように書かない。
- 引用は、直前または直後のどの主張を支えるかが分かる位置に置く。一つの引用で段落内のすべての主張を支えたことにしない。
- 文献の結論を、対象、条件、期間を外して一般化しない。反対結果や主要な異論を無視して、都合のよい文献だけを並べない。
- ウェブ資料、データセット、ソフトウェアには、名称、版、公開主体、公開日または参照日、安定した識別子を必要に応じて記載する。
- 著者自身の計算、推定、再解析、図の再構成は、その旨を示す。
- 確認していない値、存在しない文献、架空の実験条件を補完しない。不明な点は「要確認」とする。
- データや結果を作り出す捏造、都合よく変更・削除する改ざん、出典を示さない盗用を行わない。画像処理、除外、補間、変換、再解析が結論に影響する場合は、その内容を開示する。
- 原データ、実験記録、解析コード、設定、判断記録、変更履歴を、分野の規程と情報管理要件に従って保存する。公開できないデータでは、非公開の理由、利用条件、検証可能な範囲を示す。
- 研究対象、人、社会、環境、安全に関わる影響を扱う場合は、中立性と客観性を保ち、利益相反、倫理審査、法令・規程上の条件を必要に応じて示す。

### 科学用語の境界

- 「精度」が正確度、精密度、分解能のどれを指すか曖昧になる場合は、具体的な用語に置き換える。
- 「検証」は試して確かめる行為であり、必ずしも仮説が正しいと確定したことを意味しない。
- 「改善」「高速」「低コスト」「高性能」には、比較対象、評価指標、測定条件、差の大きさを添える。
- 「安全」「安定」「信頼性が高い」には、試験条件、故障モード、観測期間、基準を示す。
- 「一般に」「通常」「代表的」には、対象範囲または根拠を添える。少数の例を分野全体の性質に拡張しない。
- 同じ概念に言葉の変化を付けない。文体のリズムのために同義語へ置き換えると、別概念と誤読される。

### です・ます調における時制と態

- 確立した法則、現在の仕様、図表が示す内容は現在形で書く。
- 実施した実験、操作、観察、解析は過去形で書く。
- 予定、仮説、予測、今後の課題は、それぞれ「〜する予定です」「〜と仮定します」「〜と予測されます」「〜が課題です」と区別する。
- 行為者や責任主体が重要な場合は能動態を使う。対象や処理を中心にする方が自然で、行為者が不要な場合は受動態を使ってよい。
- 「〜と考えられます」を客観性の演出に使わない。誰の推論か、どの結果に基づくかを明示する。
- 安全上の禁止、仕様上の必須条件、法令・規格上の制約は、敬語で弱めず明確に書く。

## 文書種別ごとの運用

### 概念解説と技術記事

- 定義、前提、例、帰結の順に進める。
- 読者への呼びかけより、対象の仕組みを主語にする。
- 結論を「〜です」、動作や因果を「〜します」で明確に述べる。

### 操作手順とチュートリアル

- 操作主体を読者に固定し、番号付き手順を使う。
- 各手順に、操作対象と期待結果を含める。
- 任意操作、前提条件、警告を本文から分離して明示する。

### API・CLIリファレンス

- 機能、構文、引数、戻り値、エラー、例の順を基本とする。
- 引数説明は名詞句または「〜を指定します」で統一する。
- 実行例の結果を保証する条件を示す。

### 設計書と仕様説明

- 主体、条件、入力、処理、出力、例外を明示する。
- 要件と設計判断を区別する。
- 必須、推奨、任意、禁止の強さを固定する。

### トラブルシューティング

- 症状、確認方法、原因、対処、復旧確認の順を基本とする。
- 未確認の原因を断定しない。
- 破壊的な対処は最後に置き、影響と退避方法を先に示す。

### リリースノートと変更履歴

- 実施済みの変更は過去形で書く。
- 変更内容、利用者への影響、必要な対応を分ける。
- 将来の予定を確定事項のように書かない。

### 実験レポートと研究報告

- 目的、理論・前提、方法、結果、考察、結論、参考文献の役割を分ける。文書の規模や分野に応じて統合してよいが、事実と解釈の境界は保つ。
- 方法には、再現または追跡に必要な材料、装置、条件、試料、手順、解析を示す。
- 結果ではデータを示し、考察では結果の意味、誤差、限界、代替説明を扱う。
- 文献値、基準値、対照群、ベースラインとの比較条件を揃える。
- 予想どおりの結果だけを残さず、結論に影響する失敗や逸脱も記載する。

### 評価報告とベンチマーク

- 評価対象、比較対象、データセット、環境、バージョン、指標、測定回数、集計方法を明示する。
- 一つの指標だけで総合性能を断定しない。速度、精度、資源消費、安定性など、目的に必要な評価軸を分ける。
- 平均値だけでなく、ばらつき、外れ値、ウォームアップ、キャッシュ、再試行など、結果に影響する条件を示す。
- 有利な条件だけを選んで比較しない。除外条件と失敗例を示す。
- 「従来比○%向上」の基準値、計算式、母数を明示する。

## リライト時の保持事項

- 原文の主張、否定、条件、例外、比較対象、因果関係を保持する。
- 「かもしれません」を断定へ変えるなど、確度を勝手に強めない。
- 「推奨」を「必須」に変えない。「可能」を「許可」に変えない。
- 用語の表記揺れを直す場合は、文書内または指定された用語集の基準に合わせる。
- 不明瞭な箇所を補うときは、事実として創作しない。必要なら「要確認」と明示する。
- 原文のコード、数値、単位、バージョン、日付を再確認する。

## 整形

- 一文ごとに改行する。段落の区切りは空行で示す。
- コード、差分、ログ、設定ファイルの断片はコードブロックで示す。
- 用語の由来や定式化の名称など、本筋から一段外れる補足は、本文に並べず脚注（`[^ラベル]`）に降ろす。
- 定義や分類の列挙は箇条書きで示してよい。定義される用語は太字にする。
- 技術解説、教材、社内文書で用語を初めて定義・導入するときは、その語を太字にしてよい。研究論文や投稿原稿では太字を強制せず、投稿規定に従う。すでに導入した語を話題として指すとき、引用、通称には「」を使い、定義との役割を区別する。
- ダッシュ（em ダッシュ `—`、horizontal bar `―`、いわゆる2倍ダッシュ「——」）を日本語の地の文・見出しで使わない。同格・補足の挿入（「A——挿入——B」）は括弧（）に、言い換え・敷衍（「A——B」）は句点で二文に分けるか読点でつなぐ。範囲を示す en ダッシュ `–` や英語の複合語（`Curry–Howard` など）、コードブロック・書誌情報は対象外。
- 中黒（・）は、短い名詞の並列、複合的な分野名、外来語・人名の区切りに使ってよい。ただし、長い句や文の論理関係を中黒だけで表さず、読点、接続詞、箇条書きを使う。同じ文書で用法を統一する。
- 見出し・コラム見出しに、区切り線（罫線 `─` U+2500 やダッシュ類）で「種別──主題」「主題──概念」のように二要素を詰め込まない。見出しは単一の自然な句にする（要素を一つに絞るか、助詞・読点でつなぐ）。コラム見出しも「基礎」「補足」のような種別名だけで済ませず、「同値関係としての分類」「ループ不変条件と帰納法」のように内容を特定する。
- 用語とその定義を並べる箇条書きは、区切り線ではなく全角コロンで「**用語**：説明」と書く。

## 段落と論証の構成

パラグラフライティングを基本とする。段落は論証の一歩であり、読者は段落単位で論理を追えなければならない。

- 一つの段落には一つのトピックだけを置く。場面の進行（調査、報告、検証、評価）が複数混ざった長い段落は、一歩ずつの段落に分割する。
- 段落の最初の文を読めば、その段落が何の話かわかるようにする。
- 前の段落との論理関係は、必要に応じて接続表現、トピックセンテンス、対象語の反復で明示する。すべての段落を接続詞で始めない。
- 各節では、主張、根拠、検討、結論の流れを追えるようにする。要約、序論、考察、結論で主要結果を再提示する場合は、それぞれの役割に合わせて情報量を変え、同じ文章を反復しない。
- 例、モデル、シミュレーション、試料の代表性に制約がある場合は、その例を解釈する箇所の近くで制約を示す。物語上の流れを理由に、限界の説明を後回しにしない。
- 重大な誤読が予想される場合は、否定する解釈と、その解釈が成立しない根拠を具体的に示す。想像上の読者との問答を作る必要はない。
- 「AではなくB」と否定するときは、Aを棄却する根拠とBを支持する根拠を区別する。Aが否定されたことだけでBが確定するとは限らない。
- 譲歩（「確かに〜」「とはいえ」）で認める範囲と、その後も成立する主張を明示する。通説や先行研究へ帰属させる場合は出典を示し、架空の読者の声で根拠を代用しない。
- 科学・技術文書では、数値や主要な事実を演出のために伏せない。物語的な事例を用いる解説でも、結論の理解や安全な判断に必要な情報は先に示す。
- 何かを否定・限定するときは、否定する命題そのものを「」で正確に書き出す（「明文化されていればすべてを任せられる」という意味ではありません、など）。「何もかもが解決するわけではありません」のような漠然とした否定で済ませない。
- 「後の章で扱う」のような前方参照は、論証が一段落した位置（段落末・節末）に置く。論証の途中に挟んで流れを切らない。

## 論証の厳密さ

文章に、論理の飛躍、未提示の前提、反証への未対応を残さない。書き上げたら、想定される反論も含めて次の点を点検する。

- 推量・可能性・読者の疑念・反実仮想として書かれている文を、機械的に断定へ変えない。
  「かもしれません」「でしょう」「ようです」「らしいです」は、根拠なく主張を弱めている場合だけ削る。
  事実未確認の可能性、事例内の人物の認識、ログからの推定、想定される疑念、反実仮想を表す場合は、その不確実性を保つ。
  断定に直せるのは、本文内の根拠によって命題が確定している場合に限る。
  悪い例：「提示し続けているかもしれません」を「提示し続けています」に変える。
  良い例：「提示し続けている可能性があります」のように、不確実性を残して文を整える。
- 異なるものを「同じ」とまとめない。区別すべき対象（別々の決定、別々の原因、種類の違う問題）を一括りの言葉でくくらない。悪い例：相互依存する三つの未決事項を「同じ決定を別々に下していました」と書く。良い例：「どれも別々の決定であり、しかも互いに依存しています」と区別して示す。
- 複数の要因がある事象を、単一の原因に還元しない。例が複数種類の問題を含むなら、それぞれを切り分け、どの道具がどれを説明するのかを対応づける。悪い例：契約の不在と情報隠蔽の失敗が混ざった事故を、丸ごと「情報隠蔽の問題」と説明する。
- 章・節をまたいで、同じ概念の扱いを一致させる。ある節で「人間が決めます」と分類したものを、別の節で「チームで合意します」と書かない。分類・定義・用語の地位は全体で揃える。
- 因果を主張するときは、研究設計、時間順序、対照、交絡への対処、用量反応、機構など、その分野で必要な根拠を示す。機構が未解明なら推測で補わず、因果を主張できる範囲を限定する。
- 検出・保証・解決を「必ず」できるかのように書かない。条件付きで正確に述べる（「〜しやすくなります」「〜できる場合が多いです」「〜が成り立つときに限ります」）。
- 主張は、挙げた例が実際にその全体を支えているかを確認する。例が主張の一部しか支えないなら、主張の範囲を例に合わせて狭める。
- 「次節で扱う」と前方参照した論点は、指定した箇所で実際に扱う。対応しない前方参照を残さない。
- 譲歩や限定（「ただし」「とはいえ」）を置いたら、その後で必ず論を進める。逆接で終えて宙吊りにしない。
- 節の中心となる語は、その節以前に定義・対象範囲を述べてから使う。定義せず使い始めない。
- 複数の概念を一つの上位語にまとめるときは、命名の直前に、それらが同じものに帰着すると
  一文で述べる。複数の概念を統合する根拠を明示する。

## 読み手の負荷の管理

読者の記憶と注意は有限の資源として扱う。

- 議論にも再現・追跡にも不要な固有名は省く。一方、ファイル名、関数名、識別子、装置型番、ソフトウェア版が検証や再現に必要なら、一般化せず正確に残す。
- 抽象的な言い回しの指す内容が文脈から一意に決まらないときは、可能なときは丸括弧による同格挿入でその場で特定し、できるだけ読者に前を読み返させない。
- 新しい例や場面を追加して、読者が保持すべき文脈が増えるときは、前の例と何が違うのか、なぜもう一つ必要なのかを前置きして納得感を与える。
- 章冒頭や節の導入では、これから例で扱う内容に関係しない過剰な詳細を詰め込まない。
- その節の問い、結論、再現、監査、安全判断に関係しない詳細だけを省略する。時刻、HTTPステータス、カバレッジ率、試料情報なども、結果や失敗条件の解釈に関係する場合は残す。情報の種類だけで装飾的と判断しない。

## 視点と語り

- 行為者、責任主体、判断主体が重要な箇所では能動態で明示する。方法や対象を中心に述べる方が自然な箇所では受動態も使えるが、責任や実施者を隠すために使わない。
- 「入社2年目のエンジニアが」のような架空の人物設定を無意味に冠しない。
- 論証の中で読者を「あなた」と呼ばず、役割名（「開発者」「読者」）で書く。二人称の呼びかけは、場面への導入（「〜としましょう」）や章・本の結びなど、限られた要所にとどめる。
- 対象を指す語は具体的に選ぶ。「AI」「ツール」のような広い語でぼかさない。
- 章や節で定式化・術語（K、契約、不変条件など）を導入したら、以後はその語で通す。「文脈」「ツール」「AI」のような曖昧語に後退しない（定式化する前の導入語として「文脈」などを使うのはよい）。
- 術語・訳語は、その分野で慣用されている語を選ぶ（プッシュ通知は「配送」ではなく「配信」、など）。意味の近い漢語を一般語の感覚で充てない。
- 人名は、分野の慣用、引用元、文献一覧の表記と整合させる。原綴りとカタカナ表記を併記する場合は、初出時の方式を文書全体で統一する。
- 術語の響きを持つ語を、術語でない場面に流用しない（システムから人間までの連なりを「経路」と呼ぶ、など）。「届くまでの流れ」「あいだに何があるか」のように普通の言い方で書く。

## 演出の抑制

演出の規範は全面禁止ではなく、節度の規範である。修辞は、それが効果を生む箇所でのみ使う。

- 実験報告、研究報告、仕様書では、溜めや修辞疑問で導出を演出せず、問い、方法、結果を直接述べる。技術記事や教材で用いる場合も、理解を助ける箇所に限定する。
- 印象を強めるためだけの短文を独立段落にしない。研究報告と仕様書では体言止めを避け、技術記事で使う場合も文意が完結し、文体統一を損なわない形にする。
- 本文中の太字強調を多用しない。誤読を防ぐ否定、定義、警告などに限定し、研究論文や投稿原稿では投稿規定に従う。固定の回数ではなく、強調がなくても構造を追えるかで判断する。
- 要件、規格、安全上の禁止では、「〜してはなりません」「〜しないでください」のように明示する。解説本文で命令調が不要な場合だけ、作業者の判断として説明する形を検討する。
- 転回点を過剰に劇的にしない。研究報告、仕様書、手順書では感嘆符を原則として使わない。技術記事で使う場合も、安全警告や感情的な強調の代用にしない。
- 帰結の列挙によって事故や危険を煽らない。
- 「重要なのは〜です」のような前置きで主張を予告しない。主張をそのまま書く。ただし、主張の様式を宣言する前置き（「標語として言い換えれば」など）は使ってよい。
- 「AではなくBでした」という対句を、印象を強める目的で多用しない。Aを否定しBを支持する根拠がある場合に使う。
- 慣用表現をひねった言い回し（「知識を体に入れる」など）や、指す内容が一意に決まらない比喩（「報告の外側に世界が広がっています」など）を使わない。平易な動詞でそのまま言う（「身につきます」「気付く機会が減ります」）。

## 空疎な定型表現の抑制

出所にかかわらず、内容を増やさずに姿勢、重要性、網羅性だけを演出する定型表現を抑える。
同じ表現でも、文書構造の案内、定義済みの専門用語、根拠のある評価として必要なら使用できる。語句を一律禁止せず、その文が具体的な情報を運んでいるかを確認する。

次のような言い回しは、具体的な対象、操作、基準、根拠を伴わない場合に削除または具体化する。

- **予告と総括**：「重要なのは〜です」「ここでは〜について見ていきます」「まとめると」「要するに」（直前の言い換えだけの場合）。長い文書の道案内として「本章では〜を扱います」が必要なら、対象と範囲を具体的に示す。
- **姿勢の宣言**：「正面から扱います」「丁寧に検討します」「深く考察します」など、対象、方法、評価基準を示さず姿勢だけを宣言する表現
- **空虚な形容**：「不可欠」「核心的」「鍵となる」「根本的な」（要件や根拠を示さず強調だけする場合）、「多角的」「包括的」「総合的」（評価軸や対象範囲を示さない場合）
- **空虚な動詞**：「掘り下げます」「深掘りします」「言語化します」（何をどう書いたかを示さず終わる）、「触れます」「言及します」（一段落で済ませるだけ）
- **接続の型**：「〜において」「〜という側面から」「〜の観点から」が対象や評価軸を特定していない用法、「さらに」「また」「加えて」の連打
- **弱い緩和と称賛**：「〜と言えるでしょう」「〜かもしれません」（根拠なく主張を弱める場合だけ。推量、仮定、想定される疑念、事例内の人物の認識なら残す）、「非常に」「極めて」「大いに」（根拠のない強調）

悪い例：「本章では、〇〇の理論を正面から扱います」「この前提を丁寧に検討します」「多角的に分析すると、重要なのは〜です」。
良い例：「本章では、〇〇理論の適用条件を扱います」「この前提を式（3）の導出に用います」「評価基準は、誤差率と処理時間です」。

## 冗長の排除

無駄な文章をなるべく残さない。

- 同じ役割の箇所で、同じ主張を言い換えて繰り返さない。要約、本文、結論で主要結果を再提示する場合は、各箇所の目的に合わせて粒度を変える。
- 隣接する節が同じことを別の角度で述べているなら、役割が重複している。片方に吸収して一つの節にまとめる。
- データ、事例、図表を示した直後に同じ内容を逐語的に反復しない。本文では、読み取るべき傾向、比較、例外、解釈を示す。
- 同じ論理的役割を持つ事実は、箇条書き、一文、複数文のうち、比較軸と対応関係が最も明確になる形で示す。文をまとめることで主語や条件が曖昧になる場合は分ける。
- 周知の変形や自明な操作は簡略化してよい。ただし、結論の検証、手順の再現、近似や仮定の把握に必要な中間段階は省略しない。
- 数文を一文にまとめるのは、条件、根拠、結論の対応が明確な場合に限る。圧縮によって文が長くなる、論理段階が隠れる、検証しにくくなる場合は分ける。
- 接続や評価のためだけの文（「それ自体はよいことです」など）を置かない。
- 想像上の読者との問答（問いを立てて一語で答える形など）を修辞として使わない。主張はそのまま述べる。読者の反応を演じて応答する形（「〜と感じたかもしれません。そのとおりです」）も同様に避け、譲歩は地の文で簡潔に行う（「もちろん、処置そのものは開発者が決める問題ではありません」）。
- 読者が抱きそうな発想を、メタな枠取り（「ここまでの話には自然な続きがあります」「〜という発想です」）で紹介しない。その発想自体を直接書く。読者の疑問なら疑問文のまま書いてよい（「その保守も任せればよいのではないでしょうか」）。
- 「本稿もそれを否定しません」のような、根拠を示さない立場表明を置かない。必要な場合は、認める範囲、根拠、その後の主張を具体的に書く。
- 文脈を最短で読み手と共有できる文章にする。導出を一歩ずつ展開しなくても伝わるなら、構造に名前を与えて言い切る。
- 本文でまだ導入していない概念や文書名を、先回りして持ち出さない。
- 断定の強さは、要件の地位と証拠の強さに合わせる。根拠が確定している事項は具体的に書き、不確実性、可能性、仮定は保持する。語調を整えるためだけに「必須」を弱めたり、推定を強めたりしない。
- 複合した接続表現は、二つの論理機能が必要な場合に限る。「しかし一方で」「またさらに」などは、一語で関係を示せるなら簡略化する。文章のリズムだけを理由に重ねない。

## 見出しの付け方

見出しは内容を特定できる具体的なものにする。その節が答える問い、または扱う対象を指す句にする。

- 作業の手順だけを述べる見出し（「例に戻す」「〜を読み直す」など）や、情報量のない見出しにしない。その節が答える問い、または扱う対象を見出しにする。
- 見出しは文書の目的に合わせる。研究報告、評価報告、障害報告では、主要な知見や状態を見出しに含めてもよい。結論を後まで伏せるために情報を隠さない。
- 節で扱っている対象を指す名詞句でもよい。
- 見出しが疑問形か断定形かは問わない。問うのは、扱う対象や読者の持つ問いを指しているかである。
- 疑問形か、対象を指す名詞句かは、本文のトーンに合うほうを選ぶ。

## 読者への誠実さ

- 例、試料、データ、モデルが作為的または限定的に見え得る場合は、選定理由、代表性、適用範囲、限界を明示する。
- 現実性や一般性の根拠には、データ、出典、選定基準、対象範囲を用いる。読者の経験、通説、「よくある」という未確認の印象で代用しない。
- 確認していないことを、確認したかのように滑らかに書かない。


## 作成・推敲の実行手順

1. 文書の種類、想定読者、目的、前提知識、適用する投稿規定または組織規則を特定する。
2. 事実、観察、推論、要件、推奨、推定、例を区別する。
3. 理科系文書では、目的、方法、結果、考察、結論の役割と、再現または追跡に必要な条件を整理する。
4. 見出しと段落の役割を決め、各主張に根拠と論拠を対応させてから本文を書く。
5. 接続詞ごとに前後の論理関係を確認し、不要な接続詞と、論理を偽装する接続詞を削る。
6. 本文を「です・ます調」で統一し、手順と仕様のモダリティ、時制、確度を調整する。
7. コード、UI文字列、引用、数値、単位、有効数字、図表、固有名、バージョンを原資料と照合する。
8. `CHECKLIST.md` の順に内容、科学的妥当性、論理、文体、表記を確認する。
9. 利用者から求められていない限り、推敲過程や自己評価を本文へ混ぜず、完成稿だけを出力する。

- [ ] 結論が対象、条件、期間、試料、バージョンの範囲内です。
- [ ] 推量や可能性の確度を、文体変換によって強めていません。

- [ ] 目的、理論・前提、方法、結果、考察、結論の役割が区別されています。
- [ ] 方法に対象、材料、装置、ソフトウェア、版、設定、環境、試料数を必要な範囲で記載しています。

- [ ] 乱数シード、初期条件、ウォームアップ、キャッシュなど、結果に影響する条件を示しています。

- [ ] 実際に行った操作を過去形で書いています。
- [ ] 現在の仕様、一般法則、図表の内容を現在形で書いています。
- [ ] 計画からの逸脱、失敗試行、再測定が結果に影響する場合、その処理を記載しています。
- [ ] 結果ではデータを示し、考察では意味、誤差、限界、代替説明を扱っています。
- [ ] 結論に新しいデータや未説明の主張を初めて持ち込んでいません。
- [ ] 要約、本文、結論で主要結果を再提示する場合、各箇所の役割に応じて粒度を変えています。

## 5. 要件とモダリティ

- [ ] 「できます」を能力または実現可能性の意味で使っています。
- [ ] 許可は「〜してもかまいません」などで明示しています。
- [ ] 必須条件は「〜する必要があります」「〜しなければなりません」で示しています。
- [ ] 推奨は「〜することを推奨します」「通常は〜します」で示しています。
- [ ] 禁止や危険回避を、婉曲表現で弱めていません。
- [ ] MUST、SHOULD、MAYなどの規格語の対応が文書全体で一定です。
- [ ] 「原則として」「通常は」「場合があります」に条件または例外があります。
- [ ] 「必ず」「完全に」「すべて」を使う根拠があります。
- [ ] 「および」「または」の結合範囲が明確です。
- [ ] 包含的選言と排他的選言を、必要に応じて明示しています。
- [ ] 網羅的な要件に「や」「など」を使っていません。
- [ ] 「および」「ならびに」、「または」「もしくは」の階層が意図どおりです。
- [ ] 「かつ」は、複数条件を同時に満たす意味で使っています。
- [ ] 「および／または」を使う場合、許される組合せを一意に解釈できます。
- [ ] 複雑な条件を、括弧、箇条書き、決定表、論理式へ分解しています。

## 6. 接続詞と論理関係

- [ ] 接続詞を置く前に、前後の関係を言語化できます。
- [ ] 接続詞を削っても関係が明白な箇所では、不要な接続詞を削除しています。
- [ ] 「したがって」は、前件から後件が論理的に導ける場合に使っています。
- [ ] 「そのため」は因果的な結果、「そこで」は主体の対応に使っています。
- [ ] 「このことから」「以上から」の受けるデータや範囲が明確です。
- [ ] 「しかし」は逆接、「一方で」は同じ軸での対比に使っています。
- [ ] 「ただし」は条件・例外、「なお」は本筋を変えない補足に使っています。
- [ ] 「また」は同格の追加、「さらに」は累加に使っています。
- [ ] 「すなわち」は厳密な同値・定義、「言い換えると」は説明的な言換えに使っています。
- [ ] 「例えば」の例が、一般命題を過剰に代表していません。
- [ ] 「まず」「次に」「最後に」や番号の対応が取れています。
- [ ] 「なぜなら」「というのも」で提示した理由を文中で回収しています。
- [ ] 「から」「ので」「ため」「ことから」を機械置換せず、因果関係、焦点、分野の慣用、投稿規定に合わせています。
- [ ] 「しかし一方で」「またさらに」などを、必要なく重ねていません。
- [ ] 同じ接続詞で連続する文や段落を始めていません。
- [ ] 接続詞の後の読点と、仮名・漢字の表記が文書内で統一されています。
- [ ] 接続助詞「が」を、単なる話題継続のために使っていません。
- [ ] 「ので」「から」「ため」や連用形を連ねて、一文を長くしていません。
- [ ] 並列・選択条件の結合範囲を、接続詞と読点だけに頼らず一意に示しています。

## 7. です・ます調

- [ ] 完結した地の文が「です」「ます」とその活用形で終わっています。
- [ ] 「だ。」「である。」「だった。」「ではない。」が地の文に混在していません。
- [ ] 否定は「〜しません」「〜ではありません」で統一されています。
- [ ] 過去の事実は「〜しました」「〜でした」で統一されています。
- [ ] 文末変化のためだけの体言止めや未完文を使っていません。
- [ ] 「ます」が続くことを避けるために、不自然な言い換えをしていません。
- [ ] 「です」と「ます」の対応が述語の種類に合っています。
- [ ] 「作成しましたファイル」のように、連体修飾まで機械的に敬体へ変えていません。
- [ ] 主節の文末と、条件節・連体修飾・引用内容の普通形を区別しています。
- [ ] 見出しは本文調にせず、内容を特定する名詞句または疑問形になっています。
- [ ] 完全文の箇条書きも「です・ます調」で統一されています。
- [ ] 安全上の禁止や必須要件を、敬体によって弱めていません。

## 8. 敬語と冗長な定型句

- [ ] 単なる同定に「〜となります」を使っていません。
- [ ] 変化しない値や名称に「〜になります」を使っていません。
- [ ] 「〜することができます」を、必要に応じて「〜できます」に縮めています。
- [ ] 技術説明の進行に「〜させていただきます」を使っていません。
- [ ] 「ご確認いただけますでしょうか」のような過剰に婉曲な依頼を使っていません。
- [ ] 「ございます」を、必要のない箇所で使っていません。
- [ ] 「〜のほう」「〜という形」「〜といったところ」を削除しています。
- [ ] 「思います」「感じます」を根拠の代わりに使っていません。
- [ ] 「〜と考えられます」で書き手や根拠を隠していません。

## 9. 手順と操作説明

- [ ] 前提条件を手順の前に示しています。
- [ ] 手順を実行順に並べています。
- [ ] 一つの番号に一つの主要操作を置いています。
- [ ] 操作主体が読者、システム、管理者のどれか明確です。
- [ ] 操作対象と入力値を具体的に示しています。
- [ ] 各操作の期待結果または確認方法を示しています。
- [ ] 任意の操作を「必要に応じて」「任意で」と明示しています。
- [ ] 危険な操作の前に、危険、影響、回避方法を示しています。
- [ ] UI文字列を実際の表示どおりに記載しています。
- [ ] システムの動作を読者への依頼形で書いていません。
- [ ] 破壊的な操作には、退避、復旧、ロールバックの方法があります。

## 10. 段落と論証

- [ ] 一つの段落に一つのトピックだけがあります。
- [ ] 段落の最初の文から、その段落の役割が分かります。
- [ ] 前後の段落の関係が、接続詞、トピックセンテンス、対象語の反復で分かります。
- [ ] すべての段落を接続詞で始めていません。
- [ ] 主張、根拠、論拠の関係が成立しています。
- [ ] 否定する命題を具体的に書き出しています。
- [ ] 「AではなくB」と書いた箇所に、否定の根拠があります。
- [ ] 譲歩や限定の後で論を進めています。
- [ ] 前方参照した論点を、指定した箇所で回収しています。
- [ ] 節の中心用語を使う前に定義しています。
- [ ] 章や節をまたいで、定義と分類が一致しています。
- [ ] 科学・技術文書の主要結果を、物語的な山場のために遅らせていません。

## 11. 読みやすさと情報量

- [ ] 読者が覚える必要のない固有名を削除しています。
- [ ] 再現や追跡に必要なファイル名、識別子、型番、版は削除していません。
- [ ] 指示語が何を指すか一意に分かります。
- [ ] 新しい例を追加する理由が分かります。
- [ ] 導入部に不要な詳細を詰め込んでいません。
- [ ] 再現、判断、安全に必要な具体情報は残しています。
- [ ] 一文が長すぎる場合、論理単位で分割しています。
- [ ] 結論の検証や手順の再現に必要な中間段階を省略していません。
- [ ] 同じ主語を省略しても参照先が一意に決まります。
- [ ] 受動態の連続を避け、責任主体が必要な箇所では行為者を示しています。
- [ ] 主語、述語、修飾語、目的語が離れすぎていません。
- [ ] 読点の位置によって複数の意味に取れません。

## 12. 用語、略語、記号

- [ ] 初出の用語、略語、変数、記号を定義しています。

- [ ] 分野で慣用されている訳語を使っています。

- [ ] 誤差、不確かさ、ばらつき、偏りを区別しています。

- [ ] ベンチマークの環境、版、設定、入力、ウォームアップ、反復回数、集計方法を示しています。

- [ ] 平均値だけでなく、分布、ばらつき、外れ値、欠測を必要に応じて示しています。
- [ ] 代表例を掲載する場合、選定基準があり、都合のよい例だけを選んでいません。
- [ ] 統計的検定の名称、片側・両側、前提、有意水準を必要に応じて記載しています。
- [ ] 多重比較を行った場合、その処理を記載しています。
- [ ] `p` 値だけに頼らず、効果量、信頼区間、不確かさ、実務上の差を検討しています。
- [ ] 確証的解析と探索的解析、事前に定めた解析と事後的な解析を区別しています。
- [ ] 相関や単純な前後比較だけから因果を断定していません。
- [ ] 因果を述べる場合、介入、時間順序、対照、交絡、機構などの根拠があります。

- [ ] エラーバー、色、線種、記号、欠測値の意味を示しています。
- [ ] 図表と本文の数値が一致しています。
- [ ] 同じデータを図、表、本文で完全重複させていません。
- [ ] 色だけに意味を依存していません。
- [ ] 軸の切断、対数軸、正規化、平滑化を明示しています。
- [ ] 他者の主張、数値、図表、定義、方法に出典があります。
- [ ] 引用の位置から、どの主張を支えるか分かります。
- [ ] 一次資料を確認していない場合、確認したかのように書いていません。
- [ ] 文献の対象、条件、期間を外して一般化していません。
- [ ] 資料名、著者、版、公開年、識別子、参照日を必要に応じて記載しています。
- [ ] 著者自身の計算、推定、再解析、図の再構成を明示しています。
