# 1.6 RAGで新たに設計すべき対象

RAGを導入すると、モデルや検索製品だけでなく、知識源、検索単位、版、権限、根拠、評価、監視までが設計対象になります。これらを後付けにすると、検索品質、引用、更新、監査の責任境界が曖昧になります。

後続章で決める主な対象を、表1-3に整理します。左列は設計対象、中央列は最低限決める内容、右列は詳しく扱う章です。

**表1-3　RAGで新たに設計する対象**

| 設計対象 | 最低限決める内容 | 主に扱う章 |
|---|---|---|
| 情報源 | 正本、所有者、更新方法、利用条件 | 第3章 |
| 文書解析とchunk | 読み順、表・図の扱い、検索単位、stable ID | 第3章 |
| metadataとACL | 版、鮮度、provenance、検索時の認可 | 第3章・第8章 |
| embeddingとindex | model、distance、index方式、更新・切替方法 | 第3章 |
| retrieval | query理解、検索方式、filter、候補数 | 第4章 |
| Evidence Set | rerank、重複、圧縮、矛盾、根拠の十分性 | 第5章 |
| answerとcitation | 回答形式、回答保留、主張と根拠の対応 | 第6章 |
| evaluation | golden data、工程別指標、回帰、release gate | 第7章 |
| operation | security、privacy、監査、性能、cost、governance | 第8章 |
| advanced methods | 基本構成で残る失敗と、導入する高度化手法 | 第9章 |

これらは独立したチェック項目ではありません。例えばchunkの変更はembeddingとindexの再構築を必要とし、retrievalの結果はEvidence Setとcitationの品質を制約します。変更の影響を追えるように、各工程の入力、出力、版、traceを対応付けます。

最初からすべてを高度化する必要はありません。まず対象情報源、基本的な検索、根拠付き回答、評価可能なログを揃え、評価で観測した失敗に応じて設計を追加します。第2章では、この設計対象を一つの処理の流れとして整理します。
