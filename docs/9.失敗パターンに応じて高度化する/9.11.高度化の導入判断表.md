# 9.11 高度化の導入判断表

高度化手法は、名前の新しさや機能数ではなく、baselineで再現したfailureから選びます。表9-2は、観測した失敗、最初に確認するbaseline、候補となる高度化を対応付けています。

## 9.11.1 failure patternと候補手法

**表9-2　failure patternから選ぶ高度化手法**

| 観測したfailure | 先に確認するbaseline | 高度化の候補 |
|---|---|---|
| 省略や過去turnを解決できない | query rewriting、session境界 | Conversational RAG |
| 複数sourceを横断できない | source catalog、routing、fusion | Federated・Routed RAG |
| DB集計・現在値・厳密計算が必要 | 文書RAGとの責務分離 | Structured Data RAG・tool |
| 一文書全体の論旨を失う | chunk、parent-child、packing | Long-context・Hierarchical RAG |
| entity関係やmulti-hopを落とす | query decomposition、multi-query | GraphRAG |
| 図表・画像が根拠なのにtext化で失う | parser、layout、caption | Multimodal RAG |
| 複数stepの探索・検証・業務操作が必要 | 固定workflow、read-only API | Agentic RAG |
| 根拠があってもmodelが無視する | prompt、context、verification | Retrieval-aware training |
| distractorへ強く引かれる | reranker、Evidence Set、verification | Retrieval-aware training |
| qualityは上がるがlatency・costが悪化 | routing、cache、model選択 | 条件付きrouting・cascade |

一つのfailureに複数手法が候補となる場合は、最も小さく、rollbackしやすく、既存のevaluation contractを保てる方式から試します。例えば長文の失敗に対して、最初からGraphRAGとAgentic RAGを同時導入せず、parent-child retrievalまたはlong-context routingを個別に比較します。

## 9.11.2 導入順序と停止条件

導入前にfailureを固定datasetとtraceで再現し、期待改善、guardrail metric、最大latency、cost budget、security条件を決めます。新方式とbaselineを同じ条件で比較し、局所的な成功例だけで判断しません。

高度化後も改善が再現しない、別sliceを悪化させる、運用負荷やsecurity riskが許容範囲を超える場合は採用を止めます。限定公開では旧経路を残し、異常時にbaselineへ戻せるようにします。

高度化の完了条件は部品の実装ではなく、対象failureの改善、回帰なし、trace可能性、運用手順、rollback試験が揃うことです。
