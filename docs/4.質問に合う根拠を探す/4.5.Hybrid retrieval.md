# 4.5. Hybrid retrieval

疎検索と密検索など複数のretrieverが返す候補を、定義済みの統合規則で一つの順位へまとめる処理をhybrid retrievalとします。
語彙一致と意味一致の失敗を補い合い、識別子と自然な症状説明が同居する業務質問へ対応します。

## 4.5.1. Hybrid retrievalを使う理由と基本pipeline

「ERR-1042が出てログインできません」という質問には、エラーコードの完全一致と、ログイン障害の意味一致が含まれます。
identifierを含むqueryではsparse retrieval、言い換えた症状を含むqueryではdense retrievalが異なるcandidateを回収し得るため、両query sliceを分けて評価します。

[BEIR](https://arxiv.org/abs/2104.08663)の評価でも、検索方式の優劣はデータセットによって変わりました。
どちらか一方を万能と見なさず、異なる候補生成器として組み合わせます。

semantic matchingとlexical matchingを組み合わせた同研究のnews collectionでは、BM25とsemantic searchが異なる関連文書を取得し、統合結果のRecallがBM25単独より相対約2.8%高いと報告されています。
この論文の評価結果を適用できる範囲は、論文が用いたTREC文書集合と質問集合です。処理時間と保存容量は、この結果から推定せず、対象環境で別途測定します。
この値を導入目標にはせず、二方式が互いの検索漏れを補うかを対象業務で確かめます。

ハイブリッド検索は常に単独方式より良いとは仮定せず、同じgold evidenceと候補件数で疎検索・密検索・統合後を比較します。
疎検索、密検索、ハイブリッド検索を同じ正解集合で比較し、改善がない質問群には単純な経路を残します。

本ガイドのハイブリッド検索では、各検索器の候補を取得してからRRFまたはrerankerで統合し、尺度の異なる生スコアを無条件には加算しません。
次の段階へ分けます。

1. 同じ認可・時点条件を疎検索と密検索へ適用します。
2. 各検索器を独立して実行し、候補と順位を得ます。
3. 文書版とチャンクIDで同一候補を統合します。
4. 必須フィルターを再確認します。
5. 順位または調整済みのスコアで候補を統合します。
6. 統合候補を必要に応じて再順位付けします。

各段階の候補IDと順位を保存します。
必要根拠が取得されなかったのか、フィルターで落ちたのか、統合後に下がったのかを区別できます。

## 4.5.2. Soft constraintとboost

製品、地域、言語、鮮度などは、利用者が明示したか、モデルが推定したかによって扱いを変えます。
明示条件は必須フィルター、推定条件は順位調整条件や別経路として使うと、誤推定で正解を完全に除外しにくくなります。

情報源の信頼度も、関連度とは別の軸です。
信頼度の低い文書が質問に近い場合に、そのまま正式資料より優先されない規則を設けます。

順位をどの程度引き上げるかを数値で定め、その値の意味を記録します。
版違いを同時に返す用途では、現行、過去、例外の優先規則を決めます。
重みの変更を評価し、どの質問と候補へ影響したかを記録します。

## 4.5.3. Candidate identityと重複

複数retrieverが同じchunk_idを返した場合は一件へ統合し、根拠数を二件として数えません。
文書ID、文書版ID、チャンクIDを基本として、同一候補を統合します。
どの検索器が候補の取得に役立ったかを分析できるよう、発見元を保持します。

親子chunk、mirror、language版、region版、旧版にはrelation_typeを付け、独立source数の集計から区別します。
内容が似ているだけで一つにまとめると、適用条件と出所を失う可能性があります。
完全重複、近似重複、同一文書系列の別版を区別します。

一つの文書・情報源が候補を占有しないよう上限を設けられます。
ただし、複数箇所が必要な質問で根拠を落とさないかを評価します。

## 4.5.4. RRF・score normalization・query-dependent fusion

RRF scoreは各順位一覧のrankと固定定数kから計算し、入力一覧、depth、kをtraceへ保存します。
一般的な形は `1 / (k + rank)` を一覧ごとに合計します。
BM25とcosineの生scoreは同一尺度へ変換せず、RRFでrankを統合するか、校正済みscoreだけを重み付き統合します。

RRF原論文は、対象としたrank listと評価collectionについて、順位の逆数に基づく統合が個別方式および比較対象の統合法を上回る結果を報告しています。
RRFの統合結果は、入力する順位一覧、各一覧の検索深度、定数`k`を固定した条件で比較します。

検索器間だけでなく、複数の検索文の間の統合にも利用できます。
候補を返さなかった検索器の扱いと、各検索器が統合スコアへ与えた寄与を記録します。

本書の実装規約では`rank`を1始まりとし、ある候補を返さなかった順位一覧からの寄与を0とします。各検索器が返す深度を先に固定し、同じ`document_id`、版、`chunk_id`の候補を一件へまとめてから寄与を合計します。全検索器が0件なら空の候補集合を返し、RRFだけを理由に回答可能とは判定しません。同点は安定した候補IDで決定的に並べます。

たとえば、疎検索が`A、B、C`、密検索が`C、A、D`の順で返し、`k=60`なら、統合スコアは次のとおりです。

| 候補 | RRFスコア | 統合順位 |
|---|---:|---:|
| A | `1/61 + 1/62 = 0.03252` | 1 |
| C | `1/63 + 1/61 = 0.03227` | 2 |
| B | `1/62 = 0.01613` | 3 |
| D | `1/63 = 0.01587` | 4 |

`k`と検索深度は固定値とみなさず、開発用データで調整します。最小比較では`k`を`10、30、60、100`、各検索器の深度を`10、20、50、100`から選びます。候補数を増やしたときのRecall@k、nDCG@k、遅延、後段の再順位付け費用を測り、未使用の保留用データで最終確認します。

本ガイドでは、図4-6を「左側の疎検索と密検索が作った二つの順位表を、右へ向かって統合する流れ」として用います。
同じ文書を一件にまとめた後、RRFは元の点数を直接足さず、各順位表での順位だけを使います。
本ガイドでは、RRFを各検索器の順位を統合する工程、再順位付けを統合後の候補本文を再評価する工程として区別します。
図中の「再ランキング」は本文の「再順位付け」と同じ処理です。

**図4-6　疎検索と密検索の順位をRRFで統合する流れ**

元スコアを使う統合では、BM25とコサイン類似度を未調整のまま加算しません。
BM25とcosineをscore統合する場合は、対象queryごとの分布、値域、大小方向を測り、同じ尺度と仮定しません。

本節では、検索スコアの正規化として、最小–最大変換、標準得点化、順位変換を扱います。
正規化後に重み付き和を取る場合、重みは質問群と正解集合で調整します。
[ハイブリッド検索の統合法を比べた研究](https://arxiv.org/abs/2210.11934)では、正規化を完全に省くと、検索器間のスコア尺度の違いによって性能が不安定になりました。
min-max、z-score、rank変換は同じ候補集合で重みを再調整し、最大nDCGだけでなく安定性と外れ値影響を比較します。
RRFはk、入力depth、retriever数を個別に変え、validation sliceごとのRecallとnDCGで設定を選びます。

アルゴリズム図A8は、点数を合わせる経路と順位を合わせる経路を分けています。
重み付き融合では、BM25と密検索の生スコアをそれぞれ正規化してから、評価で決めた重みを適用します。
RRFは生スコアを使わず、各順位表の順位を統合します。どちらも同じgold evidenceで比較し、未調整の生スコアは直接足しません。

![BM25とDenseの結果を、正規化後の重み付き融合または順位だけを使うRRFで統合する比較](../../assets/images/v4/43-hybrid-fusion-strategies.png)

**アルゴリズム図A8　正規化・重み付き融合とRRFの違い**

検索モデル、インデックス、文書集合が変わるとスコア分布も変わります。
重みを再調整し、変更前の品質を保つ試験を行い、元スコア、変換後スコア、特徴ごとの寄与を保存します。

質問の種類が分かる場合は、検索方式の比重を質問ごとに変えられます。
型番・条文番号sliceでは疎検索、説明文sliceでは密検索の重みを候補にし、固定validation setで比率を決めます。
識別子と症状が混在する質問では、両方式に最低候補数を確保します。

経路の振り分け処理が誤ると、正しい検索器の候補を減らす可能性があります。
確信が低い場合は、方式を一つに絞らず、事前に定めたRRFへ戻すなどの代替経路を使います。

選んだ検索器、重み、質問分類、判定の確かさを処理記録へ残します。
質問の種類ごとに振り分け処理と検索結果を評価し、全体平均で誤判定を隠しません。

## 4.5.5. Multi-queryとの組み合わせ

三つの検索文を二つの検索器へ送ると、六つの順位一覧が生まれます。
すべてを一度に統合すると、似た検索文が同じ文書を繰り返し押し上げ、誤って生成された検索文が候補を支配する可能性があります。

検索文ごとに疎検索と密検索を統合し、その後に検索文間を候補上限付きで統合するなど、順序を定めます。
互いに似た検索文と重複候補を早い段階でまとめます。

検索文数、検索器数、各候補数の積を処理予算として監視します。
候補には発見元の検索文と検索器を結び付け、正解根拠を追加しない検索経路を評価で削除します。

## 4.5.6. Fusionとrerankingの境界

複数の順位一覧を候補IDで結合し、統合scoreと最終rankを付ける処理を順位統合と定義します。
候補本文と質問を新たに精読して、関連性を判定する処理ではありません。
再順位付けは、質問と各候補を同時に入力し、候補間の順序をより精密に見直します。

最初に疎検索と密検索で必要な根拠を拾い、順位統合後の数十件を再順位付けして、LLMへ渡す数件へ絞る構成が候補です。
候補数は例であり、対象質問、応答時間、費用で評価します。

アクセス制御リスト（Access Control List：ACL）の判定を再順位付け器のスコアへ委ねません。
再順位付け器が時間内に終わらない場合は、認可済みの統合順位へ戻すか、回答を保留します。
