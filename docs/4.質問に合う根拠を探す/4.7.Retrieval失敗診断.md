# 4.7. Retrieval失敗診断

retrievalの候補不足は、corpus欠損、indexの古さ、解析・分割、質問変換、filter、順位付けの原因へ分けて診断します。正解根拠が候補へ入らない場合でも、query、語彙、embedding、filter、routing、chunk、indexのどこに原因があるかで修正方法は変わります。

## 4.7.1. Candidate recallとquery mismatch

最初に、gold evidenceがtop-kへ入ったかを確認します。入っていない場合は、元query、正規化後query、展開queryごとに候補を比較し、質問条件が失われたのか、検索語が資料側と一致しないのかを分けます。

固有名詞、型番、条文番号を含む質問ではexact matchとsparse retrievalを確認します。言い換えが中心ならdense retrievalを確認します。複数論点を含む質問では、query decomposition前後のrecallを比較します。

## 4.7.2. 語彙不一致とembedding不一致

sparseだけが失敗する場合はtokenization、辞書、field、exact match条件を調べます。denseだけが失敗する場合はmodel、query・document encode、domain、言語、chunk長、similarity metricを調べます。両方が失敗する場合は、情報源の欠落、誤った正本、chunk境界を先に疑います。

検索器を追加する前に、失敗質問を種類別に固定します。同じ質問集合で変更前後を比較し、平均scoreの上昇ではなくgold evidenceの回収と不要候補の増加を同時に測ります。

## 4.7.3. filter・routing・chunk・indexの失敗

filter前には正解候補があるのにfilter後に消える場合は、metadataの欠損、型、継承、期間計算、ACLの過剰適用を確認します。routing先だけに正解がない場合は、query分類とsource catalogの契約を確認します。

正解箇所が複数chunkへ分断されている場合や、親文書へ戻らないと条件が読めない場合はchunk設計の問題です。新しい版が候補へ入らない場合は、ingestion、publish alias、cache、delete・freshness伝播を確認します。

**表4-2　retrieval失敗と最初に確認する箇所**

| 観測した失敗 | 最初に確認する箇所 | 主な修正先 |
|---|---|---|
| exactな識別子を落とす | tokenization、field、完全一致 | 4.3 |
| 言い換えを落とす | embedding、domain、query encode | 4.4 |
| filter後だけ正解が消える | metadata、ACL、期間条件 | 4.6 |
| 特定sourceだけ検索されない | query分類、routing、source契約 | 4.1・9.2 |
| 条件と結論が別chunkになる | chunk境界、parent-child | 3.4 |
| 最新版が出ない | ingestion、index alias、cache | 3.2・3.7 |

## 4.7.4. 第4章で直す問題と高度化する問題

query normalization、検索器の設定、fusion、filter、chunk、indexの修正で再現失敗を解消できるなら、第4章までのbaselineを改善します。失敗理由を説明できないままGraphRAGやAgentic RAGを追加してはいけません。

会話状態、複数source、構造化data、長文全体、関係探索、図表、複数回の計画的検索が不可欠だと確認できた場合に、第9章の方式を検討します。導入判断では品質だけでなく、latency、cost、security、rollback可能性を同じ評価datasetで比較します。
