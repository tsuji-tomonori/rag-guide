# 7.9. Traceに基づく失敗分析

トレースは、一回の要求が各工程を通った記録です。
共通のトレースIDで、元の質問、変換後の質問、フィルター、取得候補、再順位付け結果、最終コンテキスト、回答、引用、利用者の反応を結び付けます。
IDの生成、親子関係、retry・fallback・rollback時の継承は8.4.1の相関ID契約を使います。工程別ログが存在しても、必須の親へjoinできない記録は診断可能なtraceとして数えません。

[RAGChecker](https://arxiv.org/abs/2408.08067)は検索と生成を細かい指標に分け、主張単位でRAGの失敗を診断します。
必要な根拠を検索できなかった場合と、根拠を取得したのに生成時に無視した場合では、修正する構成要素が異なります。

失敗をデータ、検索、検索後処理、生成、方針、システムへ分類します。
各候補を除外した理由と構成要素の版も残し、原因に対応する改善作業を登録します。

## 7.9.1. layerごとの最初の失敗を特定する

同じ誤答でも、根拠がコーパスにない、検索器が落とした、検索後処理で消した、生成器が無視した、方針が遮断した、システムがタイムアウトした、という異なる原因があります。
質問から利用者の反応までをトレースIDで結び、期待動作から最初に外れた工程を分類します。

[RAGChecker](https://arxiv.org/abs/2408.08067)の主張単位の診断を使うと、コンテキストに根拠があったかと、回答がその根拠を使ったかを分けられます。
各失敗分類に担当者、重大度、再現事例をひも付けます。

印象だけで障害原因を決めず、中間成果物と設定の版を証拠にします。
一つの事例に複数原因がある場合も、最初の原因と後続の防御失敗を区別して記録します。

query理解、retrieval、rerank、context packing、generation、citationの各段階について、入力と出力を保存します。後段で観測した誤りだけを修正せず、最初に期待から外れた段階を原因候補とします。

## 7.9.2. 本番feedbackをdatasetと改善施策へ戻す

本番の低評価トレースや障害を、その場限りの調査で終わらせません。
再現する質問、利用者属性、コーパスのスナップショット、期待動作、禁止動作を固定した試験事例へ変換します。

個人情報や機密を除去しながら、失敗の原因となる条件を保持します。
元の事例を保存できない場合は、同じ原因を再現する最小の合成事例を作ります。

修正後も回帰評価項目群へ残し、同種の失敗を再び公開しないようにします。
発生頻度、重大度、業務影響で改善作業を並べ、事例の集積から構成要素ごとの改善仮説を立てます。
この循環によって、本番で得た知見を次の公開判定へ反映できます。

利用者feedbackをそのまま正解labelにせず、質問、権限、基準時点、期待根拠、失敗分類をreviewします。再現できた事例だけをregression datasetへ追加し、修正後も削除しません。

failure taxonomyへ、発生件数、risk、影響利用者、再現率、修正候補、ownerを付けます。改善後は同じtrace比較で、原因箇所が直り、別layerへ失敗が移っていないことを確認します。
