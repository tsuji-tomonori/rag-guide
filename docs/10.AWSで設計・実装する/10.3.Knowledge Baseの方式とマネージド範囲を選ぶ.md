# Knowledge Baseの方式とマネージド範囲を選ぶ

最初に決めるのは、Vector Storeの製品名ではなく、取り込み、保存、索引、検索基盤をどこまでAWSへ任せるかです。Bedrock Knowledge Basesには、基盤をAWSが隠蔽して管理するManaged Knowledge Baseと、利用者がEmbedding ModelとVector Storeを選ぶCustomer-managed Knowledge Baseがあります。同じKnowledge Baseという名称でも、作るリソース、設定構造、利用API、責任分界が異なります。

| 比較項目 | Managed Knowledge Base | Customer-managed Knowledge Base |
|---|---|---|
| 取り込み | AWSが管理 | Knowledge Basesが実行し、利用者がData Sourceと設定を管理 |
| 保存・索引・検索基盤 | AWSが内部で管理し、自動拡張 | 利用者が対応Vector Storeを作成・選択 |
| Embedding | 既定はservice-managed。条件内で独自Bedrock Modelを選択可能 | 利用者がBedrock Embedding Model、次元、Vector Typeを選択 |
| Reranking | 既定はservice-managed。構成により独自Modelまたは無効化 | 利用者がBedrock Rerank Model、候補数、返却数を選択 |
| 検索設定 | `managedSearchConfiguration` | `vectorSearchConfiguration` |
| 検索方式 | Hybridをサービス側で実行 | Storeの能力に応じてSemanticまたはHybrid |
| 検索API | `Retrieve`、`AgenticRetrieveStream` | `Retrieve` |
| 検索・生成一体API | `RetrieveAndGenerate`は利用しない | `RetrieveAndGenerate`、`RetrieveAndGenerateStream` |
| Agentic retrieval | 対応 | 非対応 |
| Vector Storeの直接操作 | できない | StoreのAPIを直接使う別経路を設計可能 |
| AgentCore GatewayのNative KB target | 対応 | 非対応。別のTool接続を設計 |
| 主な設計意図 | 基盤運用を減らしAWS標準へ寄せる | 検索方式、Schema、費用特性を選ぶ |

## Bedrock Managed Knowledge Base

**1. RAGでの目的**

文書取り込みからHybrid Retrievalまでの検索基盤をAWSへ広く任せ、Vector Storeの構築・容量計画・索引運用を利用者の管理対象から外します。複雑な質問ではagentic retrievalにより質問分解と反復検索も選べます。

**2. 四工程・二層の位置**

Batch Layerの文書側検索前処理として取り込み、解析、Chunking、Embedding、保存、索引作成を担います。Real-time Layerでは質問側検索前処理と検索を担い、service-managed Rerankingを使う場合は検索後処理の一部まで担います。`AgenticRetrieveStream`で回答生成も許可した場合だけ生成にもまたがります。

**3. AWSリソース**

Managed Knowledge Base、Data Source、Knowledge Base service role、任意のKMS Key、任意のcustom Embedding Model、custom Rerank Model、Resource Policyを使います。内部のStorageとIndexはAWSが管理し、利用者はVector Storeを作成しません。

**4. 接続先**

S3、SharePoint、Confluenceなどの対応Data Sourceを接続します。Real-time Layerから`Retrieve`または`AgenticRetrieveStream`を呼びます。AgentCore GatewayのNative Knowledge Base targetとして公開する場合もManaged Knowledge Baseを接続します。生成を分離する場合は取得結果をアプリケーションでEvidence Setへ整形し、Bedrock `Converse`または`ConverseStream`へ渡します。

**5. AWSが管理する範囲**

AWSは取り込み、内部Storage、Indexing、検索インフラの拡張、既定のservice-managed Embedding、service-managed Reranking、Hybrid Retrievalを管理します。基盤を管理することは、利用者の文書が正しいこと、Metadataが十分なこと、取得結果が質問を満たすことを保証するものではありません。

**6. 利用者が選択する項目**

Data Source、対象範囲、Parserと利用可能なChunking、同期時期、KMS Key、Resource Policy、ACL awareness、`managedSearchConfiguration`の`numberOfResults`、Metadata `filter`、Reranking方式を選びます。Embeddingは既定のservice-managedをBaselineにでき、必要な場合だけcustom Bedrock Embedding Modelを作成時に選びます。custom Embeddingは現行仕様でfloat32・1024次元が必要です。Agentic retrievalではFoundation Model、Reranking方式、最大反復数、応答を生成するかを選びます。

**7. 評価する項目**

取り込み成功率、更新反映時間、Recall@k、Metadata Filterの漏れと過剰除外、Reranking前後のnDCG・MRR、ACLテスト、agentic retrievalの質問分解妥当性、反復回数、十分性判定、Latency、1質問当たり費用を第7章で評価します。`numberOfResults`や最大反復数はBaselineであり、絶対値ではありません。

**8. 制約**

内部Data Storeへ直接アクセスできず、検索方式はHybridです。`vectorSearchConfiguration`ではなく`managedSearchConfiguration`を使います。Embedding方式は作成後に変更できず、変更時は新しいKnowledge Baseが必要です。custom Embeddingを選ぶとservice-managed Rerankingは使えず、custom Rerankerまたは無効化を選びます。`RetrieveAndGenerate`と`RetrieveAndGenerateStream`は使わず、`Retrieve`またはManaged専用の`AgenticRetrieveStream`を使います。agentic retrievalは最大5 retrieverで、GuardrailのMASKは対応せずBLOCKを使用します。Document ACL awarenessは認証機能ではなく、アプリケーションが検証済み`userContext`を渡す必要があります。

**9. 他の選択肢との使い分け**

Vector Store運用を減らし、AWS標準のHybrid Retrievalとagentic retrievalへ寄せられるなら有力です。Keyword field、Analyzer、独自Hybrid、Store API、Index schemaを細かく制御するならCustomer-managed KB＋OpenSearch Serverlessを選びます。Semantic Search中心でMetadata制約内、検索頻度と費用特性がS3 Vectorsに合うならCustomer-managed KB＋S3 Vectorsを比較します。

**10. 個別実装が必要になる条件**

独自Query rewriting、複数Indexの独自Fusion、RRF、業務固有の重複排除・MMR、Evidence Set、厳密なContext Packing、Claim-level Verificationが必要なら、`Retrieve`で結果を分離し、Real-time Layerのアプリケーションに処理を置きます。

Managed Knowledge Baseの検索設定は[`ManagedSearchConfiguration`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_ManagedSearchConfiguration.html)、API差分は[`RetrieveAndGenerate`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_RetrieveAndGenerate.html)と[agentic retrieval](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-agentic-retrieve.html)、ACLの責任は[ACL awareness](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-retrieve-acl.html)を参照します（確認日：2026年8月22日）。

```text
Data Sources
    │
    ▼
Managed Knowledge Base ───────────────── AWS管理境界 ────────────────┐
│ Parser / Chunking                                                   │
│ Service-managed Embedding → Storage → Index                        │
│ Hybrid Retrieval → Service-managed Reranking                       │
└─────────────────────────────────────────────────────────────────────┘
    │ Retrieve / AgenticRetrieveStream
    ▼
Application / AgentCore ── Evidence Set ── Bedrock Generation Model
```

**図10-2 Managed Knowledge Baseの責任分界**

### RetrieveとAgenticRetrieveStreamを分ける

`Retrieve`は1回の検索境界を明確にし、検索候補だけを返します。検索と生成を別々に評価し、独自のEvidence Setを作る場合に向きます。

`AgenticRetrieveStream`はFoundation Modelが質問を分解し、複数回検索し、情報の十分性を判断します。既定では引用付き応答も生成できますが、`generateResponse`を無効にして検索結果だけを受け取り、生成工程をアプリケーション側へ分離することもできます。これは`RetrieveAndGenerate`とは異なるManaged Knowledge Base専用APIです。分解と反復が必要な質問に限定し、単純質問を含む評価データでLatencyと費用の増加も比較します。

## Customer-managed Knowledge Base

**1. RAGでの目的**

Knowledge Basesによる取り込み、Chunkと出典の対応、共通検索APIを利用しつつ、Embedding ModelとVector Storeの能力・費用・運用範囲を利用者が選びます。

**2. 四工程・二層の位置**

Batch LayerではData Sourceの同期、解析、Chunking、Embedding、選択したStoreへの索引作成を担います。Real-time LayerではQuery Embedding、SemanticまたはHybrid Retrieval、Metadata Filter、任意のRerankingを担います。`RetrieveAndGenerate`を選ぶ場合は生成まで一体化します。

**3. AWSリソース**

Customer-managed Knowledge Base、Data Source、Knowledge Base service role、Bedrock Embedding Model、S3 VectorsのVector Bucket・Vector Index、またはOpenSearch ServerlessのCollection・Indexを使います。必要に応じてRerank Model、Generation Model、Guardrail、KMS Keyも接続します。

**4. 接続先**

Data Sourceから取り込んだ文書を、選択したEmbedding ModelでVector化し、Vector Storeへ保存します。Real-time Layerから`Retrieve`、`RetrieveAndGenerate`、`RetrieveAndGenerateStream`を呼びます。独自制御が必要ならStoreを直接検索し、`Converse`へ接続する経路を別に設けます。

**5. AWSが管理する範囲**

Knowledge BasesはIngestion Job、選択したParser・Chunkingの実行、Embedding Modelの呼び出し、Chunkと出典の関連づけ、Storeへの書き込み、検索APIを管理します。S3 VectorsやOpenSearch Serverlessは各サービスの範囲でStorage、検索処理、拡張を管理します。

**6. 利用者が選択する項目**

Embedding Model、Dimension、Vector Type、Vector Store、Index schema、Vector・Text・Metadata field、Distance Metric、Parser、Chunking、Metadata schema、IAM service roleを選びます。検索時は`vectorSearchConfiguration`の`numberOfResults`、`filter`、`implicitFilterConfiguration`、`overrideSearchType`、Rerankingを選びます。`RetrieveAndGenerate`ではGeneration Model、Prompt Template、推論Parameter、Guardrailも選びます。

**7. 評価する項目**

Embeddingの言語・Domain適合、Recall@k、Keyword・Vector・Hybridの差、Filter精度、Reranking効果、Index容量、同期時間、P95 Latency、Throttling、OCUまたはS3 Vectorsの費用要因、回答忠実性、引用正確性を評価します。

**8. 制約**

Model、Dimension、Vector TypeとStore schemaを一致させる必要があります。Embedding ModelやDimensionの変更は全Chunkの再Embeddingと新Indexを伴います。Knowledge Base作成後に一部のChunking設定は変更できないため、新Data Sourceまたは新索引を前提にします。`HYBRID`の上書きは、filterable text fieldを持つOpenSearch Serverlessなど対応Storeに限られ、それ以外は`SEMANTIC`です。Store固有のMetadata上限、Vector Type、Region、Quotaにも従います。

**9. 他の選択肢との使い分け**

Semantic Search中心で低運用、Metadata制約内ならS3 Vectorsを比較します。Keyword、Vector、Hybrid、柔軟なFilter、Analyzer、検索分析が必要ならOpenSearch Serverlessを比較します。Storeや検索Pipelineを完全に制御する必要がなく、基盤運用をさらに減らせるならManaged Knowledge Baseを比較します。

**10. 個別実装が必要になる条件**

独自の複数Retriever、Knowledge Basesが対応しないStore、独自Chunk schema、複雑な業務ACL、Score正規化、独自RRF、Evidence Setが必要なら、Knowledge Basesを検索境界までに限定するか、使わない構成にします。

Customer-managed Knowledge Baseの設定は[`KnowledgeBaseVectorSearchConfiguration`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_KnowledgeBaseVectorSearchConfiguration.html)、対応StoreとVector Typeは[Knowledge Base用Vector Storeの前提条件](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-setup.html)、検索動作は[Knowledge Baseからの情報取得](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-retrieve.html)を参照します（確認日：2026年8月22日）。

## Knowledge Basesを使わない構成

次の条件では、Knowledge Basesを使わず、アプリケーションがS3 VectorsまたはOpenSearch APIを直接呼ぶ構成を比較します。AWS実行基盤は提供されますが、Pipelineの処理ロジックと責任は利用者が持ちます。

- 複数Indexや複数Retrieverを検索し、独自RRFまたは重み付きFusionを必須にする
- Knowledge Basesが対応しない検索基盤またはIndex schemaを使う
- Chunk ID、Parent-child、表、節、権限を含む独自Schemaを完全に制御する
- Evidence Setの採否理由を検索候補単位で必ず記録する
- 検索前後の複雑な業務ACLと文書信頼度規則を適用する
- 検索、圧縮、Packing、生成、Claim検証のすべてを個別にTraceする

これはAWSを使わない構成ではありません。S3、S3 Vectors、OpenSearch Serverless、Bedrock Model、Lambda、ECS、EKS、AgentCore Runtimeを部品として利用し、結合ロジックを利用者が実装する構成です。
