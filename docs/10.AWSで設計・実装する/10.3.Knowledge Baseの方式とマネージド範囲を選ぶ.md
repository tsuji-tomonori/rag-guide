# Knowledge Baseの方式とマネージド範囲を選ぶ

最初に決めるのは、ベクトルストアの製品名ではなく、取り込み、保存、索引、検索基盤をどこまでAWSへ任せるかです。
Bedrock Knowledge Basesには、基盤をAWSが隠蔽して管理するManaged Knowledge Baseと、利用者が埋め込みモデルとベクトルストアを選ぶCustomer-managed Knowledge Baseがあります。
同じKnowledge Baseという名称でも、作るリソース、設定構造、利用API、責任分界が異なります。
**表10-3 Managed Knowledge BaseとCustomer-managed Knowledge Baseの比較**

| 比較項目 | Managed Knowledge Base | Customer-managed Knowledge Base |
|---|---|---|
| 取り込み | AWSが管理 | Knowledge Basesが実行し、利用者がデータソースと設定を管理 |
| 保存・索引・検索基盤 | AWSが内部で管理し、自動拡張 | 利用者が対応ベクトルストアを作成・選択 |
| 埋め込み | 既定はAWSが管理する方式。条件内で独自Bedrock モデルを選択可能 | 利用者がBedrock 埋め込みモデル、次元、ベクトル型を選択 |
| 再順位付け | 既定はAWSが管理する方式。構成により独自モデルまたは無効化 | 利用者がBedrock 再順位付けモデル、候補数、返却数を選択 |
| 検索設定 | `managedSearchConfiguration` | `vectorSearchConfiguration` |
| 検索方式 | ハイブリッドをサービス側で実行 | ストアの能力に応じて意味に基づくまたはハイブリッド |
| 検索API | `Retrieve`、`AgenticRetrieveStream` | `Retrieve` |
| 検索・生成一体API | `RetrieveAndGenerate`は利用しない | `RetrieveAndGenerate`、`RetrieveAndGenerateStream` |
| Agentic retrieval | 対応 | 非対応 |
| ベクトルストアの直接操作 | できない | ストアのAPIを直接使う別経路を設計可能 |
| AgentCore GatewayのNative KB target | 対応 | 非対応。別のツール接続を設計 |
| 主な設計意図 | 基盤運用を減らしAWS標準へ寄せる | 検索方式、スキーマ、費用特性を選ぶ |


AWS公式の[Managed Knowledge Baseの概要](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-build-managed.html)、[Managed Knowledge Baseの作成時選択](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-create.html)、[Customer-managed Knowledge Baseの作成](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-create.html)を根拠とします（確認日：2026年9月5日）。

## Bedrock Managed Knowledge Base

### 1. RAGでの目的

文書取り込みからハイブリッド検索までの検索基盤をAWSへ広く任せ、ベクトルストアの構築・容量計画・索引運用を利用者の管理対象から外します。
複雑な質問ではエージェント型検索により質問分解と反復検索も選べます。

### 2. 四工程・二層の位置

Batch Layerの文書側検索前処理として取り込み、解析、チャンク分割、埋め込み、保存、索引作成を担います。
Real-time Layerでは質問側検索前処理と検索を担い、AWS管理の再順位付けを使う場合は検索後処理の一部まで担います。
`AgenticRetrieveStream`で回答生成も許可した場合だけ生成にもまたがります。

### 3. AWSリソース

Managed Knowledge Base、データソース、Knowledge Base サービスロール、任意のKMS キー、任意の独自埋め込みモデル、独自再順位付けモデル、リソースポリシーを使います。
内部の保存容量とインデックスはAWSが管理し、利用者はベクトルストアを作成しません。

### 4. 接続先

S3、SharePoint、Confluenceなどの対応データソースを接続します。
Real-time Layerから`Retrieve`または`AgenticRetrieveStream`を呼びます。
AgentCore GatewayのNative Knowledge Base targetとして公開する場合もManaged Knowledge Baseを接続します。
生成を分離する場合は取得結果をアプリケーションで根拠集合へ整形し、Bedrock `Converse`または`ConverseStream`へ渡します。

### 5. AWSが管理する範囲

AWSは取り込み、内部ストレージ、索引の作成、検索インフラの拡張、既定のAWS管理の埋め込み、AWS管理の再順位付け、ハイブリッド検索を管理します。
文書の正しさ、メタデータの十分性、取得結果の有用性は、利用者が対象データで評価します。

### 6. 利用者が選択する項目

データソース、対象範囲、解析器と利用可能なチャンク分割、同期時期、KMS キー、リソースポリシー、ACL対応検索、`managedSearchConfiguration`の`numberOfResults`、メタデータ `filter`、再順位付け方式を選びます。
埋め込みは既定のAWSが管理する方式を基準構成にでき、必要な場合だけ独自 Bedrock 埋め込みモデルを作成時に選びます。
独自埋め込みは現行仕様でfloat32・1024次元が必要です。
Agentic retrievalでは基盤モデル、再順位付け方式、最大反復数、応答を生成するかを選びます。

### 7. 評価する項目

取り込み成功率、更新反映時間、Recall@k、メタデータフィルターの漏れと過剰除外、再順位付け前後のnDCG・MRR、ACLテスト、エージェント型検索の質問分解妥当性、反復回数、十分性判定、応答時間、1質問当たり費用を第7章で評価します。
`numberOfResults`や最大反復数は、基準構成から比較評価によって調整します。

### 8. 制約

内部データストアへ直接アクセスできず、検索方式はハイブリッドです。
`vectorSearchConfiguration`ではなく`managedSearchConfiguration`を使います。
埋め込み方式は作成後に変更できず、変更時は新しいKnowledge Baseが必要です。
独自埋め込みを選ぶとAWS管理の再順位付けは使えず、独自再順位付け器または無効化を選びます。
`RetrieveAndGenerate`と`RetrieveAndGenerateStream`は使わず、`Retrieve`またはManaged専用の`AgenticRetrieveStream`を使います。
エージェント型検索は最大5 retrieverで、GuardrailのMASKは対応せずBLOCKを使用します。
文書ACL awarenessは認証機能ではなく、アプリケーションが検証済み`userContext`を渡す必要があります。

### 9. 他の選択肢との使い分け

ベクトルストア運用を減らし、AWS標準のハイブリッド検索とエージェント型検索へ寄せられるなら有力です。
キーワード項目、解析器、独自ハイブリッド、ストア API、インデックスのスキーマを細かく制御するならCustomer-managed KB＋OpenSearch Serverlessを選びます。
意味検索中心でメタデータ制約内、検索頻度と費用特性がS3 Vectorsに合うならCustomer-managed KB＋S3 Vectorsを比較します。

### 10. 個別実装が必要になる条件

独自質問の書き換え、複数インデックスの独自統合、RRF、業務固有の重複排除・MMR、根拠集合、厳密なコンテキスト入力への配置、主張単位の検証が必要なら、`Retrieve`で結果を分離し、Real-time Layerのアプリケーションに処理を置きます。

Managed Knowledge Baseの検索設定は[`ManagedSearchConfiguration`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_ManagedSearchConfiguration.html)、API差分は[`RetrieveAndGenerate`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_RetrieveAndGenerate.html)と[agentic retrieval](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-agentic-retrieve.html)、ACLの責任は[ACL awareness](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-retrieve-acl.html)を参照します（確認日：2026年9月5日）。

```text
Data Sources
    │
    ▼
Managed Knowledge Base ───────────────── AWS管理境界 ────────────────┐
│ Parser / Chunking                                                   │
│ Service-managed Embedding → Storage → Index                        │
│ Hybrid Retrieval → Service-managed Reranking                       │
└─────────────────────────────────────────────────────────────────────┘
    │ Retrieve / AgenticRetrieveStream
    ▼
Application / AgentCore ── Evidence Set ── Bedrock Generation Model
```

**図10-2 Managed Knowledge Baseの責任分界**

### RetrieveとAgenticRetrieveStreamを分ける

`Retrieve`は1回の検索境界を明確にし、検索候補だけを返します。
検索と生成を別々に評価し、独自の根拠集合を作る場合に向きます。

`AgenticRetrieveStream`は基盤モデルが質問を分解し、複数回検索し、情報の十分性を判断します。
既定では引用付き応答も生成できますが、`generateResponse`を無効にして検索結果だけを受け取り、生成工程をアプリケーション側へ分離することもできます。
これは`RetrieveAndGenerate`とは異なるManaged Knowledge Base専用APIです。
分解と反復が必要な質問に限定し、単純質問を含む評価データで応答時間と費用の増加も比較します。

## Customer-managed Knowledge Base

### 1. RAGでの目的

Knowledge Basesによる取り込み、チャンクと出典の対応、共通検索APIを利用しつつ、埋め込みモデルとベクトルストアの能力・費用・運用範囲を利用者が選びます。

### 2. 四工程・二層の位置

Batch Layerではデータソースの同期、解析、チャンク分割、埋め込み、選択したストアへの索引作成を担います。
Real-time Layerでは質問の埋め込み、意味に基づくまたはハイブリッド検索、メタデータフィルター、任意の再順位付けを担います。
`RetrieveAndGenerate`を選ぶ場合は生成まで一体化します。

### 3. AWSリソース

Customer-managed Knowledge Base、データソース、Knowledge Base サービスロール、Bedrock 埋め込みモデル、S3 Vectorsのベクトルバケット・ベクトルインデックス、またはOpenSearch Serverlessのコレクション・インデックスを使います。
必要に応じて再順位付けモデル、生成モデル、Guardrail、KMS キーも接続します。

### 4. 接続先

データソースから取り込んだ文書を、選択した埋め込みモデルでベクトル化し、ベクトルストアへ保存します。
Real-time Layerから`Retrieve`、`RetrieveAndGenerate`、`RetrieveAndGenerateStream`を呼びます。
独自制御が必要ならストアを直接検索し、`Converse`へ接続する経路を別に設けます。

### 5. AWSが管理する範囲

Knowledge Basesは取り込み Job、選択した解析器・チャンク分割の実行、埋め込みモデルの呼び出し、チャンクと出典の関連づけ、ストアへの書き込み、検索APIを管理します。
S3 VectorsやOpenSearch Serverlessは各サービスの範囲で保存容量、検索処理、拡張を管理します。

### 6. 利用者が選択する項目

埋め込みモデル、次元数、ベクトル型、ベクトルストア、インデックスのスキーマ、ベクトル・テキスト・メタデータ項目、距離指標、解析器、チャンク分割、メタデータのスキーマ、IAMサービスロールを選びます。
検索時は`vectorSearchConfiguration`の`numberOfResults`、`filter`、`implicitFilterConfiguration`、`overrideSearchType`、再順位付けを選びます。
`RetrieveAndGenerate`では生成モデル、プロンプトテンプレート、推論パラメーター、Guardrailも選びます。

### 7. 評価する項目

埋め込みの言語・分野適合、Recall@k、キーワード・ベクトル・ハイブリッドの差、フィルター精度、再順位付け効果、インデックス容量、同期時間、P95 応答時間、Throttling、OCUまたはS3 Vectorsの費用要因、回答忠実性、引用正確性を評価します。

### 8. 制約

モデル、次元数、ベクトル型とストアスキーマを一致させる必要があります。
埋め込みモデルや次元数の変更は全チャンクの再埋め込みと新インデックスを伴います。
Knowledge Base作成後に一部のチャンク分割設定は変更できないため、新データソースまたは新索引を前提にします。
`HYBRID`の上書きは、フィルターに使えるテキスト項目を持つOpenSearch Serverlessなど対応ストアに限られ、それ以外は`SEMANTIC`です。
ストア固有のメタデータ上限、ベクトル型、リージョン、クォータにも従います。

### 9. 他の選択肢との使い分け

意味検索中心で低運用、メタデータ制約内ならS3 Vectorsを比較します。
キーワード、ベクトル、ハイブリッド、柔軟なフィルター、解析器、検索分析が必要ならOpenSearch Serverlessを比較します。
ストアや検索処理の流れを完全に制御する必要がなく、基盤運用をさらに減らせるならManaged Knowledge Baseを比較します。

### 10. 個別実装が必要になる条件

独自の複数検索器、Knowledge Basesが対応しないストア、独自チャンクスキーマ、複雑な業務ACL、スコア正規化、独自RRF、根拠集合が必要なら、Knowledge Basesを検索境界までに限定するか、使わない構成にします。

Customer-managed Knowledge Baseの設定は[`KnowledgeBaseVectorSearchConfiguration`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_KnowledgeBaseVectorSearchConfiguration.html)、対応ストアとベクトル型は[Knowledge Base用Vector Storeの前提条件](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-setup.html)、検索動作は[Knowledge Baseからの情報取得](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-retrieve.html)を参照します（確認日：2026年9月5日）。

## Knowledge Basesを使わない構成

次の条件では、Knowledge Basesを使わず、アプリケーションがS3 VectorsまたはOpenSearch APIを直接呼ぶ構成を比較します。
AWS実行基盤は提供されますが、処理の流れの処理ロジックと責任は利用者が持ちます。

- 複数インデックスや複数検索器を検索し、独自RRFまたは重み付き統合を必須にする
- Knowledge Basesが対応しない検索基盤またはインデックスのスキーマを使う
- チャンク ID、親チャンク-child、表、節、権限を含む独自スキーマを完全に制御する
- 根拠集合の採否理由を検索候補単位で必ず記録する
- 検索前後の複雑な業務ACLと文書信頼度規則を適用する
- 検索、圧縮、入力への配置、生成、主張検証のすべてを個別にトレースする

これはAWSを使わない構成ではありません。
S3、S3 Vectors、OpenSearch Serverless、Bedrock モデル、Lambda、ECS、EKS、AgentCore Runtimeを部品として利用し、結合ロジックを利用者が実装する構成です。
