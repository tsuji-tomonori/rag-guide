# Real-time Layerの検索を構成する

Real-time Layerでは、認証済みの利用者コンテキストと質問から検索文・フィルターを作り、根拠候補だけを取得します。
第4章のSparse、Dense、ハイブリッド、メタデータフィルターをAWSのAPIと設定へ対応づけます。
検索と生成を分けて測れるよう、まず`Retrieve`の出力で検索評価を行います。

```text
利用者 → 認証 → Application
                    │ 原質問・会話・検証済みUser Context
                    ▼
              質問理解 / Query・Filter作成
                    │
                    ▼
       Retrieve / QueryVectors / OpenSearch Query
                    │
                    ▼
          候補 + Location + Metadata + Score
                    │
                    ▼
              Rerank / Evidence Set
                    │
                    ▼
        Converse / RetrieveAndGenerate → 回答・引用
```

## APIを選ぶ

### 1. RAGでの目的

検索、検索後処理、生成のどこをAWSの一つのAPIへまとめ、どこをアプリケーション境界として分離するかを決めます。

### 2. 四工程・二層の位置

すべてReal-time Layerです。
`Retrieve`、`QueryVectors`、OpenSearch 検索文は検索、`RetrieveAndGenerate`は検索から生成、`Converse`は生成を担います。
`AgenticRetrieveStream`は質問側検索前処理、反復検索、任意の回答生成にまたがります。

### 3. AWSリソース

Bedrock Agent Runtimeのエンドポイント、ManagedまたはCustomer-managed Knowledge Base、S3 ベクトルインデックス、OpenSearch Serverless インデックス、Bedrock Runtimeのエンドポイント、生成モデルを使います。

### 4. 接続先

アプリケーションが認証・認可後に各APIを呼び、取得結果を検索後処理または生成へ渡します。
API GatewayやALBは外部からの通信を受け付ける境界を担います。
Knowledge Baseは、その内側で資料の検索を担います。

### 5. AWSが管理する範囲

AWSはAPI受付、選択リソースへの検索文実行、権限評価、サービス指標を管理します。
`RetrieveAndGenerate`ではKnowledge Base検索、プロンプトへの検索結果挿入、モデル呼び出し、引用と取得した参照資料の返却も行います。

### 6. 利用者が選択する項目

Knowledge Base方式、API、検索結果数、フィルター、検索方式、再順位付け器、生成モデル、プロンプト、セッション、ストリーミングの要否を選びます。
検索品質を工程別に評価・制御したい場合は`Retrieve`と`Converse`を分離します。

### 7. 評価する項目

API別のRecall@k、MRR、nDCG、引用情報の完全性、P50/P95 応答時間、ストリーミング開始時間、エラー、スロットリング、要求当たりの費用、トレース可能性を評価します。

### 8. 制約

Managed KBでは`Retrieve`または`AgenticRetrieveStream`を使います。
Customer-managed KBの`HYBRID`は対応ストアに限られます。
直接`QueryVectors`を使う場合、質問の埋め込みと原文出典位置復元を利用者が担当します。
OpenSearch直接検索文ではインデックスのスキーマと検索文 DSLも利用者責任です。

### 9. 他の選択肢との使い分け

検索だけ欲しい、根拠集合を作る、検索を独立評価するなら`Retrieve`。
Customer-managed KBで標準的な検索・生成・引用を一体化するなら`RetrieveAndGenerate`。
ストア機能を直接制御するなら`QueryVectors`またはOpenSearch 検索文。
生成モデルを共通APIで制御するなら`Converse`を選びます。

### 10. 個別実装が必要になる条件

複数APIの振り分け、独自質問の書き換え、複数検索器の統合、根拠集合、独自セッション契約、厳密な引用検証が必要なら、APIの間にアプリケーション処理を置きます。
**表10-8 APIの使い分け**

|---|---|---|

| `RetrieveAndGenerate` | 標準的な一体経路を使う |

| OpenSearch 検索文 API | 解析器、項目、検索パイプラインを制御する |

Customer-managed KBでは、OpenSearch Serverlessなどフィルターに使えるテキスト項目を持つ対応構成で`overrideSearchType`を`HYBRID`にできます。
S3 Vectors連携は`SEMANTIC`です。
OpenSearchを直接使えばキーワード、ベクトル、ハイブリッド検索文と検索パイプラインをより細かく制御できます。

## 検索設定を評価する

### `numberOfResults`とTop-k

`numberOfResults`は生成へ渡す件数ではなく、まず検索候補を何件取るかの設定として扱います。
少なすぎるとRecallを失い、多すぎると再順位付け、トークン、応答時間、費用を増やします。
複数のkを第7章で比較し、質問型別に必要件数を確認します。
Managed 検索とCustomer-managed Vector 検索では、それぞれに対応する設定構造を使います。

階層型チャンク分割では、複数の子チャンク候補が同じ親チャンクへ置換されるため、返却結果が指定件数を下回ることがあります。
件数不足と検索失敗を区別し、子チャンク単位のRecallと親チャンク返却後のコンテキスト量を評価します。

### 検索方式とスコア

`SEMANTIC`、`HYBRID`はアルゴリズムの優劣ではなく、質問・文書特性に対する比較対象です。
意味が同じ別表現はDenseが、型番・固有語・エラーコードはキーワードが強いという第4章の仮説を、実データで検証します。

検索スコアは候補の並べ替えと観測に使えますが、異なるストア、検索文方式、モデルのスコアを同じ尺度として直接比較しません。
合格しきい値を導入する場合は、正例・難しい負例を含む評価データから校正します。

### メタデータフィルターと利用者コンテキスト

メタデータフィルターは、`tenant`、`department`、`role`、`status`、`version`、`valid_from`、`valid_to`など、検索前に除外すべき条件へ使います。
利用者入力のテナントIDをそのままフィルターへ採用せず、認証済み識別情報の属性をアプリケーションで検証して構築します。

Customer-managed KBの`implicitFilterConfiguration`は、メタデータ属性の説明とモデルを使って自然言語からフィルターを補助的に生成する選択肢です。
明示フィルターと同じ権限境界として盲信せず、許可する項目・演算子を限定し、漏れ・過剰除外を評価します。
Managed KBのACL対応検索には、アプリケーションで認証・検証した`userContext`を渡します。

フィルターの演算子と対応ストアは[Knowledge Base retrieval configuration](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-config.html)、Managed KBの利用者コンテキストは[ACL awareness](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-retrieve-acl.html)を参照します（確認日：2026年9月5日）。

## 個別に実装する検索前処理・検索

以下の処理は、AWSのモデルと実行基盤を使って個別に実装します。
設計の考え方は、各項目で示す章を参照してください。

- **会話から独立した検索文への変換・質問の書き換え**：会話の省略、表記揺れ、略語、期間補完が検索Recallを下げる場合に必要。Real-time Layerの質問側検索前処理へ配置。Lambda、ECS、EKS、AgentCore RuntimeとBedrock モデルを利用可能。第4章の検索文理解と第9章の失敗分析を参照。
- **HyDE・Query2doc**：短い質問と文書表現の隔たりが大きい場合に比較。Real-time Layerの質問側検索前処理へ配置。Lambda、ECS、EKS、AgentCore RuntimeとBedrock モデルを利用可能。第4章のDense 検索を参照。
- **複数Knowledge Base・インデックスへの振り分け**：分野、テナント、機密区分ごとに検索先を分ける場合に必要。Real-time Layerの検索前処理から検索へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第4章と第8章を参照。
- **独自統合・RRF・スコア正規化**：複数検索器の順位をAWS標準と異なる規則で統合する場合に必要。Real-time Layerの検索工程へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第4章のハイブリッド検索と第9章を参照。
