# Real-time Layerの検索を構成する

Real-time Layerでは、認証済みの利用者Contextと質問から検索Query・Filterを作り、根拠候補だけを取得します。第4章のSparse、Dense、Hybrid、Metadata FilterをAWSのAPIと設定へ対応づけます。検索と生成を分けて測れるよう、まず`Retrieve`の出力でRetrieval評価を行います。

```text
利用者 → 認証 → Application
                    │ 原質問・会話・検証済みUser Context
                    ▼
              質問理解 / Query・Filter作成
                    │
                    ▼
       Retrieve / QueryVectors / OpenSearch Query
                    │
                    ▼
          候補 + Location + Metadata + Score
                    │
                    ▼
              Rerank / Evidence Set
                    │
                    ▼
        Converse / RetrieveAndGenerate → 回答・引用
```

**図10-7 Real-time Layerの検索・生成シーケンス**

## APIを選ぶ

**1. RAGでの目的**

検索、検索後処理、生成のどこをAWSの一つのAPIへまとめ、どこをアプリケーション境界として分離するかを決めます。

**2. 四工程・二層の位置**

すべてReal-time Layerです。`Retrieve`、`QueryVectors`、OpenSearch Queryは検索、`RetrieveAndGenerate`は検索から生成、`Converse`は生成を担います。`AgenticRetrieveStream`は質問側検索前処理、反復検索、任意の回答生成にまたがります。

**3. AWSリソース**

Bedrock Agent Runtime endpoint、ManagedまたはCustomer-managed Knowledge Base、S3 Vector Index、OpenSearch Serverless Index、Bedrock Runtime endpoint、Generation Modelを使います。

**4. 接続先**

アプリケーションが認証・認可後に各APIを呼び、取得結果を検索後処理または生成へ渡します。API GatewayやALBは外部境界であり、Knowledge Baseの代替ではありません。

**5. AWSが管理する範囲**

AWSはAPI受付、選択リソースへのQuery実行、権限評価、サービスMetricsを管理します。`RetrieveAndGenerate`ではKnowledge Base検索、Promptへの検索結果挿入、Model呼び出し、CitationとRetrieved Referenceの返却も行います。

**6. 利用者が選択する項目**

Knowledge Base方式、API、検索結果数、Filter、Search type、Reranker、Generation Model、Prompt、Session、Streamingの要否を選びます。検索品質を工程別に評価・制御したい場合は`Retrieve`と`Converse`を分離します。

**7. 評価する項目**

API別のRecall@k、MRR、nDCG、Citation情報の完全性、P50/P95 Latency、Streaming開始時間、Error、Throttle、Cost per request、Trace可能性を評価します。

**8. 制約**

Managed KBでは`RetrieveAndGenerate`を使いません。Customer-managed KBの`HYBRID`は対応Storeに限られます。直接`QueryVectors`を使う場合、Query Embeddingと原文Location復元を利用者が担当します。OpenSearch直接QueryではIndex schemaとQuery DSLも利用者責任です。

**9. 他の選択肢との使い分け**

検索だけ欲しい、Evidence Setを作る、検索を独立評価するなら`Retrieve`。Customer-managed KBで標準的な検索・生成・引用を一体化するなら`RetrieveAndGenerate`。Store機能を直接制御するなら`QueryVectors`またはOpenSearch Query。生成Modelを共通APIで制御するなら`Converse`を選びます。

**10. 個別実装が必要になる条件**

複数APIのRouting、独自Query rewriting、複数RetrieverのFusion、Evidence Set、独自Session契約、厳密なCitation検証が必要なら、APIの間にアプリケーション処理を置きます。

| API | 対象 | 担当する範囲 | 主な選択条件 |
|---|---|---|---|
| `Retrieve` | Managed / Customer-managed KB | 根拠候補、Location、Metadata、Scoreの取得 | 検索を分離評価し、独自の検索後処理・生成を行う |
| `AgenticRetrieveStream` | Managed KBのみ | 質問分解、反復検索、十分性判断、任意の引用付き応答 | 複雑な質問を複数回検索する |
| `RetrieveAndGenerate` | Customer-managed KB | 検索、任意のRerank、生成、Citation | 標準的な一体経路を使う |
| `RetrieveAndGenerateStream` | Customer-managed KB | 上記の生成をStreaming | 応答開始時間を短く見せる必要がある |
| `QueryVectors` | S3 Vectors | Query Vectorによる直接Semantic Search | KB外のIndex schemaや直接制御が必要 |
| OpenSearch Query API | OpenSearch Serverless | Keyword、Vector、Hybrid、Filterの直接Query | Analyzer、Field、Search Pipelineを制御する |
| `Converse` / `ConverseStream` | Bedrock生成モデル | Evidenceから回答を生成 | 検索後処理・Prompt・Modelを分離制御する |

**表10-8 APIの使い分け**

APIのRequest・Response境界は[`Retrieve`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_Retrieve.html)、[`AgenticRetrieveStream`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_AgenticRetrieveStream.html)、[`RetrieveAndGenerate`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_RetrieveAndGenerate.html)、[`QueryVectors`](https://docs.aws.amazon.com/AmazonS3/latest/API/API_S3VectorBuckets_QueryVectors.html)、[`Converse`](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html)を参照します（確認日：2026年8月22日）。

## Sparse・Dense・Hybridを対応づける

| 第3〜6章の技術 | AWS機能 | AWSが行うこと | 利用者が決めること | 個別実装が必要になる条件 |
|---|---|---|---|---|
| 文書解析 | KB Default/BDA/FM parser | 抽出処理を実行 | Parser、抽出要件 | 業務固有の正規化 |
| Fixed-size Chunking | KB Fixed-size | Token数とOverlapに従い分割 | `maxTokens`、`overlapPercentage` | 原則不要 |
| Semantic Chunking | KB Semantic | 意味境界を計算して分割 | Threshold、`maxTokens`、`bufferSize` | 原則不要 |
| Hierarchical Chunking | KB Hierarchical | Child検索、Parent返却 | Parent/Child/Overlap | 独自階層が必要 |
| Dense Embedding | Bedrock Embedding Model | Model hostingと推論 | Model、Dimension、Vector Type | 非対応Model・複数表現 |
| Vector Storage | S3 Vectors / OpenSearch | 保存、検索基盤、拡張 | Store、Index schema | 非対応Store |
| BM25 / Sparse | OpenSearch | Inverted IndexとKeyword検索 | Analyzer、Field、Query | 複数Indexの独自統合 |
| Dense Retrieval | KB / S3 Vectors / OpenSearch | Query Vectorの近傍検索 | Top-k、Filter、Store | 複数Embeddingの統合 |
| Hybrid Retrieval | Managed KB / KB＋OpenSearch / OpenSearch | KeywordとVectorを検索・統合 | Store、Search type、Pipeline | 独自RRF・重み付きFusion |

| Query decomposition | Managed KB Agentic Retrieval | 分解、反復検索、十分性判定 | Model、反復、生成の有無 | 独自分解・Routing |
| Reranking | Bedrock Rerank | 候補の関連度を再計算 | Model、候補数、返却数 | 業務規則とのScore統合 |
| Grounded Generation | RetrieveAndGenerate / Converse | Model hostingと生成 | Model、Prompt、推論Parameter | Evidence Setや検証を厳密化 |
| Citation | RetrieveAndGenerate / Agentic / Application | Source情報を返却 | 表示、粒度、正確性評価 | Claim単位の再検証 |

| Agent loop | AgentCore Runtime | Runtime、Isolation、Scaling | Agent logic、停止条件 | Agent logic自体は必要 |

**表10-9 第3〜6章のアルゴリズムとAWS機能・設定項目の対応**

Managed KBのHybridはサービス側の検索方式として使います。Customer-managed KBでは、OpenSearch Serverlessなどfilterable text fieldを持つ対応構成で`overrideSearchType`を`HYBRID`にできます。S3 Vectors連携は`SEMANTIC`です。OpenSearchを直接使えばKeyword、Vector、Hybrid QueryとSearch Pipelineをより細かく制御できます。

## 検索設定を評価する

### `numberOfResults`とTop-k

`numberOfResults`はGenerationへ渡す件数ではなく、まず検索候補を何件取るかの設定として扱います。少なすぎるとRecallを失い、多すぎるとReranking、Token、Latency、費用を増やします。複数のkを第7章で比較し、質問型別に必要件数を確認します。Managed SearchとCustomer-managed Vector Searchの設定構造は混同しません。

Hierarchical Chunkingでは、複数のChild候補が同じParentへ置換されるため、返却結果が指定件数を下回ることがあります。件数不足と検索失敗を区別し、Child単位のRecallとParent返却後のContext量を評価します。

### Search typeとScore

`SEMANTIC`、`HYBRID`はアルゴリズムの優劣ではなく、質問・文書特性に対する比較対象です。意味が同じ別表現はDenseが、型番・固有語・Error codeはKeywordが強いという第4章の仮説を、実データで検証します。

Retrieval Scoreは候補の並べ替えと観測に使えますが、異なるStore、Query方式、ModelのScoreを同じ尺度として直接比較しません。合格Thresholdを導入する場合は、正例・難しい負例を含む評価データから校正します。

### Metadata FilterとUser Context

Metadata Filterは、`tenant`、`department`、`role`、`status`、`version`、`valid_from`、`valid_to`など、検索前に除外すべき条件へ使います。利用者入力のtenant IDをそのままFilterへ採用せず、認証済みIdentityのClaimをアプリケーションで検証して構築します。

Customer-managed KBの`implicitFilterConfiguration`は、Metadata属性の説明とModelを使って自然言語からFilterを補助的に生成する選択肢です。明示Filterと同じ権限境界として盲信せず、許可するField・Operatorを限定し、漏れ・過剰除外を評価します。Managed KBのACL awarenessも認証の代替ではなく、検証済み`userContext`を渡します。

Filterの演算子と対応Storeは[Knowledge Base retrieval configuration](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-config.html)、Managed KBのUser Contextは[ACL awareness](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-retrieve-acl.html)を参照します（確認日：2026年8月22日）。

## AWS標準だけでは完結しない検索前処理・検索

以下は詳細実装を本章で扱いません。AWSのModelと実行基盤を使えますが、処理ロジックは利用者が作ります。

- **Standalone Query化・Query rewriting**：会話の省略、表記揺れ、略語、期間補完が検索Recallを下げる場合に必要。Real-time Layerの質問側検索前処理へ配置。Lambda、ECS、EKS、AgentCore RuntimeとBedrock Modelを利用可能。第4章のQuery理解と第9章の失敗分析を参照。
- **HyDE・Query2doc**：短い質問と文書表現の隔たりが大きい場合に比較。Real-time Layerの質問側検索前処理へ配置。Lambda、ECS、EKS、AgentCore RuntimeとBedrock Modelを利用可能。第4章のDense Retrievalを参照。
- **複数Knowledge Base・IndexへのRouting**：Domain、Tenant、機密区分ごとに検索先を分ける場合に必要。Real-time Layerの検索前処理から検索へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第4章と第8章を参照。
- **独自Fusion・RRF・Score正規化**：複数Retrieverの順位をAWS標準と異なる規則で統合する場合に必要。Real-time Layerの検索工程へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第4章のHybrid Retrievalと第9章を参照。
