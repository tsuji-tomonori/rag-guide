# Evidence Setを作り回答する

検索後処理は、取得候補をそのままModelへ渡す工程ではありません。候補を並べ直し、重複、版、信頼度、矛盾、Token予算を確認して、回答に使うEvidence Setへ変換します。その後、Evidenceに基づいて回答、引用、回答保留を作ります。

## 検索候補をEvidence Setへ変換する

![検索候補をRerankと業務規則でEvidence Setへ整える流れ](../../assets/images/v4/50-aws-evidence-shaping-flow.png)

**図10-8 検索候補からEvidence Setを作る流れ**

### Bedrock Rerankを使う

Bedrock Rerankは、質問と候補Textをまとめて評価し、関連度順を付け直します。単体`Rerank` API、Knowledge Baseの`Retrieve`、Customer-managed Knowledge Baseの`RetrieveAndGenerate`へ組み込めます。

利用者はModel、最初の候補数、Rerank後の返却数、Modelへ渡すMetadataを選びます。次を別々に評価します。

- 最初の候補数を増やしたとき、正解EvidenceのRecallが改善するか
- Rerank後の件数を減らしたとき、正解を残したままTokenを削減できるか
- nDCG、MRR、Precision、P95 Latency、費用が改善幅に見合うか

Rerankerは入力された候補だけを並べ替えます。検索で取得できなかった根拠を回復できません。最新版、公開状態、Source trustなどの決定的な規則もRerankerへ任せず、Filterまたは業務選別で扱います。[Bedrock Rerank](https://docs.aws.amazon.com/bedrock/latest/userguide/rerank.html)と[`Rerank` API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_Rerank.html)を参照します（確認日：2026年8月22日）。

### 業務規則とContextを整える

AWSのModelと実行基盤を利用できますが、次の処理ロジックは利用者が持ちます。

- **重複排除・Diversity**：同じ文書や観点だけでContextが埋まることを防ぐ
- **版・鮮度・信頼度の選別**：新旧の矛盾、公開前文書、非公式Sourceを処理する
- **Evidence Set**：採用・不採用理由、矛盾、回答可能性、Citation IDを記録する
- **Context Compression**：根拠を失わず、不要部分とTokenを減らす
- **Context Packing**：文書の順序、文書当たり上限、Token配分を決める

Evidence Setには、少なくとも本文、Source、Location、文書版、Retriever、Score、採否理由、Citation IDを含めます。検索結果の全件ではなく、回答へ使う根拠と使わない理由を再現できる状態を成果物にします。

## 生成経路を選ぶ

![RetrieveAndGenerateとRetrieveからEvidence Setを経てConverseへ渡す経路を比較した図](../../assets/images/v4/51-aws-generation-control-paths.png)

**図10-9 標準生成経路と分離生成経路**

### 標準経路：RetrieveAndGenerate

Customer-managed Knowledge Baseで、検索、任意のRerank、Promptへの結果挿入、Generation Model呼び出し、Citation返却を一体化します。構成を短くし、End-to-end評価を始めやすい経路です。

ただし、API内部のContext構築が中心になるため、候補の採否理由、矛盾、回答可能性を独自Schemaで残す要件には向きません。Managed Knowledge Baseでは使いません。

### 分離経路：Retrieve＋Evidence Set＋Converse

Managed / Customer-managed Knowledge Baseで候補を取得し、アプリケーションがEvidence Setを作って`Converse`へ渡します。Prompt、Model、会話、Citation ID、回答保留、Claim検証を工程別に制御できます。

分離するほど実装は増えますが、検索、Rerank、Evidence、生成を別々に評価できます。監査、複数Retriever、厳密な引用、業務固有の保留が必要なら、この経路を比較します。

どちらの経路でも、Citationが存在するだけで正しい回答とは判定しません。主要ClaimをCitationが本当に支持するかを第7章で評価します。[RetrieveAndGenerateのResponse](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_RetrieveAndGenerate.html)と[Conversation inference](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html)を参照します（確認日：2026年8月22日）。

## ModelとPromptを固定する

利用者はModel / Inference Profile、Prompt Version、System instruction、Temperature、Top-p、Max tokens、Stop sequence、回答形式を選びます。Knowledge BasesのCustom Promptでは検索結果を渡す`$search_results$`を含め、Citationを返す構成では`$output_format_instructions$`を維持します。

Modelを大きくする前に、検索とEvidenceの不足を切り分けます。Model、Prompt、Inference Parameterを変えると回答分布が変わるため、Faithfulness、Correctness、Completeness、Citation precision / coverage、形式適合、Latency、Token、Cost per answerを回帰評価します。[Model API compatibility](https://docs.aws.amazon.com/bedrock/latest/userguide/models-api-compatibility.html)、[Retrieve and generate configuration](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-config.html)、[Model lifecycle](https://docs.aws.amazon.com/bedrock/latest/userguide/model-lifecycle.html)を参照します（確認日：2026年8月22日）。

## SessionとStreamingを境界に使わない

`RetrieveAndGenerate`のSession IDは会話継続に使いますが、Authorization境界には使いません。各Requestで利用者を認証・認可し、アプリケーションのUser・Conversation・AWS Sessionを対応づけます。

Streamingは最初の表示を早めますが、総処理時間やToken費用を必ず減らすわけではありません。途中結果を業務処理へ使わず、回答とCitationが確定した状態をUIで区別します。

## Guardrailsの役割を限定する

Bedrock Guardrailsは、入力と生成結果へ有害Content、Denied topic、Sensitive informationなどのPolicyを適用します。Productionでは評価済み数値Versionを記録し、危険入力の検出率、正常質問の誤Block率、PII Maskの漏れ、Latency、費用を評価します。

Guardrailsは、Knowledge Basesが取得したReference本文そのもの、Document ACL、Sourceの正しさ、Citation correctnessを保証しません。文書の公開状態とACLはData Source・Metadata Filter、根拠性はEvidence・Citation評価、Tool認可はIAM・AgentCore Policyで扱います。[Guardrailsの仕組み](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-how.html)と[Knowledge Base retrieval configuration](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-config.html)を参照します（確認日：2026年8月22日）。

## 回答保留を設計する

回答保留はModelの気分に任せません。少なくとも次のSignalを評価します。

- 必須Filter適用後に候補がない
- 正解を支えるEvidenceが基準を満たさない
- Evidenceが矛盾し、版・信頼度規則で解消できない
- Citationが主要Claimを支えない
- Guardrailが入力または出力をBlockした
- 権限外操作、人の承認、高リスク判断が必要である

閾値は、答えるべき質問と答えるべきでない質問を含む評価データで校正します。誤回答だけでなく、答えられる質問を過剰に保留する率も確認します。Claim-level Verification、Citation再検証、Human reviewへのEscalationが必要なら、生成前後にアプリケーション処理を追加します。
