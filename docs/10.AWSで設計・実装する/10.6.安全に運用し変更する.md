# 安全に運用し変更する

IAM、KMS、監視、評価、版管理、コスト管理は、検索とは別の第三Layerではありません。Batch Layerの取り込みからReal-time Layerの回答まで、同じRequestと版を追跡する横断的な管理面です。

![認可、暗号化、監視、評価、版管理、コスト管理を全工程へ通す図](../../assets/images/v4/53-aws-crosscutting-controls.png)

**図10-11 全工程を横断する管理面**

## 認可を四つの境界へ分ける

一つのIAM Roleだけで全経路を許可しません。役割ごとに境界を分けます。

1. **AWS APIの認可**：Application role、Knowledge Base service role、AgentCore Runtime / Gateway roleを分け、必要なActionとResourceだけを許可します。
2. **検索基盤のData plane**：OpenSearch ServerlessではIAMに加えてData Access Policyを設定します。
3. **文書単位の絞り込み**：認証済みClaimからMetadata FilterまたはACL `userContext`を構築します。
4. **Tool Callの認可**：AgentCore PolicyとTool側IAM・業務認可を組み合わせます。

Managed Knowledge BaseのACL awareness、Metadata Filter、AgentCore Policyは、IAMや利用者認証の代替ではありません。正常な主体のAllowだけでなく、権限外主体、Cross-tenant、失効済みCredential、Tool引数のDenyを自動テストします。[Knowledge BasesのService role](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-permissions.html)、[Managed KB permissions](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-permissions.html)、[Runtime security best practices](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-security-best-practices.html)を参照します（確認日：2026年8月22日）。

## 暗号化の境界をData分類に合わせる

原文、Vector、Index、Memory、Log、Evaluation dataを分類し、AWS owned / managed keyまたはCustomer managed KMS Keyを選びます。独自Keyを使う場合は、Key administratorとKey userを分け、各Service roleへ必要な`kms:Decrypt`と`kms:GenerateDataKey`だけを許可します。

Keyを無効化・削除すると、取り込み、検索、Log閲覧、Memoryへ影響します。Resourceごとに作成後のKey変更可否、再作成、移行、復旧を確認します。[Knowledge BasesのData encryption](https://docs.aws.amazon.com/bedrock/latest/userguide/encryption-kb.html)と[OpenSearch Serverless Encryption policies](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-encryption.html)を参照します（確認日：2026年8月22日）。

## 同じtrace_idで全工程を追う

BatchとReal-timeを別々のLogにしないで、次の情報を同じReleaseと`trace_id`へ関連づけます。

- **Batch**：Source、Data Source、Parser、Chunk、Embedding、Index、同期結果
- **検索**：原質問、Query、Filter、Retriever、候補数、Score、Rerank前後件数
- **生成**：Evidence版、Prompt、Model、Guardrail、Citation、回答保留理由
- **Agent**：Step、Tool、引数、Policy判定、Memory、停止理由
- **運用**：Error、Throttle、P95 Latency、Token、Cost per request、Feedback

CloudWatchはMetrics・Logs・Alarm、CloudTrailはAPI監査、X-Ray / ADOTは分散Trace、AgentCore ObservabilityはAgent stepの相関に使います。Model Invocation LoggingへFull request / responseを記録する場合は、機密情報、Masking、保持期間を先に決めます。[Managed KB observability](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-observability.html)、[Runtime CloudWatch metrics](https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-runtime-metrics.html)、[Model invocation logging](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html)、[AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-configure.html)を参照します（確認日：2026年8月22日）。

## 評価をRelease gateにする

AWSのEvaluation機能は実行基盤として使い、第7章のGround truth datasetと合格基準を共通入力にします。

- **Retrieve-only**：Recall@k、MRR、nDCG、Context relevance / coverage、ACL漏えい
- **Rerank・Evidence**：正解採用率、重要候補の脱落、矛盾、回答可能性
- **Generation**：Correctness、Completeness、Faithfulness、Citation precision / coverage、回答保留
- **Agent**：Task success、Trajectory、Tool Allow/Deny、Memory、不要Step
- **非機能**：Error、P95 Latency、Throttle、安全性、Cost per answer

LLM-as-a-judgeには偏り、変動、費用があります。決定的な正解照合、専門家評価、Production feedbackと組み合わせます。[Knowledge Bases evaluation](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-kb.html)、[Retrieve evaluation metrics](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-eval-retrieve.html)、[AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations-types.html)を参照します（確認日：2026年8月22日）。

## 変更単位と再評価範囲を固定する

Promptだけでなく、SourceからApplicationまでを一組のVersionとして残します。

| 変更のまとまり | 再作成・移行 | 必須の再評価 |
|---|---|---|
| Parser・Chunk・Embedding | 再取り込み、再Embedding、新Index | Recall、Citation粒度、容量、Latency |
| Store・Metadata・ACL | 新Index / Collection、Backfill | Search type、Filter、Allow/Deny、費用 |
| Rerank・Generation・Guardrail | Configuration / Version更新 | nDCG、Faithfulness、Citation、安全性 |
| Agent・Tool・Memory・Application | Agent / Application版更新 | Task success、Trajectory、Policy、Rollback |

**表10-8 変更時の再作成・再評価範囲**

Managed KBのEmbedding方式、S3 VectorsのDimension・Distance Metric・non-filterable key、OpenSearchのCollection typeや非互換Mappingは、新しいKnowledge BaseまたはIndexを必要とする場合があります。上書きせず、新旧を同条件で比較してから切り替えます。

Prompt ManagementとGuardrailsはDRAFTではなく、評価済み数値VersionをReleaseへ固定します。[Prompt versionのDeploy](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-management-deploy.html)と[GuardrailのVersion](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-test.html)を参照します（確認日：2026年8月22日）。

## 費用を工程別に配賦する

| 工程 | 主なCost driver |
|---|---|
| Batch | 原文Storage、Parser、Embedding、同期、再取り込み |
| 検索 | Managed KB、S3 Vectors Query、OpenSearch OCU、Rerank候補数 |
| 生成 | Input / Output token、Model、Guardrails、Streaming |
| Application・運用 | Runtime、Gateway、Memory、Log、Trace、Evaluation |

**表10-9 工程別の主なCost driver**

単価だけでなく、保存量、検索頻度、候補数、Token、待機Capacity、再処理を同じTraffic前提へ換算します。費用削減のためにTop-kやContextを減らす場合も、第7章の品質基準をRelease gateにします。[Application inference profilesによるCost management](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-application-inference-profiles.html)、[Amazon Bedrock pricing](https://aws.amazon.com/bedrock/pricing/)、[AgentCore pricing](https://aws.amazon.com/bedrock/agentcore/pricing/)を参照します（確認日：2026年8月22日）。

## ADRで設計を完了する

Architecture Decision Recordには、採用案だけでなく次を残します。

- **工程と責任**：四工程・二層の入出力、AWSが管理する範囲、利用者が実装する範囲
- **選択理由**：KB方式、Parser、Chunking、Embedding、Store、API、Model、AgentCoreの採否
- **Security**：IAM主体、KMS Key、Network、ACL / Filter、Tool Policy
- **検証**：Dataset、Metric、合格基準、費用前提、失敗時の保留・Escalation
- **変更**：再取り込み、再Embedding、再索引、切替、Rollback、再検討条件

これにより、AWSサービス名の一覧ではなく、責任分界と検証可能な構成として第1章から第9章の設計を実装へ翻訳できます。
