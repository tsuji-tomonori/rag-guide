# 10.7. 構成パターン

以下のdimension、chunk size、候補数、rerank後件数は、固定評価データで比較を始めるための初期値です。無条件の推奨値やサービス上限ではありません。data、query、region、model、store、latency budget、cost条件を固定し、変更前後を測定して採用値を決めます。

## 10.7.1. S3 Vectorsによるsemantic RAG

`S3 → Knowledge Bases → S3 Vectors → Retrieve → Converse`

Titan Text Embeddings V2の1024次元、`float32`、正規化、cosineを基準にし、default chunking約300 token、Retrieve 20件、rerank後5件から評価を始めます。S3 Vectorsはdense semantic search専用とし、固有名詞の取りこぼしが許容範囲かを確認します。

## 10.7.2. 対応vector storeによるhybrid RAG

`S3 → Knowledge Bases → hybrid対応vector store → Retrieve(HYBRID) → reranker → Converse`

Amazon OpenSearch Serverlessを使う場合、indexは`faiss` engineで作成し、embedding modelと同じdimensionのvector field、raw chunkを保存するfilterableなtext field、filter対象metadata、Bedrock metadata fieldを定義します。Knowledge Base作成時に各field名をindex mappingと一致させ、`overrideSearchType="HYBRID"`を指定します。Amazon Aurora PostgreSQLまたはMongoDB Atlasを使う場合も、対応するvector fieldとfilterableなtext fieldを公式手順に従って構成します。

AWSのユーザーガイドとAPI Referenceで対応storeの記述が一致しない場合があるため、対象リージョンで最小indexを作り、同一requestの`SEMANTIC`と`HYBRID`を実行してから構成を確定します。確認日、region、store種別、index schema、request、responseを証跡へ残します。固有名詞、識別子、表記揺れを含むqueryでRecallが改善するかを同じcandidate数で確認します。

## 10.7.3. S3 VectorsとBM25を分けるAdvanced RAG

`Lambda → S3 Vectorsのdense検索 + OpenSearchのBM25 → RRF → reranker → Evidence Set → Converse`

vector保存量をS3 Vectorsへ置きつつ、語彙一致を別検索器で補う構成です。各検索器には同じ`chunk_id`、version、filter metadata、アクセス制御属性を登録し、取り込み、更新、削除を両方へ伝播させます。初期値として各20件を取得し、RRFで20件へ統合してから5件へrerankします。denseのみ、BM25のみ、統合後を別々に記録し、各retrieverのtimeoutと部分失敗も評価します。

## 10.7.4. 複数情報源・構造化dataを使うRAG

`LambdaまたはStep Functions → Knowledge Bases + Athena/Aurora/Redshift + Neptune Analytics → Evidence Set → Converse`

文書、表、関係graphを別のretrieverとして扱い、sourceごとにquery、結果schema、timeout、最大件数を固定します。結果はsource scoreを直接加算せず、役割とprovenanceを持つEvidence Setへ変換します。適用条件は[Federated・Routed RAG](../9.失敗パターンに応じて高度化する/9.3.Federated・Routed RAG.md)と[Structured Data RAG](../9.失敗パターンに応じて高度化する/9.4.Structured Data RAG.md)で確認します。

構造化dataへの問い合わせは、読み取り専用の認証情報、許可したschema・table・column、parameter binding、SQL構文木の検査、tenant条件、row limit、timeout、cost上限を強制します。0行、権限不足、timeout、一部結果を通常値と混同せず、実行したquery、parameter、実行時刻、結果行を回答の根拠へ結び付けます。書き込み操作は別の業務手順へ分離し、人の承認を要求します。

## 10.7.5. Multimodal文書RAG

`S3 → Bedrock Data Automationまたはmultimodal embedding → Knowledge Bases → Retrieve → Converse`

layout解析後のtextを検索する方式と、imageをmultimodal embeddingで検索する方式を分けます。表の値を答えるquery、図を探すquery、ページ全体の意味を問うqueryで評価し、text-onlyの基準を上回る処理だけを残します。[Multimodal Knowledge Base](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-multimodal.html)の対応parser、model、image保存先を実装時に確認します。

## 10.7.6. Managed Knowledge Baseによる運用委任型RAG

`S3またはnative connector → Managed Knowledge Base → Retrieve(managedSearchConfiguration) → 必要に応じて検索後処理 → Converse`

Managed Knowledge Baseでは`RetrieveAndGenerate`を使用せず、検索に`Retrieve`または`AgenticRetrieveStream`を使います。
取り込み、索引、vector保存、hybrid search、document ranking、権限を考慮した検索の運用をサービスへ委ねる構成です。`managedSearchConfiguration.numberOfResults`を開始値20として調整し、検索方式を`overrideSearchType`で上書きしません。カスタマーマネージド型と同じ評価データを使い、Recall、引用の正確性、権限negative test、更新反映時間、traceの粒度、latency、cost、独自rerankingやEvidence Setとの接続性を比較します。agentic retrievalを使う場合も、探索step、上限、失敗時のfallback、根拠のprovenanceを記録し、サービスへ委ねたことを検証省略の理由にしません。
