# 10.7 構成パターン

## 10.7.1 S3 Vectorsによるsemantic RAG

`S3 → Knowledge Bases → S3 Vectors → Retrieve → Converse`

Titan Text Embeddings V2の1024次元、`float32`、正規化、cosineを基準にし、default chunking約300 token、Retrieve 20件、rerank後5件から評価を始めます。S3 Vectorsはdense semantic search専用とし、固有名詞の取りこぼしが許容範囲かを確認します。

## 10.7.2 OpenSearch Serverlessによるhybrid RAG

`S3 → Knowledge Bases → OpenSearch Serverless → Retrieve(HYBRID) → reranker → Converse`

indexは`faiss` engineで作成し、embedding modelと同じdimensionのvector field、raw chunkを保存するfilterableなtext field、filter対象metadata、Bedrock metadata fieldを定義します。Knowledge Base作成時に各field名をindex mappingと一致させ、`overrideSearchType="HYBRID"`を指定します。SEMANTICとHYBRIDを同じcandidate数で比較し、固有名詞、識別子、表記揺れを含むqueryでRecallが改善するかを確認します。

## 10.7.3 S3 VectorsとBM25を分けるAdvanced RAG

`Lambda → S3 Vectorsのdense検索 + OpenSearchのBM25 → RRF → reranker → Evidence Set → Converse`

vector保存量をS3 Vectorsへ置きつつ、語彙一致を別検索器で補う構成です。各検索器には同じ`chunk_id`、version、filter metadata、アクセス制御属性を登録し、取り込み、更新、削除を両方へ伝播させます。初期値として各20件を取得し、RRFで20件へ統合してから5件へrerankします。denseのみ、BM25のみ、統合後を別々に記録し、各retrieverのtimeoutと部分失敗も評価します。

## 10.7.4 複数情報源・構造化dataを使うRAG

`LambdaまたはStep Functions → Knowledge Bases + Athena/Aurora/Redshift + Neptune Analytics → Evidence Set → Converse`

文書、表、関係graphを別のretrieverとして扱い、sourceごとにquery、結果schema、timeout、最大件数を固定します。結果はsource scoreを直接加算せず、役割とprovenanceを持つEvidence Setへ変換します。適用条件は[Federated・Routed RAG](../9.失敗パターンに応じて高度化する/9.3.Federated・Routed RAG.md)と[Structured Data RAG](../9.失敗パターンに応じて高度化する/9.4.Structured Data RAG.md)で確認します。

## 10.7.5 Multimodal文書RAG

`S3 → Bedrock Data Automationまたはmultimodal embedding → Knowledge Bases → Retrieve → Converse`

layout解析後のtextを検索する方式と、imageをmultimodal embeddingで検索する方式を分けます。表の値を答えるquery、図を探すquery、ページ全体の意味を問うqueryで評価し、text-onlyの基準を上回る処理だけを残します。[Multimodal Knowledge Base](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-multimodal.html)の対応parser、model、image保存先を実装時に確認します。
