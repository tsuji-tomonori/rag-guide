# 検索後処理を構成する

検索後処理は、検索で得た候補をそのまま生成へ渡さず、質問に対する有用性、重複、版、信頼度、トークン予算を確認し、根拠集合へ変換する工程です。
AWS標準ではBedrock 再順位付けモデルを詳しく利用できます。
一方、業務規則を含む選別や根拠集合は利用者の処理として明示します。

## Bedrock 再順位付けモデル

### 1. RAGでの目的

質問と候補テキストをまとめて評価し、第5章のcross-encoder型再順位付けとして関連度順を付け直します。
Denseやキーワード検索の粗い順位を、生成へ渡す前に改善します。

### 2. 四工程・二層の位置

Real-time Layerの検索後処理に置きます。
検索で候補を取得した後、重複排除、業務規則、コンテキスト入力への配置の前後関係は評価によって決めます。

### 3. AWSリソース

Bedrock 再順位付けモデル、モデル ARN、Bedrock Agent Runtimeの`Rerank` API、Knowledge Baseの再順位付け設定、呼び出し元IAMロールを使います。
Managed KBのAWS管理の再順位付けはサービス設定として選びます。

### 4. 接続先

単体`Rerank` APIへ質問とテキストの情報源を渡すか、Knowledge Basesの`Retrieve`またはCustomer-managed KBの`RetrieveAndGenerate`内へ組み込みます。
結果は根拠選別または生成へ渡します。

### 5. AWSが管理する範囲

AWSは再順位付けモデルのホスティング、推論、入力候補に対する関連度スコアと順位の返却を管理します。
Managed KBの既定構成ではAWS管理の再順位付けもAWSが管理します。

### 6. 利用者が選択する項目

モデル ARN、初期候補数、再順位付け後の返却数、メタデータを`ALL`または`SELECTIVE`のどちらでモデルへ含めるか、タイムアウト、IAMの`bedrock:Rerank`権限を選びます。
候補数と返却数は品質・応答時間・費用の比較対象です。

### 7. 評価する項目

再順位付け前後のnDCG@k、MRR、Precision@k、正解根拠採用率、重要な候補の脱落率、P95 応答時間、候補数当たり費用、生成トークン削減量を評価します。
質問型と文書型で効果を分けます。

### 8. 制約

再順位付け器は入力された候補だけを並べ替えるため、Initial 検索で取得できなかった根拠を回復できません。
再順位付け APIはテキストの情報源を対象とし、要求当たりの検索文数・情報源数、対応モデル・リージョン・クォータに従います。
候補を増やすほど推論費用と応答時間が増えます。

### 9. 他の選択肢との使い分け

検索順位が十分で、候補が少ない場合は無効化を基準構成にできます。
検索Recallは高いが上位Precisionが低い場合に再順位付けを比較します。
公開状態、最新版、情報源 trustなど決定的な業務規則は再順位付け器へ代替させず、フィルターまたは個別処理で扱います。

### 10. 個別実装が必要になる条件

複数再順位付け器の統合、検索スコアとの独自合成、業務信頼度による採否、採用・不採用理由の記録、Imageや構造化Recordの独自評価が必要ならアプリケーション処理を追加します。

再順位付けの利用経路は[Bedrock Rerank](https://docs.aws.amazon.com/bedrock/latest/userguide/rerank.html)、要求とスコアは[`Rerank` API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_Rerank.html)、対応モデルとリージョンは[Rerank対応状況](https://docs.aws.amazon.com/bedrock/latest/userguide/rerank-supported.html)を参照します（確認日：2026年9月5日）。

## 候補数と返却数を分ける

初期候補数は再順位付け器へ渡す検索結果数、再順位付け後の返却数は次工程へ残す件数です。
前者は検索Recallの上限、後者はコンテキストのPrecisionとトークン量へ影響します。
`numberOfResults`と再順位付け後件数を同じ値に固定せず、次の比較を行います。

- 初期候補を増やしたときにRecallと正解採用率がどこまで改善するか
- 再順位付け後件数を減らしたときにFaithfulnessを保ったままトークンを削減できるか
- 再順位付けに追加した応答時間・費用が、回答品質改善に見合うか
- メタデータをモデル入力へ含めることで順位が改善するか、不要な情報で悪化するか

**表10-10 検索後処理におけるAWSと利用者の責任分界**

| 区分 | AWSが行うこと | 利用者が決めること |
|---|---|---|
| 候補取得 | KB・ストアで検索 | 検索器、Top-k、フィルター |
| 再順位付け | モデル推論、スコア・順位返却 | モデル、候補数、返却数、メタデータ |
| 業務選別 | 実行基盤を提供 | 版、公開状態、信頼度規則 |
| 根拠集合 | モデル・保存容量・実行環境を利用可能 | スキーマ、採否理由、矛盾、回答可能性 |
| コンテキスト整形 | モデル・実行環境を利用可能 | 圧縮、順序、トークン配分 |

| 区分 | 利用者が評価すること | 個別実装が必要になる場合 |
|---|---|---|
| 候補取得 | Recall@k、応答時間 | 複数検索器の独自統合 |
| 再順位付け | nDCG、MRR、費用 | 業務スコアとの統合 |
| 業務選別 | 誤採用、監査可能性 | 処理ロジックが必要 |
| 根拠集合 | 根拠十分性、再現性 | 処理ロジックが必要 |
| コンテキスト整形 | Faithfulness、Lost-in-the-middle | 処理ロジックが必要 |


## AWS標準だけでは完結しない検索後処理

以下は実装方法を本章で扱いません。
必要条件、配置、利用可能な実行基盤だけを示します。

- **重複排除**：同一文書の重複チャンク、転載、版違いがコンテキストを占有する場合に必要。Real-time Layerの検索後処理へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第5章の重複排除と第9章の失敗分析を参照。
- **MMR・Diversity制御**：上位候補が同じ文書・同じ観点へ偏り、複数観点を覆えない場合に必要。Real-time Layerの検索後処理へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第5章のDiversityを参照。
- **版・鮮度・信頼度による選別**：新旧文書が矛盾する、公開前文書を除外する、公式情報源を優先する場合に必要。可能な条件は検索フィルター、残りはReal-time Layerの検索後処理へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第5章と第8章を参照。
- **独自スコア統合**：検索、再順位付け、鮮度、信頼度を業務規則で統合する場合に必要。Real-time Layerの検索後処理へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第5章を参照。
- **根拠集合**：採用・不採用理由、矛盾、回答可能性、引用 IDを監査可能にする場合に必要。Real-time Layerの検索後処理と生成の境界へ配置。Lambda、ECS、EKS、AgentCore Runtime、DynamoDBやS3を利用可能。第5章の根拠設計と第7章を参照。
- **コンテキスト圧縮**：取得候補がモデルのトークン予算を超える、不要部分がFaithfulnessを下げる場合に必要。Real-time Layerの検索後処理へ配置。Lambda、ECS、EKS、AgentCore RuntimeとBedrock モデルを利用可能。第5章のコンテキスト圧縮を参照。
- **コンテキスト入力への配置**：複数文書の順序、文書当たり上限、トークン配分、Lost-in-the-middleを厳密に制御する場合に必要。Real-time Layerの検索後処理から生成の境界へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第5章のコンテキスト入力への配置を参照。
- **採用・不採用理由の記録**：規制、監査、失敗分析で候補単位の判断を説明する場合に必要。Real-time Layerの検索後処理へ配置。Lambda、ECS、EKS、AgentCore RuntimeとCloudWatch、S3を利用可能。第7〜9章を参照。
