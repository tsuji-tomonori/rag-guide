# 検索後処理を構成する

検索後処理は、検索で得た候補をそのまま生成へ渡さず、質問に対する有用性、重複、版、信頼度、Token予算を確認し、Evidence Setへ変換する工程です。AWS標準ではBedrock Rerank Modelを詳しく利用できます。一方、業務規則を含む選別やEvidence Setは利用者の処理として明示します。

## Bedrock Rerank Model

**1. RAGでの目的**

質問と候補Textをまとめて評価し、第5章のcross-encoder型Rerankingとして関連度順を付け直します。DenseやKeyword検索の粗い順位を、生成へ渡す前に改善します。

**2. 四工程・二層の位置**

Real-time Layerの検索後処理に置きます。検索で候補を取得した後、重複排除、業務規則、Context Packingの前後関係は評価によって決めます。

**3. AWSリソース**

Bedrock Rerank Model、Model ARN、Bedrock Agent Runtimeの`Rerank` API、Knowledge BaseのReranking Configuration、呼び出し元IAM roleを使います。Managed KBのservice-managed Rerankingはサービス設定として選びます。

**4. 接続先**

単体`Rerank` APIへ質問とText sourceを渡すか、Knowledge Basesの`Retrieve`またはCustomer-managed KBの`RetrieveAndGenerate`内へ組み込みます。結果はEvidence選別またはGenerationへ渡します。

**5. AWSが管理する範囲**

AWSはRerank ModelのHosting、推論、入力候補に対するRelevance Scoreと順位の返却を管理します。Managed KBの既定構成ではservice-managed RerankingもAWSが管理します。

**6. 利用者が選択する項目**

Model ARN、Initial candidate数、Rerank後の返却数、Metadataを`ALL`または`SELECTIVE`のどちらでModelへ含めるか、Timeout、IAMの`bedrock:Rerank`権限を選びます。候補数と返却数は品質・Latency・費用の比較対象です。

**7. 評価する項目**

Rerank前後のnDCG@k、MRR、Precision@k、正解Evidence採用率、重要な候補の脱落率、P95 Latency、候補数当たり費用、Generation Token削減量を評価します。質問型と文書型で効果を分けます。

**8. 制約**

Rerankerは入力された候補だけを並べ替えるため、Initial Retrievalで取得できなかった根拠を回復できません。Rerank APIはText sourceを対象とし、Request当たりのQuery数・Source数、対応Model・Region・Quotaに従います。候補を増やすほど推論費用とLatencyが増えます。

**9. 他の選択肢との使い分け**

検索順位が十分で、候補が少ない場合は無効化をBaselineにできます。検索Recallは高いが上位Precisionが低い場合にRerankを比較します。公開状態、最新版、Source trustなど決定的な業務規則はRerankerへ代替させず、Filterまたは個別処理で扱います。

**10. 個別実装が必要になる条件**

複数Rerankerの統合、検索Scoreとの独自合成、業務信頼度による採否、採用・不採用理由の記録、Imageや構造化Recordの独自評価が必要ならアプリケーション処理を追加します。

Rerankの利用経路は[Bedrock Rerank](https://docs.aws.amazon.com/bedrock/latest/userguide/rerank.html)、RequestとScoreは[`Rerank` API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_Rerank.html)、対応ModelとRegionは[Rerank対応状況](https://docs.aws.amazon.com/bedrock/latest/userguide/rerank-supported.html)を参照します（確認日：2026年8月22日）。

## Candidate数と返却数を分ける

Initial candidate数はRerankerへ渡す検索結果数、Rerank後の返却数は次工程へ残す件数です。前者は検索Recallの上限、後者はContextのPrecisionとToken量へ影響します。`numberOfResults`とRerank後件数を同じ値に固定せず、次の比較を行います。

- Initial candidateを増やしたときにRecallと正解採用率がどこまで改善するか
- Rerank後件数を減らしたときにFaithfulnessを保ったままTokenを削減できるか
- Rerankに追加したLatency・費用が、回答品質改善に見合うか
- MetadataをModel入力へ含めることで順位が改善するか、不要な情報で悪化するか

| 区分 | AWSが行うこと | 利用者が決めること | 利用者が評価すること | 個別実装が必要になる場合 |
|---|---|---|---|---|
| 候補取得 | KB・Storeで検索 | Retriever、Top-k、Filter | Recall@k、Latency | 複数Retrieverの独自統合 |
| Rerank | Model推論、Score・順位返却 | Model、候補数、返却数、Metadata | nDCG、MRR、費用 | 業務Scoreとの統合 |
| 業務選別 | 実行基盤を提供 | 版、公開状態、信頼度規則 | 誤採用、監査可能性 | 処理ロジックが必要 |
| Evidence Set | Model・Storage・Runtimeを利用可能 | Schema、採否理由、矛盾、回答可能性 | 根拠十分性、再現性 | 処理ロジックが必要 |
| Context整形 | Model・Runtimeを利用可能 | 圧縮、順序、Token配分 | Faithfulness、Lost-in-the-middle | 処理ロジックが必要 |

## AWS標準だけでは完結しない検索後処理

以下は実装方法を本章で扱いません。必要条件、配置、利用可能な実行基盤だけを示します。

- **重複排除**：同一文書の重複Chunk、転載、版違いがContextを占有する場合に必要。Real-time Layerの検索後処理へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第5章の重複排除と第9章の失敗分析を参照。
- **MMR・Diversity制御**：上位候補が同じ文書・同じ観点へ偏り、複数観点を覆えない場合に必要。Real-time Layerの検索後処理へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第5章のDiversityを参照。
- **版・鮮度・信頼度による選別**：新旧文書が矛盾する、公開前文書を除外する、公式Sourceを優先する場合に必要。可能な条件は検索Filter、残りはReal-time Layerの検索後処理へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第5章と第8章を参照。
- **独自Score統合**：Retrieval、Rerank、鮮度、信頼度を業務規則で統合する場合に必要。Real-time Layerの検索後処理へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第5章を参照。
- **Evidence Set**：採用・不採用理由、矛盾、回答可能性、Citation IDを監査可能にする場合に必要。Real-time Layerの検索後処理と生成の境界へ配置。Lambda、ECS、EKS、AgentCore Runtime、DynamoDBやS3を利用可能。第5章のEvidence設計と第7章を参照。
- **Context Compression**：取得候補がModelのToken予算を超える、不要部分がFaithfulnessを下げる場合に必要。Real-time Layerの検索後処理へ配置。Lambda、ECS、EKS、AgentCore RuntimeとBedrock Modelを利用可能。第5章のContext Compressionを参照。
- **Context Packing**：複数文書の順序、文書当たり上限、Token配分、Lost-in-the-middleを厳密に制御する場合に必要。Real-time Layerの検索後処理から生成の境界へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第5章のContext Packingを参照。
- **採用・不採用理由の記録**：規制、監査、失敗分析でCandidate単位の判断を説明する場合に必要。Real-time Layerの検索後処理へ配置。Lambda、ECS、EKS、AgentCore RuntimeとCloudWatch、S3を利用可能。第7〜9章を参照。
