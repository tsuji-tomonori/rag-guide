# 権限・監視・版管理を全工程へ通す

IAM、KMS、監視、評価、版管理、コスト管理は、検索とは別の第三Layerではありません。Batch Layerの取り込みからReal-time Layerの回答まで同じRequestと版を追跡し、誰がどの文書・Model・Toolへアクセスできるかを一貫して制御する横断的な管理面です。

## IAM――主体とTrust Boundary

**1. RAGでの目的**

構築者、AWS service、Application、Agent、End userを分け、原文、Index、Model、Toolへ必要最小限の操作だけを許可します。

**2. 四工程・二層の位置**

Batch LayerとReal-time Layer、四工程すべてに横断適用します。

**3. AWSリソース**

IAM Identity、Role、Policy、Resource-based Policy、STS session、Knowledge Base service role、Application execution role、AgentCore Runtime role、Gateway roleを使います。

**4. 接続先**

Knowledge Base service roleからData Source、Embedding Model、Vector Store、KMS Keyへ接続します。Application roleからKnowledge Base APIとBedrock Runtimeへ、AgentCore Runtime/Gateway roleからTool targetへ接続します。

**5. AWSが管理する範囲**

AWSはPolicy evaluation、Temporary credential、Service principal、CloudTrailの管理Event記録基盤を提供します。

**6. 利用者が選択する項目**

Trust Policy、Action、Resource、Condition、Session tag、Cross-account Resource Policy、Permission boundary、ToolごとのRoleを選びます。Data planeのMetadata FilterはIAM Policyとは別に設計します。

**7. 評価する項目**

正常な主体のAllow、権限外主体のDeny、Cross-tenant漏えい、Privilege escalation、失効、Key復号、Tool単位のAllow/Denyを自動テストします。

**8. 制約**

Managed KBのACL awarenessはAuthorizationそのものではありません。OpenSearch ServerlessはIAM Policyに加えてData Access Policyが必要です。AgentCore PolicyもIAMを置き換えません。Service roleへ広いWildcardを与えるとTrust Boundaryが崩れます。

**9. 他の選択肢との使い分け**

IAMはAWS APIの認可、OpenSearch Data Access PolicyはCollection/Index data plane、Metadata FilterはDocument-level絞り込み、AgentCore PolicyはGateway Tool Callを扱います。各層を役割どおりに組み合わせます。

**10. 個別実装が必要になる条件**

IdP ClaimからDocument Filterへの変換、業務RoleとTool Policyの対応、Approval、Temporary access、Tenant境界の検証はアプリケーションと運用処理が必要です。

Knowledge Base service roleの権限は[Knowledge BasesのService role](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-permissions.html)、Managed KBは[Managed KB permissions](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-permissions.html)、AgentCore Runtimeは[Runtime security best practices](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-security-best-practices.html)を参照します（確認日：2026年8月22日）。

```text
End User / IdP
      │ verified claims
      ▼
Application Role ── Retrieve / Converse ── Bedrock・Knowledge Base
      │                                      │ service role
      │ Metadata Filter                      ├─ S3 Data Source
      │                                      ├─ Embedding / Rerank Model
      │                                      └─ S3 Vectors / OpenSearch
      │
      └─ AgentCore Runtime Role ── Gateway Role ── Tool / API / Managed KB

Trust Boundaryごとに IAM / Resource Policy / Data Access Policy / Tool Policy を分離
```

## KMS――保存・通信・Logの暗号化

**1. RAGでの目的**

原文、Vector、Index、Memory、Log、Evaluation dataをData分類に応じたKeyで暗号化し、Key利用を監査します。

**2. 四工程・二層の位置**

Batch/Real-time両Layerと全工程の保存データ、サービス間通信、Logに横断適用します。

**3. AWSリソース**

AWS owned key、AWS managed key、Customer managed KMS Key、Key Policy、Grant、Aliasを使います。S3、Managed KB、S3 Vectors、OpenSearch Serverless、CloudWatch Logs、AgentCore Memoryなどへ関連づけます。

**4. 接続先**

各Service roleとApplication roleへ必要な`kms:Decrypt`、`kms:GenerateDataKey`などを最小範囲で許可します。OpenSearchはEncryption PolicyからKeyを参照します。

**5. AWSが管理する範囲**

AWSはKMSのKey material保護、暗号Operation、監査Event、AWS owned keyのRotationとService integrationを管理します。

**6. 利用者が選択する項目**

Key種別、ResourceごとのKey分離、Key administratorとKey user、Cross-account、Rotation、Deletion待機、Log用Key、Data residency要件を選びます。

**7. 評価する項目**

暗号化対象の網羅、正当Roleの復号、権限外Roleの拒否、Key無効化時の影響、Cross-account、Rotation、KMS Request費用、復旧を評価します。

**8. 制約**

Key PolicyとIAMの両方が必要な接続があります。Keyを無効化・削除すると取り込み、検索、Log閲覧、Memoryへ影響します。ServiceやResourceによって作成後のKey変更に制約があり、再作成やデータ移行が必要になる場合があります。

**9. 他の選択肢との使い分け**

運用を減らすならAWS owned/managed key、Key Policy、Cross-account、独自Rotation、監査境界が必要ならCustomer managed keyを比較します。

**10. 個別実装が必要になる条件**

Data分類に応じたKey選択、Tenant別暗号境界、Key失効時の業務Fallback、再暗号化・移行Workflowは利用者が設計します。

Knowledge Basesの暗号化範囲は[Knowledge BasesのData encryption](https://docs.aws.amazon.com/bedrock/latest/userguide/encryption-kb.html)、OpenSearch Serverlessの暗号化は[Encryption policies](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-encryption.html)を参照します（確認日：2026年8月22日）。

## CloudWatch・CloudTrail・Trace――監視する

**1. RAGでの目的**

Ingestion、Retrieval、Rerank、Generation、Agent/Toolを一つの`trace_id`で追跡し、品質低下、Error、Throttle、Latency、費用増を検知します。

**2. 四工程・二層の位置**

Batch LayerのIngestionからReal-time Layerの全工程まで横断します。

**3. AWSリソース**

CloudWatch Metrics、Logs、Alarms、Dashboards、CloudTrail、X-Ray、ADOT、AgentCore Observability、S3/FirehoseのLog destinationを使います。

**4. 接続先**

Managed KBのRuntime Metrics・Storage Metrics・Ingestion Log、Knowledge Base API、Bedrock Runtime Metrics、Application Log、AgentCoreのRuntime/Gateway/Memory/Tool TraceをCloudWatchへ接続します。

**5. AWSが管理する範囲**

AWSは各Service Metrics、Log配信機能、CloudTrail Event、CloudWatchの保存・Query・Alarm基盤を提供します。Managed KBはRequest、Error、Throttle、Storage、Ingestion Logを公開します。AgentCoreはBuilt-in MetricsをCloudWatchへ送り、詳細TraceはADOT計装とTransaction Searchを利用します。

**6. 利用者が選択する項目**

Log destination、Metric、SLO、Alarm閾値、Trace sampling、Request metadata、保持期間、Masking、Dashboard、Correlation IDを選びます。Model Invocation Loggingは既定で無効であり、Full request/responseを記録する前に機密性を評価します。

**7. 評価する項目**

Ingestion成功・失敗、文書件数、Raw data size、Retrieve回数、候補数、Rerank前後件数、Model Token、Error、Throttle、P95 Latency、Agent Step、Tool Call、Trace欠損、Cost per requestを監視します。

**8. 制約**

Service MetricsはBest effortの場合があり、品質指標やCandidate採否理由を自動的には含みません。Full Prompt・Reference・ResponseのLogは機密情報を含み得ます。Managed KBのX-Ray対応範囲やAgentCoreの標準Trace範囲はAPIごとに異なります。

**9. 他の選択肢との使い分け**

CloudWatchはAWS資源とApplicationの運用観測、CloudTrailはAPI監査、X-Ray/ADOTは分散Trace、AgentCore ObservabilityはAgent stepの相関に使います。第7章のOffline評価は運用Metricsで置き換えません。

**10. 個別実装が必要になる条件**

Candidate単位の採否、Query/Index/Prompt版、Citation正確性、Feedback、業務OutcomeをTraceへ結ぶにはApplication telemetryが必要です。

Managed KBの公開Metricsは[Managed KB observability](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-observability.html)、Bedrock Model Metricsは[Runtime CloudWatch metrics](https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-runtime-metrics.html)、Invocation Logの注意は[Model invocation logging](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html)、Agent traceは[AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-configure.html)を参照します（確認日：2026年8月22日）。

```text
Design versions ─────────────────────────────────────────────────────┐
Source → Data Source → Parser → Chunk → Embedding → Index            │
                                        Query → Retrieve → Rerank    │
                                                  → Evidence → Model │
Telemetry ─ trace_id ─ Metrics / Logs / Trace / Evaluation / Cost ──┘

同じRequestに Source・Index・Retrieval・Rerank・Prompt・Guardrail・Application版を記録
```

## 評価――第7章へ接続する

**1. RAGでの目的**

設定変更を印象で判断せず、検索と生成を分け、品質・性能・安全・費用を比較します。

**2. 四工程・二層の位置**

Batchの索引候補、Real-timeのRetrieval・Rerank・Generation、Agent trajectoryの全境界に横断します。

**3. AWSリソース**

Bedrock Knowledge Bases Evaluation、Foundation Model Evaluation、AgentCore Evaluations、S3 Evaluation dataset、IAM role、CloudWatchを使えます。

**4. 接続先**

Retrieve-only評価をKnowledge Baseへ、Retrieve-and-generate評価をKBとModelへ、Agentic flow評価をAgentCore Traceへ接続します。第7章のGround truth datasetを共通入力にします。

**5. AWSが管理する範囲**

AWSはEvaluation Job、Built-in evaluator、LLM-as-a-judgeまたは対応評価方式、結果保存の基盤を提供します。

**6. 利用者が選択する項目**

Dataset、Ground truth、比較構成、Evaluator、Judge Model、Metric、合格基準、Human review、再評価条件を選びます。

**7. 評価する項目**

RetrievalはRecall@k、MRR、nDCG、Context relevance/coverage、GenerationはCorrectness、Completeness、Faithfulness、Citation precision/coverage、Harm、Refusal、AgentはTask successとTrajectoryを評価します。

**8. 制約**

LLM-as-a-judgeには偏り・変動・費用があり、Citationの存在と正しさを同一視できません。Built-in Metricsだけで業務正解や権限境界は保証されません。Model・Region・Dataset形式の対応条件があります。

**9. 他の選択肢との使い分け**

AWSのEvaluation機能は実行基盤と標準Metricに使い、第7章の決定的な正解照合、専門家評価、Production feedbackと組み合わせます。AgentCore EvaluationsはAgent trajectory向けで、通常RAGのRetrieval評価の代替ではありません。

**10. 個別実装が必要になる条件**

Domain固有Metric、Claim-level評価、ACL漏えい、版矛盾、費用対品質、Online A/B、Human review集計は独自Evaluatorまたは評価Pipelineが必要です。

Knowledge BasesのRetrieve-only/RAG評価は[Knowledge Bases evaluation](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-kb.html)、Retrieval metricは[Retrieve evaluation metrics](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-eval-retrieve.html)、Agent評価は[AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations-types.html)を参照します（確認日：2026年8月22日）。

## 版管理――再現可能な単位を残す

Promptだけでなく、SourceからApplicationまで一組のVersionとして残します。最低限、次の属性をTraceまたはEvaluation resultへ関連づけます。

| 対象 | 記録する属性 | 変更時の主な処置 |
|---|---|---|
| Knowledge Base | `knowledge_base_id`、方式 | 全経路の回帰評価 |
| Data Source | `data_source_id`、`data_source_version`、同期時刻 | 増分同期、Document件数・削除確認 |
| Parser / Chunk | Parser、Parsing Prompt版、Chunking StrategyとParameter | 再取り込み、新Data Source/Index、Retrieval評価 |
| Embedding | Model、Dimension、Vector Type | 全Chunk再Embedding、新Index、旧新比較 |
| Index | Store、Collection/Bucket、`index_version`、Schema | 新Index、Backfill、切替、Rollback |
| Retrieval | Search type、Filter schema、Top-k、Query変換版 | Retrieve-only回帰評価 |
| Rerank | Model、Candidate数、返却数、Metadata選択 | nDCG/MRR、Latency、費用評価 |
| Evidence | Evidence Set schema/version、採否規則 | Faithfulness、Citation回帰評価 |
| Generation | Model、Inference Profile、Prompt Version、Parameter | End-to-end回答評価 |
| Guardrail | Guardrail ID、数値Version | SafetyとFalse positive回帰評価 |
| Agent | Runtime、Tool schema、Policy、Memory Strategy | Trajectory、Allow/Deny、Memory評価 |
| Application | `application_version`、Feature flag | Canary/A-B、Rollback |

Prompt ManagementはDRAFTから数値Versionを作成し、GuardrailsもDRAFTと数値Versionを分けます。[Prompt versionのDeploy](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-management-deploy.html)と[GuardrailのVersion](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-test.html)を参照します（確認日：2026年8月22日）。

## 変更時に再作成・再評価する範囲

| 変更 | 再作成・移行の主な対象 | 必須の再評価 |
|---|---|---|
| Managed KBのEmbedding方式 | 新Managed KB、全Data Source同期 | Retrieval、Rerank、Latency、費用 |
| Customer-managedのEmbedding Model/Dimension/Vector Type | 新Index、全Chunk再Embedding | 言語・質問型別Recall、容量、Latency |
| Chunking Strategy | 新Data SourceまたはIndex、再取り込み | Recall、Citation粒度、Context量 |
| S3 VectorsのDimension/Distance/non-filterable key | 新Vector Index | Recall、Filter、Storage、Query費用 |
| OpenSearch Collection type・非互換Mapping | 新Collection/Index、Reindex | Keyword/Vector/Hybrid、Security、OCU |
| Metadata schema・ACL | Backfillまたは再同期 | Allow/Deny、漏えい、過剰除外 |
| Rerank Model・Candidate数 | Configuration更新 | nDCG、MRR、Latency、費用 |
| Generation Model・Prompt・Parameter | Version更新 | Faithfulness、Citation、形式、保留 |
| Guardrail Policy・Version | Version更新 | 攻撃・安全・False positive回帰 |
| Agent Tool/Policy/Memory Strategy | Agent構成更新 | Task success、Trajectory、Allow/Deny、Memory |

## コスト管理――工程別に配賦する

Cost per answerは、Model Tokenだけでは決まりません。Batch LayerとReal-time Layerを分け、次のDriverを同じTraffic前提で積算します。

| 工程 | 主なCost driver |
|---|---|
| 原文 | S3 Storage、Request、Version保持、Data transfer |
| Ingestion | ParserのPage/Token、Embedding、同期頻度、再取り込み |
| Managed KB | Raw data Storage、Retrieve、Agentic retrieval、Custom Model利用 |
| S3 Vectors | Vector/Metadata Storage、PUT、Query、処理データ量 |
| OpenSearch Serverless | Indexing/Search OCU、Storage、Data transfer、待機Capacity |
| Rerank | Candidate数、Request数、Model |
| Generation | Input/Output token、Model、Inference Profile、Streaming |
| Guardrails | 評価Text unit・Policy利用量 |
| AgentCore | Runtime CPU/Memory、Gateway Call、Memory、Policy、Evaluation、Observability |
| 観測 | CloudWatch Log量、Metric、Trace、保持、Query |

Model単位の費用配賦にはApplication Inference ProfileとTagを使える場合があります。[Application inference profilesによるCost management](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-application-inference-profiles.html)、[Amazon Bedrock pricing](https://aws.amazon.com/bedrock/pricing/)、[AgentCore pricing](https://aws.amazon.com/bedrock/agentcore/pricing/)を参照します（確認日：2026年8月22日）。

費用削減だけを目的にTop-k、Rerank候補、Context、Modelを減らすと品質を損ないます。第7章の合格基準を満たす構成の中から、1質問当たり費用とピーク時容量を比較します。BudgetとCost anomalyのAlertは、品質・Latency Alertと同じRelease単位へ関連づけます。
