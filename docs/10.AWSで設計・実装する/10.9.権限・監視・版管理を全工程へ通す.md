# 権限・監視・版管理を全工程へ通す

IAM、KMS、監視、評価、版管理、コスト管理は、二層の全工程に適用します。
Batch Layerの取り込みからReal-time Layerの回答まで同じ要求と版を追跡し、誰がどの文書・モデル・ツールへアクセスできるかを一貫して制御する横断的な管理面です。

## IAM――主体と信頼境界

### 1. RAGでの目的

構築者、AWS service、アプリケーション、エージェント、End userを分け、原文、インデックス、モデル、ツールへ必要最小限の操作だけを許可します。

### 2. 四工程・二層の位置

Batch LayerとReal-time Layer、四工程すべてに横断適用します。

### 3. AWSリソース

IAM 識別情報、役割、ポリシー、リソースベースのポリシー、STSセッション、Knowledge Base サービスロール、アプリケーション 実行ロール、AgentCore Runtimeの実行ロール、Gatewayの実行ロールを使います。

### 4. 接続先

Knowledge Base サービスロールからデータソース、埋め込みモデル、ベクトルストア、KMS キーへ接続します。
アプリケーション roleからKnowledge Base APIとBedrock 実行環境へ、AgentCore Runtime/Gatewayの実行ロールからツール targetへ接続します。

### 5. AWSが管理する範囲

AWSはポリシー evaluation、Temporary credential、Service principal、CloudTrailの管理Event記録基盤を提供します。

### 6. 利用者が選択する項目

Trust ポリシー、処理結果、リソース、Condition、セッション tag、Cross-アカウントリソースポリシー、権限 boundary、ツールごとの役割を選びます。
データ planeのメタデータフィルターはIAM ポリシーとは別に設計します。

### 7. 評価する項目

正常な主体のAllow、権限外主体のDeny、Cross-tenant漏えい、Privilege escalation、失効、キー復号、ツール単位のAllow/Denyを自動テストします。

### 8. 制約

Managed KBのACL対応検索は、渡された利用者情報に基づいて文書の閲覧条件を適用します。
アプリケーション側で、利用者の認証とAPI呼び出しの認可を行います。
OpenSearch ServerlessはIAM ポリシーに加えてデータアクセスポリシーが必要です。
AgentCore PolicyもIAMを置き換えません。
サービスロールへ広いWildcardを与えると信頼境界が崩れます。

### 9. 他の選択肢との使い分け

IAMはAWS APIの認可、OpenSearch データアクセスポリシーはコレクション/インデックス データ操作、メタデータフィルターは文書単位の絞り込み、AgentCore PolicyはGateway ツール呼び出しを扱います。
各層を役割どおりに組み合わせます。

### 10. 個別実装が必要になる条件

認証基盤の属性情報から文書フィルターへの変換、業務役割とツールポリシーの対応、承認、一時アクセス、テナント境界の検証はアプリケーションと運用処理が必要です。

Knowledge Base サービスロールの権限は[Knowledge BasesのService role](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-permissions.html)、Managed KBは[Managed KB permissions](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-permissions.html)、AgentCore Runtimeは[Runtime security best practices](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-security-best-practices.html)を参照します（確認日：2026年9月5日）。

```text
End User / IdP
      │ verified claims
      ▼
Application Role ── Retrieve / Converse ── Bedrock・Knowledge Base
      │                                      │ service role
      │ Metadata Filter                      ├─ S3 Data Source
      │                                      ├─ Embedding / Rerank Model
      │                                      └─ S3 Vectors / OpenSearch
      │
      └─ AgentCore Runtime Role ── Gateway Role ── Tool / API / Managed KB

Trust Boundaryごとに IAM / Resource Policy / Data Access Policy / Tool Policy を分離
```

## KMS――保存・通信・ログの暗号化

### 1. RAGでの目的

原文、ベクトル、インデックス、記憶管理、ログ、Evaluation dataをデータ分類に応じたキーで暗号化し、キー利用を監査します。

### 2. 四工程・二層の位置

Batch/Real-time両層と全工程の保存データ、サービス間通信、ログに横断適用します。

### 3. AWSリソース

AWS owned key、AWS managed key、Customer managed KMS キー、キー ポリシー、Grant、Aliasを使います。
S3、Managed KB、S3 Vectors、OpenSearch Serverless、CloudWatch ログ、AgentCore Memoryなどへ関連づけます。

### 4. 接続先

各サービスロールとアプリケーション roleへ必要な`kms:Decrypt`、`kms:GenerateDataKey`などを最小範囲で許可します。
OpenSearchは暗号化ポリシーからキーを参照します。

### 5. AWSが管理する範囲

AWSはKMSのキー material保護、暗号Operation、監査Event、AWS owned keyのRotationとService integrationを管理します。

### 6. 利用者が選択する項目

キー種別、リソースごとのキー分離、キー administratorとキー user、Cross-アカウント、Rotation、Deletion待機、ログ用キー、データ residency要件を選びます。

### 7. 評価する項目

暗号化対象の網羅、正当役割の復号、権限外役割の拒否、キー無効化時の影響、Cross-アカウント、Rotation、KMS 要求費用、復旧を評価します。

### 8. 制約

キー ポリシーとIAMの両方が必要な接続があります。
キーを無効化・削除すると取り込み、検索、ログ閲覧、記憶管理へ影響します。
Serviceやリソースによって作成後のキー変更に制約があり、再作成やデータ移行が必要になる場合があります。

### 9. 他の選択肢との使い分け

運用を減らすならAWS owned/managed key、キー ポリシー、Cross-アカウント、独自Rotation、監査境界が必要ならCustomer managed keyを比較します。

### 10. 個別実装が必要になる条件

データ分類に応じたキー選択、テナント別暗号境界、キー失効時の業務代替処理、再暗号化・移行ワークフローは利用者が設計します。

Knowledge Basesの暗号化範囲は[Knowledge BasesのData encryption](https://docs.aws.amazon.com/bedrock/latest/userguide/encryption-kb.html)、OpenSearch Serverlessの暗号化は[Encryption policies](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-encryption.html)を参照します（確認日：2026年9月5日）。

## CloudWatch・CloudTrail・トレース――監視する

### 1. RAGでの目的

取り込み、検索、再順位付け、生成、エージェント/ツールを一つの`trace_id`で追跡し、品質低下、エラー、スロットリング、応答時間、費用増を検知します。

### 2. 四工程・二層の位置

Batch Layerの取り込みからReal-time Layerの全工程まで横断します。

### 3. AWSリソース

CloudWatch 指標、ログ、Alarms、Dashboards、CloudTrail、X-Ray、ADOT、AgentCore Observability、S3/Firehoseのログ destinationを使います。

### 4. 接続先

Managed KBの実行環境指標・保存容量指標・取り込みログ、Knowledge Base API、Bedrock 実行環境指標、アプリケーションログ、AgentCoreの実行環境/Gateway/記憶管理/ツールトレースをCloudWatchへ接続します。

### 5. AWSが管理する範囲

AWSは各Service 指標、ログ配信機能、CloudTrail Event、CloudWatchの保存・検索文・Alarm基盤を提供します。
Managed KBは要求、エラー、スロットリング、保存容量、取り込みログを公開します。
AgentCoreはBuilt-in 指標をCloudWatchへ送り、詳細トレースはADOT計装とTransaction 検索を利用します。

### 6. 利用者が選択する項目

ログ destination、指標、SLO、Alarm閾値、トレース sampling、要求 metadata、保持期間、マスキング、Dashboard、Correlation IDを選びます。
モデル呼び出しログは既定で無効であり、要求と応答の全文を記録する前に機密性を評価します。

### 7. 評価する項目

取り込み成功・失敗、文書件数、Raw data size、Retrieve回数、候補数、再順位付け前後件数、モデルトークン、エラー、スロットリング、P95 応答時間、エージェント Step、ツール呼び出し、トレース欠損、要求当たりの費用を監視します。

### 8. 制約

Service 指標はBest effortの場合があり、品質指標や候補採否理由を自動的には含みません。
Full プロンプト・参照資料・応答のログは機密情報を含み得ます。
Managed KBのX-Ray対応範囲やAgentCoreの標準トレース範囲はAPIごとに異なります。

### 9. 他の選択肢との使い分け

CloudWatchはAWS資源とアプリケーションの運用観測、CloudTrailはAPI監査、X-Ray/ADOTは分散トレース、AgentCore Observabilityはエージェント stepの相関に使います。
第7章のOffline評価は運用指標で置き換えません。

### 10. 個別実装が必要になる条件

候補単位の採否、検索文/インデックス/プロンプト版、引用正確性、Feedback、業務Outcomeをトレースへ結ぶにはアプリケーション telemetryが必要です。

Managed KBの公開指標は[Managed KB observability](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-managed-observability.html)、Bedrock モデル指標は[Runtime CloudWatch metrics](https://docs.aws.amazon.com/bedrock/latest/userguide/monitoring-runtime-metrics.html)、Invocation ログの注意は[Model invocation logging](https://docs.aws.amazon.com/bedrock/latest/userguide/model-invocation-logging.html)、エージェント traceは[AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability-configure.html)を参照します（確認日：2026年9月5日）。

```text
Design versions ─────────────────────────────────────────────────────┐
Source → Data Source → Parser → Chunk → Embedding → Index            │
                                        Query → Retrieve → Rerank    │
                                                  → Evidence → Model │
Telemetry ─ trace_id ─ Metrics / Logs / Trace / Evaluation / Cost ──┘

同じRequestに Source・Index・Retrieval・Rerank・Prompt・Guardrail・Application版を記録
```

## 評価――第7章へ接続する

### 1. RAGでの目的

設定変更を印象で判断せず、検索と生成を分け、品質・性能・安全・費用を比較します。

### 2. 四工程・二層の位置

Batchの索引候補、Real-timeの検索・再順位付け・生成、エージェントの実行履歴の全境界に横断します。

### 3. AWSリソース

Bedrock Knowledge Bases Evaluation、基盤モデル Evaluation、AgentCore Evaluations、S3 Evaluation dataset、IAMロール、CloudWatchを使えます。

### 4. 接続先

Retrieve-only評価をKnowledge Baseへ、Retrieve-and-generate評価をKBとモデルへ、Agentic flow評価をAgentCore トレースへ接続します。
第7章のGround truth datasetを共通入力にします。

### 5. AWSが管理する範囲

AWSはEvaluation Job、Built-in evaluator、LLM-as-a-judgeまたは対応評価方式、結果保存の基盤を提供します。

### 6. 利用者が選択する項目

Dataset、Ground truth、比較構成、Evaluator、Judge モデル、指標、合格基準、人による確認、再評価条件を選びます。

### 7. 評価する項目

検索はRecall@k、MRR、nDCG、コンテキスト relevance/coverage、生成はCorrectness、Completeness、Faithfulness、引用 precision/coverage、Harm、Refusal、エージェントはTask successと実行履歴を評価します。

### 8. 制約

LLM-as-a-judgeには偏り・変動・費用があり、引用の存在と正しさを同一視できません。
Built-in 指標だけで業務正解や権限境界は保証されません。
モデル・リージョン・Dataset形式の対応条件があります。

### 9. 他の選択肢との使い分け

AWSのEvaluation機能は実行基盤と標準指標に使い、第7章の決定的な正解照合、専門家評価、本番 feedbackと組み合わせます。
AgentCore Evaluationsはエージェントの実行履歴向けで、通常RAGの検索評価の代替ではありません。

### 10. 個別実装が必要になる条件

分野固有指標、主張単位評価、ACL漏えい、版矛盾、費用対品質、Online A/B、人による確認集計は独自Evaluatorまたは評価処理の流れが必要です。

Knowledge BasesのRetrieve-only/RAG評価は[Knowledge Bases evaluation](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-kb.html)、検索 metricは[Retrieve evaluation metrics](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-eval-retrieve.html)、エージェント評価は[AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations-types.html)を参照します（確認日：2026年9月5日）。

## 版管理――再現可能な単位を残す

プロンプトだけでなく、情報源からアプリケーションまで一組の版として残します。
最低限、次の属性をトレースまたはEvaluation resultへ関連づけます。

| 対象 | 記録する属性 | 変更時の主な処置 |
|---|---|---|
| Knowledge Base | `knowledge_base_id`、方式 | 全経路の回帰評価 |
| データソース | `data_source_id`、`data_source_version`、同期時刻 | 増分同期、文書件数・削除確認 |
| 解析器 / チャンク | 解析器、解析プロンプト版、チャンク分割 Strategyとパラメーター | 再取り込み、新データソース/インデックス、検索評価 |
| 埋め込み | モデル、次元数、ベクトル型 | 全チャンク再埋め込み、新インデックス、旧新比較 |
| インデックス | ストア、コレクション/バケット、`index_version`、スキーマ | 新インデックス、Backfill、切替、切り戻し |
| 検索 | 検索方式、フィルター スキーマ、Top-k、検索文変換版 | Retrieve-only回帰評価 |
| 再順位付け | モデル、候補数、返却数、メタデータ選択 | nDCG/MRR、応答時間、費用評価 |
| 根拠 | 根拠集合スキーマ/version、採否規則 | Faithfulness、引用回帰評価 |
| 生成 | モデル、推論プロファイル、プロンプト版、パラメーター | システム全体回答評価 |
| Guardrail | Guardrail ID、数値版 | SafetyとFalse positive回帰評価 |
| エージェント | 実行環境、ツールスキーマ、ポリシー、記憶管理 Strategy | 実行履歴、Allow/Deny、記憶管理評価 |
| アプリケーション | `application_version`、Feature flag | Canary/A-B、切り戻し |

Prompt managementはDRAFTから数値版を作成し、GuardrailsもDRAFTと数値版を分けます。
[Prompt versionのDeploy](https://docs.aws.amazon.com/bedrock/latest/userguide/prompt-management-deploy.html)と[GuardrailのVersion](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-test.html)を参照します（確認日：2026年9月5日）。

| OpenSearch コレクション type・非互換Mapping | 新コレクション/インデックス、Reindex | キーワード/ベクトル/ハイブリッド、セキュリティ、OCU |
| メタデータのスキーマ・ACL | Backfillまたは再同期 | Allow/Deny、漏えい、過剰除外 |
| 再順位付けモデル・候補数 | 設定更新 | nDCG、MRR、応答時間、費用 |
| 生成モデル・プロンプト・パラメーター | 版更新 | Faithfulness、引用、形式、保留 |
| Guardrail ポリシー・版 | 版更新 | 攻撃・安全・False positive回帰 |
| エージェントツール/ポリシー/記憶管理 Strategy | エージェント構成更新 | Task success、実行履歴、Allow/Deny、記憶管理 |


## コスト管理――工程別に配賦する

回答当たりの費用は、モデルトークンだけでは決まりません。
Batch LayerとReal-time Layerを分け、次の費用の要因を同じ利用量前提で積算します。

| 工程 | 主な費用 driver |
|---|---|
| 原文 | S3 保存容量、要求、版保持、データ transfer |
| 取り込み | 解析器のPage/トークン、埋め込み、同期頻度、再取り込み |
| Managed KB | Raw data 保存容量、Retrieve、Agentic retrieval、カスタムモデル利用 |
| S3 Vectors | ベクトル/メタデータ保存容量、PUT、検索文、処理データ量 |
| OpenSearch Serverless | 索引の作成/検索 OCU、保存容量、データ transfer、待機Capacity |
| 再順位付け | 候補数、要求数、モデル |
| 生成 | 入力・出力トークン数、モデル、推論プロファイル、ストリーミング |
| Guardrails | 評価テキスト単位・ポリシー利用量 |
| AgentCore | 実行環境 CPU/記憶管理、Gateway Call、記憶管理、ポリシー、Evaluation、実行状態の観測 |
| 観測 | CloudWatch ログ量、指標、トレース、保持、検索文 |

モデル単位の費用配賦にはアプリケーション推論プロファイルとTagを使える場合があります。
[Application inference profilesによるCost management](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-application-inference-profiles.html)、[Amazon Bedrock pricing](https://aws.amazon.com/bedrock/pricing/)、[AgentCore pricing](https://aws.amazon.com/bedrock/agentcore/pricing/)を参照します（確認日：2026年9月5日）。

費用削減だけを目的にTop-k、再順位付け候補、コンテキスト、モデルを減らすと品質を損ないます。
第7章の合格基準を満たす構成の中から、1質問当たり費用とピーク時容量を比較します。
Budgetと費用 anomalyの通知は、品質・応答時間通知と同じRelease単位へ関連づけます。
