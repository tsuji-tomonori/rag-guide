# RAGアプリケーションとAgentCoreを配置する

Knowledge BaseまたはVector Storeは根拠を探す基盤であり、利用者のRequestを受け、認証し、工程を順に実行して回答するアプリケーションは別に必要です。通常の一問一答RAGを先に検討し、Agent loop、Tool、Memory、Tool単位のPolicyが必要な場合だけAgentCoreを追加します。

```text
通常の一問一答RAG                     AgentCoreを使うAgentic RAG

利用者                                利用者
  │                                     │
認証                                  Identity
  │                                     │
API Gateway / ALB                     AgentCore Runtime
  │                                     ├─ Gateway → Managed KB / API / Lambda / MCP
Lambda / ECS / EKS                     ├─ Memory
  ├─ Knowledge Base / Vector Store      ├─ Policy
  ├─ Evidence Set                       └─ Observability
  └─ Bedrock Generation Model              │
  │                                     Bedrock Model / Tool
回答                                  回答・業務実行
```

## 通常のRAGアプリケーション

次の条件では、AgentCoreを使わず、API GatewayまたはALBとLambda、ECS、EKSなどで実行する通常アプリケーションをBaselineにできます。

- 一つの質問に対し、検索・生成を一巡すれば完了する
- Knowledge Baseまたは検索先が一つで、動的Routingが不要である
- Toolを使って業務状態を変更しない
- 長時間処理や複数Stepの再開が不要である
- SessionをアプリケーションのStorageで管理できる
- 通常のApplication Log、Metric、Traceで十分に追跡できる

通常構成でも、認証、Metadata Filter、Evidence Set、Model呼び出し、回答保留、監視は必要です。AgentCoreを使わないことは、これらの責任がなくなることを意味しません。

## Amazon Bedrock AgentCore

**1. RAGでの目的**

RAGや業務Toolを利用し、複数Stepで判断・実行するAgentアプリケーションへ、Runtime、Tool接続、Identity、Memory、Policy、Observability、Evaluationsを提供します。Knowledge BaseやVector Storeを置き換えません。

**2. 四工程・二層の位置**

主にReal-time Layerのアプリケーション実行基盤として、質問側検索前処理、検索呼び出し、検索後処理、生成、Tool実行をオーケストレーションします。AgentCore自体を第三のLayerに数えません。Batch LayerのIngestionとIndexingはKnowledge Basesや別のBatch基盤が担当します。

**3. AWSリソース**

AgentCore Runtime、Gateway、Identity、Memory、Policy、Observability、Evaluations、Runtime execution role、Gateway role、Credential providerを使います。必要なモジュールだけを選べます。

**4. 接続先**

RuntimeからBedrock Model、Knowledge Base、S3 Vectors、OpenSearch、業務APIを呼びます。GatewayはLambda、API、MCP serverなどをTool化します。Managed Knowledge BaseはGatewayのNative targetとして`Retrieve`と`AgenticRetrieveStream`を公開できます。Customer-managed KBはNative KB targetの対象ではないため、RuntimeからAPIを呼ぶか、Lambda/API ToolとしてGatewayへ接続します。

**5. AWSが管理する範囲**

AWSはRuntimeのServerless hosting、Session isolationとScaling、GatewayのTool endpoint、IdentityのCredential管理、Memoryの保存・抽出基盤、Policy engineでの決定的評価、CloudWatchへのMetrics・Trace基盤を提供します。Agentの判断Logic、Toolの意味、許可Policy、Memoryへ保存する内容は利用者が持ちます。

**6. 利用者が選択する項目**

Agent framework・Model・停止条件、Runtime ProtocolとSession、公開ToolとSchema、Inbound/Outbound認証、Credential、MemoryのShort-term/Long-term Strategy・Namespace・保持、Cedar Policy、Trace計装、EvaluationのEvaluatorとDatasetを選びます。

**7. 評価する項目**

Task success、Trajectory、Tool選択・引数、検索品質、最終回答品質、不要Step、Loop停止、Policy deny/allow、Memory汚染、P95 Latency、Runtime・Gateway・Memory等の費用、Agent step単位のTrace完全性を評価します。

**8. 制約**

RuntimeはAgent loop Logicを提供するKnowledge Baseではなく、利用者のAgent/ToolをHostingする基盤です。Runtime Sessionの一時状態とLong-term Memoryは別です。Gateway PolicyはGatewayを通るTool Callへ適用し、IAMやアプリケーション認可の代替ではありません。Native Managed KB targetでUser Contextを使う場合も、アプリケーションが検証済み値を渡します。Agent化によりStep数、Latency、費用、失敗経路、評価対象が増えます。

**9. 他の選択肢との使い分け**

一問一答、短い処理、Toolなしなら通常のLambda/ECS/EKSアプリケーションを選びます。複数回検索、複数KBへのRouting、Tool/MCP、長時間処理、Memory、Tool単位認可、Step Traceが必要ならAgentCoreを比較します。単にManaged KBのagentic retrievalだけが必要なら、通常アプリケーションから`AgenticRetrieveStream`を呼ぶ構成でもよく、AgentCore全体は必須ではありません。

**10. 個別実装が必要になる条件**

Agentの計画、検索先選択、Tool引数、停止条件、Fallback、Compensation、Human approval、Memoryへ保存する情報、業務APIの変換は利用者が実装します。AgentCoreは実行・統制基盤を提供しますが、Agent Logicを自動的に正しくしません。

AgentCore全体の責任は[Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html)、Runtimeの責任は[AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html)、Managed KB接続は[Gateway target connector for Managed Knowledge Bases](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-connector-managed-kb.html)を参照します（確認日：2026年8月22日）。

## AgentCore要素をRAGの責任へ対応づける

| AgentCore要素 | RAGアプリでの役割 | AWSが管理する範囲 | 利用者が選ぶ項目 | 主な制約・評価 |
|---|---|---|---|---|
| Runtime | AgentまたはToolの実行環境 | Serverless hosting、Isolation、Scaling | Framework、Model、Protocol、Session、Execution role | Agent Logicは利用者責任。Task success、Loop、Latencyを評価 |
| Gateway | API、Lambda、MCP、Managed KBをTool接続 | MCP endpoint、Target呼び出し、認証経路 | Tool schema、Target、公開引数、Credential | Native KB targetはManaged KB。Tool successと引数を評価 |
| Identity | Inbound/Outbound認証・Credential | Workload identity、Token・Secret連携 | IdP、Credential provider、委譲範囲 | UserとAgentの権限混同を防ぐ。認証失敗・過剰権限を評価 |
| Memory | 会話と利用者文脈 | Short-term保存、Long-term抽出・検索基盤 | Strategy、Namespace、保持、削除、同意 | 検索Indexの代替ではない。汚染、漏えい、再現性を評価 |
| Policy | Gateway Tool Callの決定的な認可 | Cedar Policy engineでTool call評価 | Default deny、許可条件、User/Tool属性 | Gateway外の呼び出しは別統制。Allow/Denyテストが必要 |
| Observability | Agent・Model・Tool・Memoryの追跡 | Built-in Metrics、CloudWatch統合 | ADOT計装、Trace属性、Masking、保持 | 詳細Traceは計装が必要。欠損と機密混入を評価 |
| Evaluations | Agentic flowの品質評価 | Online/On-demand/Batch評価基盤 | Evaluator、Dataset、Judge/Lambda、合格基準 | 通常RAGのRetrieval評価を置換しない。Trajectoryを評価 |

Gatewayは[Core concepts](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-core-concepts.html)、Identityは[AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html)、Memoryは[AgentCore Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html)、Policyは[Policy core concepts](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-core-concepts.html)、Observabilityは[AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html)、Evaluationsは[AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html)を参照します（確認日：2026年8月22日）。

## Runtime、Memory、Knowledge Baseを混同しない

Runtime Sessionは一連のAgent処理を隔離して実行する単位です。MemoryはSession内の短期Eventや、Strategyによって抽出した長期Memoryを保持します。Knowledge Baseは組織文書を検索するための索引です。この三つは保存期間、権限、削除、評価が異なります。

- Runtimeの一時状態：処理の継続と隔離に必要な最小状態
- Short-term Memory：会話Session内のEvent
- Long-term Memory：利用者同意とStrategyに基づくSession横断の記憶
- Knowledge Base：管理された組織文書と検索可能な根拠
- 原文S3：版・所有者・公開状態を持つ正本

個人情報や業務秘密をMemoryへ保存する場合、検索用文書のACLとは別に、保存目的、Namespace、保持期間、削除、本人同意、KMS Key、Log maskingを設計します。[Memory terminology](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-terminology.html)（確認日：2026年8月22日）。

## AgentCoreを使う判断

AgentCoreの採否は「RAGかどうか」ではなく、次の能力が必要かで決めます。

- 一つの質問で複数回検索し、検索先や次のQueryをAgentが決める
- 複数Knowledge Base、社内API、Lambda、MCP Toolを選択する
- 回答後に申請、登録、通知などのTool実行を行う
- 長時間処理、複数Step、Session隔離が必要である
- Short-termまたはLong-term Memoryが必要である
- Tool Callを決定的なPolicyで許可・拒否する
- Model、Tool、MemoryをまたぐAgent step TraceとTrajectory評価が必要である

これらがなければ、AgentCoreを追加しても検索品質そのものは改善しません。まず第4〜7章のRetrieval・Generation Baselineを通常アプリケーションで確立し、Agent化で増える効果と費用を比較します。
