# RAGアプリケーションとAgentCoreを配置する

Knowledge Baseまたはベクトルストアは根拠を探す基盤であり、利用者の要求を受け、認証し、工程を順に実行して回答するアプリケーションは別に必要です。
通常の一問一答RAGを先に検討し、エージェントの反復処理、ツール、記憶管理、ツール単位のポリシーが必要な場合だけAgentCoreを追加します。

```text
通常の一問一答RAG                     AgentCoreを使うAgentic RAG

利用者                                利用者
  │                                     │
認証                                  Identity
  │                                     │
API Gateway / ALB                     AgentCore Runtime
  │                                     ├─ Gateway → Managed KB / API / Lambda / MCP
Lambda / ECS / EKS                     ├─ Memory
  ├─ Knowledge Base / Vector Store      ├─ Policy
  ├─ Evidence Set                       └─ Observability
  └─ Bedrock Generation Model              │
  │                                     Bedrock Model / Tool
回答                                  回答・業務実行
```

## 通常のRAGアプリケーション

次の条件では、AgentCoreを使わず、API GatewayまたはALBとLambda、ECS、EKSなどで実行する通常アプリケーションを基準構成にできます。

- 一つの質問に対し、検索・生成を一巡すれば完了する
- Knowledge Baseまたは検索先が一つで、動的振り分けが不要である
- ツールを使って業務状態を変更しない
- 長時間処理や複数Stepの再開が不要である
- セッションをアプリケーションの保存容量で管理できる
- 通常のアプリケーションログ、指標、トレースで十分に追跡できる

通常構成でも、認証、メタデータフィルター、根拠集合、モデル呼び出し、回答保留、監視は必要です。
AgentCoreを使わないことは、これらの責任がなくなることを意味しません。

## Amazon Bedrock AgentCore

### 1. RAGでの目的

RAGや業務ツールを利用し、複数Stepで判断・実行するエージェントアプリケーションへ、実行環境、ツール接続、識別情報、記憶管理、ポリシー、実行状態の観測、Evaluationsを提供します。
Knowledge Baseやベクトルストアを置き換えません。

### 2. 四工程・二層の位置

主にReal-time Layerのアプリケーション実行基盤として、質問側検索前処理、検索呼び出し、検索後処理、生成、ツール実行をオーケストレーションします。
AgentCore自体を第三の層に数えません。
Batch Layerの取り込みと索引の作成はKnowledge Basesや別のBatch基盤が担当します。

### 3. AWSリソース

AgentCore Runtime、Gateway、識別情報、記憶管理、ポリシー、実行状態の観測、Evaluations、実行環境 実行ロール、Gatewayの実行ロール、Credential providerを使います。
必要なモジュールだけを選べます。

### 4. 接続先

実行環境からBedrock モデル、Knowledge Base、S3 Vectors、OpenSearch、業務APIを呼びます。
GatewayはLambda、API、MCP serverなどをツール化します。
Managed Knowledge BaseはGatewayのNative targetとして`Retrieve`と`AgenticRetrieveStream`を公開できます。
Customer-managed KBはNative KB targetの対象ではないため、実行環境からAPIを呼ぶか、Lambda/API ツールとしてGatewayへ接続します。

### 5. AWSが管理する範囲

AWSは実行環境のServerless ホスティング、セッション isolationと拡張、Gatewayのツール endpoint、識別情報のCredential管理、記憶管理の保存・抽出基盤、ポリシー engineでの決定的評価、CloudWatchへの指標・トレース基盤を提供します。
エージェントの判断Logic、ツールの意味、許可ポリシー、記憶管理へ保存する内容は利用者が持ちます。

### 6. 利用者が選択する項目

エージェント framework・モデル・停止条件、実行環境 Protocolとセッション、公開ツールとスキーマ、Inbound/Outbound認証、Credential、記憶管理のShort-term/Long-term Strategy・Namespace・保持、Cedar ポリシー、トレース計装、EvaluationのEvaluatorとDatasetを選びます。

### 7. 評価する項目

Task success、実行履歴、ツール選択・引数、検索品質、最終回答品質、不要Step、Loop停止、ポリシー deny/allow、記憶管理汚染、P95 応答時間、実行環境・Gateway・記憶管理等の費用、エージェント step単位のトレース完全性を評価します。

### 8. 制約

実行環境はエージェントの反復処理 Logicを提供するKnowledge Baseではなく、利用者のエージェント/ツールをホスティングする基盤です。
実行セッションの一時状態とLong-term 記憶管理は別です。
Gateway ポリシーはGatewayを通るツール呼び出しへ適用し、IAMやアプリケーション認可の代替ではありません。
Native Managed KB targetで利用者コンテキストを使う場合も、アプリケーションが検証済み値を渡します。
エージェント化によりStep数、応答時間、費用、失敗経路、評価対象が増えます。

### 9. 他の選択肢との使い分け

一問一答、短い処理、ツールなしなら通常のLambda/ECS/EKSアプリケーションを選びます。
複数回検索、複数KBへの振り分け、ツール/MCP、長時間処理、記憶管理、ツール単位認可、Step トレースが必要ならAgentCoreを比較します。
単にManaged KBのエージェント型検索だけが必要なら、通常アプリケーションから`AgenticRetrieveStream`を呼ぶ構成でもよく、AgentCore全体は必須ではありません。

### 10. 個別実装が必要になる条件

エージェントの計画、検索先選択、ツール引数、停止条件、代替処理、Compensation、Human approval、記憶管理へ保存する情報、業務APIの変換は利用者が実装します。
AgentCoreは実行・統制基盤を提供しますが、エージェント Logicを自動的に正しくしません。

AgentCore全体の責任は[Amazon Bedrock AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html)、実行環境の責任は[AgentCore Runtime](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agents-tools-runtime.html)、Managed KB接続は[Gateway target connector for Managed Knowledge Bases](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-target-connector-managed-kb.html)を参照します（確認日：2026年9月5日）。

## AgentCore要素をRAGの責任へ対応づける

| AgentCore要素 | RAGアプリでの役割 | AWSが管理する範囲 |
|---|---|---|
| 実行環境 | エージェントまたはツールの実行環境 | Serverless ホスティング、分離、拡張 |
| Gateway | API、Lambda、MCP、Managed KBをツール接続 | MCP endpoint、Target呼び出し、認証経路 |
| 識別情報 | Inbound/Outbound認証・Credential | Workload identity、トークン・Secret連携 |
| 記憶管理 | 会話と利用者文脈 | Short-term保存、Long-term抽出・検索基盤 |
| ポリシー | Gateway ツール呼び出しの決定的な認可 | Cedar ポリシー engineでツール call評価 |
| 実行状態の観測 | エージェント・モデル・ツール・記憶管理の追跡 | Built-in 指標、CloudWatch統合 |
| Evaluations | Agentic flowの品質評価 | Online/On-demand/Batch評価基盤 |

| AgentCore要素 | 利用者が選ぶ項目 | 主な制約・評価 |
|---|---|---|
| 実行環境 | Framework、モデル、Protocol、セッション、Execution role | エージェント Logicは利用者責任。Task success、Loop、応答時間を評価 |
| Gateway | ツールスキーマ、Target、公開引数、Credential | Native KB targetはManaged KB。ツール successと引数を評価 |
| 識別情報 | IdP、Credential provider、委譲範囲 | 利用者とエージェントの権限混同を防ぐ。認証失敗・過剰権限を評価 |
| 記憶管理 | Strategy、Namespace、保持、削除、同意 | 検索インデックスの代替ではない。汚染、漏えい、再現性を評価 |
| ポリシー | 標準 deny、許可条件、利用者/ツール属性 | Gateway外の呼び出しは別統制。Allow/Denyテストが必要 |
| 実行状態の観測 | ADOT計装、トレース属性、マスキング、保持 | 詳細トレースは計装が必要。欠損と機密混入を評価 |
| Evaluations | Evaluator、Dataset、Judge/Lambda、合格基準 | 通常RAGの検索評価を置換しない。実行履歴を評価 |

Gatewayは[Core concepts](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/gateway-core-concepts.html)、識別情報は[AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html)、記憶管理は[AgentCore Memory](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory.html)、ポリシーは[Policy core concepts](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-core-concepts.html)、実行状態の観測は[AgentCore Observability](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/observability.html)、Evaluationsは[AgentCore Evaluations](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/evaluations.html)を参照します（確認日：2026年9月5日）。

## 実行環境、記憶管理、Knowledge Baseを混同しない

実行セッションは一連のエージェント処理を隔離して実行する単位です。
記憶管理はセッション内の短期Eventや、Strategyによって抽出した長期記憶管理を保持します。
Knowledge Baseは組織文書を検索するための索引です。
この三つは保存期間、権限、削除、評価が異なります。

- 実行環境の一時状態：処理の継続と隔離に必要な最小状態
- Short-term 記憶管理：会話セッション内のEvent
- Long-term 記憶管理：利用者同意とStrategyに基づくセッション横断の記憶
- Knowledge Base：管理された組織文書と検索可能な根拠
- 原文S3：版・所有者・公開状態を持つ正本

個人情報や業務秘密を記憶管理へ保存する場合、検索用文書のACLとは別に、保存目的、Namespace、保持期間、削除、本人同意、KMS キー、ログ maskingを設計します。
[Memory terminology](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/memory-terminology.html)（確認日：2026年9月5日）。

## AgentCoreを使う判断

AgentCoreの採否は「RAGかどうか」ではなく、次の能力が必要かで決めます。

- 一つの質問で複数回検索し、検索先や次の検索文をエージェントが決める
- 複数Knowledge Base、社内API、Lambda、MCP ツールを選択する
- 回答後に申請、登録、通知などのツール実行を行う
- 長時間処理、複数Step、セッション隔離が必要である
- Short-termまたはLong-term 記憶管理が必要である
- ツール呼び出しを決定的なポリシーで許可・拒否する
- モデル、ツール、記憶管理をまたぐエージェント step トレースと実行履歴評価が必要である

これらがなければ、AgentCoreを追加しても検索品質そのものは改善しません。
まず第4〜7章の検索・生成基準構成を通常アプリケーションで確立し、エージェント化で増える効果と費用を比較します。
