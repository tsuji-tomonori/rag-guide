# Batch Layerを構成する

Batch Layerは、質問を受ける前に、信頼できる原文を検索可能な索引へ変換します。
第3章の文書解析、チャンク分割、埋め込み、索引作成をAWSリソースへ対応づけます。
各設定の良し悪しは単体では決まらないため、原文、チャンク、ベクトル、インデックスの版を関連づけ、第7章の同じ評価データで比較します。

```text
原文・Metadata
    │
    ▼
Amazon S3 / Data Source
    │ Ingestion Job・増分同期
    ▼
Parser ──→ Chunking ──→ Bedrock Embedding Model
                              │
                              ▼
                 S3 Vectors / OpenSearch Serverless
                              │
                              ▼
                 検証済みIndexをReal-time Layerへ公開
```

**図10-3 Batch Layerの取り込みフロー**

## Amazon S3――原文とデータソース

### 1. RAGでの目的

検索結果から戻れる原文・正本を保持し、Knowledge Baseへ取り込む対象範囲をバケットとPrefixで定義します。
S3 Vectorsとは別の役割です。

### 2. 四工程・二層の位置

Batch Layerの文書側検索前処理の入口です。
生成時の引用先としてReal-time Layerから出典位置を参照することはありますが、検索や生成は、それぞれのサービスが担います。

### 3. AWSリソース

General purpose S3 バケット、Object、Prefix、任意のVersioning、Lifecycle、Object Tag、メタデータ sidecar、バケットポリシー、KMS キーを使います。
Knowledge Base側にはS3 データソースを作ります。

### 4. 接続先

S3 データソースをManagedまたはCustomer-managed Knowledge Baseへ接続します。
バケットはKnowledge Baseと同じリージョンに置き、サービスロールへ読み取り権限と、必要ならKMS復号権限を与えます。
原文更新後は取り込み Jobで同期します。

### 5. AWSが管理する範囲

S3はObject 保存容量の耐久性、可用性、暗号化機能、Versioning、Lifecycleを提供します。
Knowledge Basesは同期時に追加・変更・削除を検出し、対応する取り込み処理を実行します。

### 6. 利用者が選択する項目

バケット・Prefixの境界、原文形式、Object キー、Versioning、暗号化キー、保持期間、削除方針、文書所有者、公開状態、更新日、版、出典URLなどのメタデータを選びます。
メタデータ sidecarを使う場合は埋め込み対象に含める項目とフィルター専用項目も選びます。

### 7. 評価する項目

対象文書の網羅率、誤ったPrefix混入、正本と索引の一致、更新・削除反映時間、メタデータ欠損、古い版の残存、引用出典位置の再現性、保存容量・要求・転送費を評価します。

### 8. 制約

Knowledge BasesのS3 データソースはGeneral purpose バケットを使用し、同じリージョンに置きます。
メタデータ sidecarは対応形式とサイズ上限に従います。
S3を正本にした構成でKnowledge Baseへ直接投入した変更はS3へ逆反映されず、次回同期で上書きされる可能性があります。
したがって、更新経路を一つに定めます。

### 9. 他の選択肢との使い分け

原文をS3で統制できるなら、版、暗号化、Lifecycle、再取り込みを設計しやすい構成です。
SharePointなどを正本にするManaged Knowledge Baseでは、S3への複製が必須とは限りません。
S3 Vectorsは原文の代替ではなく、検索用ベクトルストアとして別に選びます。

### 10. 個別実装が必要になる条件

外部システムからの収集、承認ワークフロー、正本判定、文書信頼度付与、ウイルス検査、独自データ分類が必要ならBatch LayerのLambda、ECS、EKS、Step Functionsなどへ配置します。

S3 データソースの対象、メタデータ、増分同期は[S3 Data Source connector](https://docs.aws.amazon.com/bedrock/latest/userguide/s3-data-source-connector.html)、直接投入との整合は[Knowledge Baseへの直接取り込み](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-direct-ingestion.html)を参照します（確認日：2026年9月5日）。

## 解析器

### 1. RAGでの目的

PDF、Office文書、HTMLなどから、検索単位を作れるテキスト、表、図、レイアウト情報を抽出します。

### 2. 四工程・二層の位置

Batch Layerの文書側検索前処理で、チャンク分割より前に置きます。

### 3. AWSリソース

Knowledge Base データソースの解析設定、標準解析器、Bedrock データ Automation（BDA）解析器、基盤モデル解析器、任意のカスタム変換用Lambdaを使います。

### 4. 接続先

データソースから読み取った文書を解析器へ渡し、抽出結果をチャンク分割へ渡します。
Custom transformationは取り込み処理の流れからLambdaを呼びます。

### 5. AWSが管理する範囲

AWSは選択した解析器の実行、Bedrock モデルまたはBDAの推論基盤、Knowledge Basesへの結果受け渡しを管理します。
高度な解析器が失敗した場合、対応する構成では標準解析器へ代替処理することがあります。

### 6. 利用者が選択する項目

文書のレイアウト、表、図、画像の必要性から解析器を選びます。
基盤モデル解析器では対応モデルと解析プロンプト、BDAではOutputやMultimodalの要件、Custom transformationではLambdaと出力スキーマを選びます。

### 7. 評価する項目

見出し階層、表の行列対応、ページ位置、画像内テキスト、脚注、文字化け、読み順、抽出漏れを第3章の抽出評価と検索Recallで確認します。
ページ当たりまたはトークン当たり費用、同期応答時間も比較します。

### 8. 制約

標準解析器はテキスト中心で、複雑な表・図・画像の意味を十分に保持しない場合があります。
高度な解析器には対応形式、リージョン、モデル、クォータ、追加費用があります。
データソースの解析設定変更は再取り込みと比較評価を伴います。

### 9. 他の選択肢との使い分け

テキスト主体なら標準を基準構成にします。
表、図、段組み、画像が回答根拠になるときだけBDAまたは基盤モデル解析器を比較します。
業務固有のHeader、帳票、OCR後補正が必須ならCustom transformationを比較します。

### 10. 個別実装が必要になる条件

独自OCR、表の業務スキーマ化、帳票分類、機密情報の事前除去、独自の正規化が必要ならカスタム変換用Lambdaまたは上流のBatch処理へ置きます。
**表10-4 解析器の選択**

| 選択肢 | AWSが行うこと | 利用者が選ぶ主な項目 |
|---|---|---|
| 標準解析器 | 対応文書からテキストを抽出 | 原則追加設定なし |
| BDA 解析器 | レイアウト、表、図、画像を含む解析 | BDA利用、出力要件 |
| 基盤モデル解析器 | 指定モデルで高度な解析 | モデル、解析プロンプト |
| Custom transformation | Lambdaを取り込みから実行 | Function、出力スキーマ |

| 選択肢 | 選択条件 | 第7章で評価する項目 |
|---|---|---|
| 標準解析器 | テキスト主体の基準構成 | テキスト欠落、読み順、検索Recall |
| BDA 解析器 | Visual情報が根拠になる | 表・図の忠実性、費用、応答時間 |
| 基盤モデル解析器 | 文書構造に合わせた抽出 | 分野文書の抽出品質、トークン費用 |
| Custom transformation | 業務固有の変換が必須 | スキーマ適合、失敗率、再現性 |


解析器ごとの機能と課金単位は[高度なParsing](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-advanced-parsing.html)、Custom transformationは[Knowledge BasesのCustom transformation](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-custom-transformation.html)を参照します（確認日：2026年9月5日）。

## チャンク分割

### 1. RAGでの目的

解析器の出力を、検索時に見つけやすく、生成時に意味を解釈できる単位へ分けます。
第3章の「検索単位」と「読解単位」をAWS設定へ対応づけます。

### 2. 四工程・二層の位置

Batch Layerの文書側検索前処理で、解析の後、埋め込みの前に置きます。

### 3. AWSリソース

Knowledge Base データソースのチャンク分割設定を使います。
Customer-managed KBでは標準、固定長、階層型、意味に基づく、No chunkingを選べます。
Managed KBではサービスが公開するBuilt-in/標準や固定長など、その時点で利用可能な方式から選びます。

### 4. 接続先

解析器出力を受け、各チャンクを埋め込みモデルへ渡します。
階層型では子チャンクをベクトル検索し、返却時に広い親チャンクへ置換します。
No chunkingでは上流で検索単位に分割済みのObjectを渡します。

### 5. AWSが管理する範囲

AWSは方式に従う分割、重なり、チャンクと原文出典位置の関連づけ、階層型の子チャンク検索・親チャンク返却、意味に基づくの意味境界計算を実行します。

### 6. 利用者が選択する項目

`maxTokens`、`overlapPercentage`、親チャンク/子チャンクのトークン数、意味に基づくの`bufferSize`と境界しきい値を選びます。
値は第3章の仮説を比較する基準構成であり、文書形式と質問で評価して調整します。

### 7. 評価する項目

チャンク単体の意味完結性、Boundary跨ぎ、Recall@k、親チャンク返却後のPrecision、コンテキストトークン量、同一文書への偏り、引用粒度、保存容量・埋め込み量を評価します。

### 8. 制約

データソース接続後にチャンク分割 Strategyを変更できない構成があるため、比較と変更は新しいデータソースまたはインデックスを前提にします。
階層型は複数子チャンクが同じ親チャンクへ統合されるため、返却件数が`numberOfResults`より少なくなることがあります。
No chunkingではページ番号など一部の出典位置情報を失うことがあります。

### 9. 他の選択肢との使い分け

標準を最初の基準構成、固定長を再現可能な比較対象、意味に基づくを意味境界が重要な文書、階層型を小さく検索して広く読ませる文書、No chunkingを上流分割済み文書に使います。

### 10. 個別実装が必要になる条件

Recursive、Table-aware、見出し・条文・会話Turn単位、独自親チャンク-child、特殊な重なりが必要ならCustom transformationを使います。
詳細ロジックは第3章で定義し、Batch LayerのLambdaなどで実行します。
**表10-5 チャンク分割の選択**

| 方式 | AWSで選択する項目 | 主な選択理由 |
|---|---|---|
| 標準 | 原則として追加設定なし | 最初の基準構成。約300 tokenを目安に文境界を考慮 |
| 固定長 | `maxTokens`、`overlapPercentage` | 比較実験を再現しやすい |
| 階層型 | 親チャンク、子チャンク、重なり | 小さく検索し、広い文脈を返す |
| 意味に基づく | `maxTokens`、`bufferSize`、境界しきい値 | 意味の切れ目を優先 |
| No chunking | 分割なし | 上流で検索単位へ分割済み |

| 方式 | 注意点 |
|---|---|
| 標準 | 文書構造に最適とは限らない |
| 固定長 | 意味境界を跨ぐ場合がある |
| 階層型 | 親チャンク統合で返却件数が減る場合がある |
| 意味に基づく | 処理時間・費用と境界品質を評価する |
| No chunking | 出典位置と粒度を上流で保証する |


方式、設定値、変更制約は[IngestionのChunking設定](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-data-source-customize-ingestion.html)と[Chunkingの動作](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html)を参照します（確認日：2026年9月5日）。

## Bedrock 埋め込みモデル

### 1. RAGでの目的

文書チャンクと質問を同じベクトル空間へ変換し、第4章のDense 検索を可能にします。

### 2. 四工程・二層の位置

Batch Layerで文書チャンクを埋め込みし、Real-time Layerの検索前処理で質問を埋め込みします。
同じインデックスを検索する両側で互換なモデル、次元数、ベクトル型を使います。

### 3. AWSリソース

Bedrock 埋め込みモデル、モデルアクセスまたは推論プロファイル、Knowledge Baseの埋め込み設定、ベクトルストアのインデックスのスキーマを使います。
Managed KBのAWS管理の埋め込みはモデルリソースの選択が隠蔽されます。

### 4. 接続先

Knowledge Basesの取り込みとRetrieveから呼び、出力ベクトルをS3 VectorsまたはOpenSearch Serverlessへ保存・照会します。
Knowledge Basesを使わない場合はBedrock 実行環境のモデル inferenceをアプリケーションから呼びます。

### 5. AWSが管理する範囲

AWSはモデルホスティング、推論Endpoint、基盤拡張、モデル固有の推論APIを管理します。
Customer-managed KBでは選択モデルをKnowledge Basesが呼び、Managed KBの既定ではAWS管理の埋め込みをAWSが選択・運用します。

### 6. 利用者が選択する項目

Customer-managed KBではモデル、言語、次元数、floatまたはbinaryのベクトル型、処理量方式を選びます。
日本語、日本語・英語混在、Cross-language、分野用語を候補モデルで比較します。
次元数は品質だけでなく保存容量、検索記憶管理、費用、応答時間へ影響します。

### 7. 評価する項目

同じ正解データでRecall@k、MRR、言語別・質問型別Recall、Cross-language 検索、質問の埋め込み応答時間、トークン/要求費用、インデックス容量を比較します。

### 8. 制約

モデルが出す次元数・ベクトル型をストアスキーマと一致させます。
モデルまたは次元数変更時は既存ベクトルと互換ではないため、全チャンクを再埋め込みして新インデックスを作ります。
対応モデル、次元数、ベクトル型、リージョン、クォータは変わり得ます。
Managed KBで独自埋め込みを選ぶ場合はfloat32・1024次元というManaged固有条件にも従います。

### 9. 他の選択肢との使い分け

AWS管理の埋め込みはManaged KBの運用を減らす基準構成です。
モデルを固定して比較可能性を高める、特定言語・分野を改善する、ベクトル型や次元数を選ぶ場合は独自埋め込みまたはCustomer-managed KBを選びます。

### 10. 個別実装が必要になる条件

AWSが対応しない埋め込みモデル、複数埋め込みの並列インデックス、独自前処理、用途別振り分けが必要ならBatch/Real-time両側に同じ変換契約を持つ実装が必要です。
**表10-6 埋め込みモデルの選択観点**

| 選択観点 | 比較内容 | 第7章での確認 |
|---|---|---|
| 言語 | 日本語、英語、混在、Cross-language | 言語別Recall@k |
| 分野 | 型番、略語、専門語、長い節 | 質問型・文書型別Recall |
| 次元数 | 表現力と保存容量・記憶管理のTrade-off | 品質、インデックス容量、応答時間、費用 |
| ベクトル型 | floatの精度とbinaryの容量・対応ストア | Recall低下と資源削減の比較 |
| 処理量 | Batch取り込みと検索文推論 | 同期時間、P95 応答時間、スロットリング |
| 変更影響 | 再埋め込み・新インデックス・切り戻し | 旧新インデックスの同条件回帰評価 |


対応モデル、次元数、ベクトル型は[Knowledge Bases対応ModelとStore](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-supported.html)、埋め込みとベクトル検索の関係は[Knowledge Basesの仕組み](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-how-it-works.html)を参照します（確認日：2026年9月5日）。

## Amazon S3 Vectors

### 1. RAGでの目的

大量のベクトルとメタデータを保存し、意味検索とメタデータ Filteringで近い根拠候補を取得します。
原文用S3 バケットとは別のベクトルストアです。

### 2. 四工程・二層の位置

Batch Layerでは埋め込みベクトルの保存・索引、Real-time Layerの検索工程では質問ベクトルの近傍検索を担います。

### 3. AWSリソース

ベクトルバケット、ベクトルインデックス、ベクトルキー、ベクトルデータ、メタデータ、ベクトルバケットポリシー、任意のKMS キーを使います。
Customer-managed Knowledge Baseから使う場合はベクトルバケットとインデックスをKnowledge Baseへ関連づけます。

### 4. 接続先

Knowledge BasesがBedrock 埋め込みモデルの出力をベクトルインデックスへ書き、`Retrieve`から照会します。
Knowledge Basesを使わない構成ではアプリケーションが`QueryVectors`を直接呼びます。
必要に応じてOpenSearchとの連携・移行経路を設計します。

### 5. AWSが管理する範囲

AWSはベクトルのDurable 保存容量、インデックスの最適化、意味に基づく similarity query、メタデータフィルター、基盤拡張、ベクトルバケットのブロック Public Accessを管理します。

### 6. 利用者が選択する項目

インデックス名、次元数、距離指標、filterableとnon-filterable メタデータ、ベクトルキー、`topK`、フィルター、返却メタデータを選びます。
Knowledge Bases連携ではメタデータのスキーマを1Vector当たりの上限内に収めます。

### 7. 評価する項目

Recall@k、フィルター適用後Recall、返却件数、検索文応答時間、検索頻度別の性能、ベクトル・メタデータ容量、PUT・検索文・処理データ量による費用、同期時間を評価します。

### 8. 制約

意味検索中心で、Knowledge Bases連携ではハイブリッド検索に対応しません。
インデックスの次元数は1〜4096、距離指標は作成時に選び、次元数、指標、non-filterable メタデータ keyは後から変更できないため新インデックスが必要です。
Knowledge Bases連携ではfloat ベクトルのみ、独自メタデータは1Vector当たり1KB・35 keyまでです。
大きな階層型親チャンクや豊富なメタデータは上限へ影響します。
検索頻度とインデックス状態により応答時間特性が変わります。

### 9. 他の選択肢との使い分け

意味検索で要件を満たし、メタデータ制約内で、大量ベクトルを低い運用負担と費用特性で保持したい場合に比較します。
キーワード、型番、条文番号、柔軟な全文・ハイブリッド検索、高QPS・低応答時間、集計やFacetingが重要ならOpenSearch Serverlessを比較します。

### 10. 個別実装が必要になる条件

キーワード検索との独自統合、複数ベクトルインデックスのRRF、スコア正規化、メタデータ上限を超える外部参照、独自ACL変換が必要ならアプリケーション処理を追加します。

S3 Vectorsの役割は[Amazon S3 Vectors](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors.html)、インデックス不変項目は[Vector Index](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-indexes.html)、フィルターは[Metadata filtering](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-metadata-filtering.html)、Knowledge Bases固有上限は[Knowledge Base用Vector Storeの前提条件](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-setup.html)を参照します（確認日：2026年9月5日）。

```text
Amazon S3（原文）
    │ Data Source
    ▼
Customer-managed Knowledge Base
    ├─ Parser / Chunking
    ├─ Bedrock Embedding Model
    └─ Vector write / Retrieve
            │
            ▼
      S3 Vector Bucket
        └─ Vector Index ── Semantic Search + Metadata Filter
```

**図10-4 Customer-managed Knowledge BaseとS3 Vectorsの構成**

## Amazon OpenSearch Serverless

### 1. RAGでの目的

第4章のBM25/キーワード、ベクトル、ハイブリッド検索とメタデータフィルターを一つの検索エンジンで扱い、型番、条文番号、エラーコードなどの語彙一致と意味類似を組み合わせます。

### 2. 四工程・二層の位置

Batch Layerではテキスト・ベクトル・メタデータ項目の索引の作成、Real-time Layerの検索工程ではキーワード、ベクトル、ハイブリッド、フィルターを担います。

### 3. AWSリソース

Serverless コレクション、Collection Group、インデックス、テキスト項目、ベクトル項目、メタデータ項目、検索パイプライン、暗号化ポリシー、ネットワークポリシー、データアクセスポリシー、VPC Endpointを使います。
Knowledge Bases接続ではKnowledge Base サービスロールも必要です。

### 4. 接続先

Customer-managed Knowledge Baseからコレクションとインデックスへ接続するか、アプリケーションからOpenSearch 検索文 APIを直接呼びます。
Knowledge Basesではベクトル・テキスト・メタデータ項目対応付けを指定します。
Private接続ではネットワークポリシーへBedrockのPrivate アクセスとVPC Endpointを設計します。

### 5. AWSが管理する範囲

AWSはCluster Provisioning、Software、ShardとCapacityの多く、索引の作成/検索 OCUの拡張、コレクション暗号化、Service availabilityを管理します。
利用者はNodeを直接管理しません。

### 6. 利用者が選択する項目

コレクション type、Collection Groupの容量範囲、インデックスのスキーマ、解析器、キーワード/テキスト対応付け、ベクトル次元数・エンジン・距離の種類、検索検索文、ハイブリッド検索パイプラインの正規化・結合、フィルター 項目、暗号化キー、ネットワークポリシー、データアクセスポリシーを選びます。
低レベルのHNSW、Faiss、Lucene設定は、必要な場合だけCustomer-managed インデックスの補足として扱います。

### 7. 評価する項目

BM25、ベクトル、ハイブリッドごとのRecall@k・MRR・nDCG、型番・完全一致の成功率、フィルター精度、索引の作成/検索 P95 応答時間、OCU、保存容量、スロットリング、規模調整-to-zero後のCold start、検索頻度別費用を評価します。

### 8. 制約

コレクション typeは作成後に変更できません。
コレクションは暗号化され、暗号化ポリシー、ネットワークポリシー、データアクセスポリシーを正しく組み合わせる必要があります。
IAM許可だけではデータアクセスポリシーの代わりになりません。
Knowledge Basesから`HYBRID`を使うには対応するフィルターに使えるテキスト項目が必要です。
規模調整-to-zeroを使う構成はIdle後の最初の検索文に追加応答時間が生じます。

### 9. 他の選択肢との使い分け

キーワードとベクトルの併用、柔軟なメタデータ、解析器、検索分析、高い検索頻度や安定した低応答時間が重要なら比較します。
意味検索中心で検索頻度が比較的低く、S3 Vectorsのメタデータ制約内で運用対象と費用を抑えたいならS3 Vectorsを比較します。
どちらも常に標準とはしません。

### 10. 個別実装が必要になる条件

複数コレクション・インデックスの振り分け、独自RRF、業務別スコア統合、複雑なACL変換、候補の採否理由記録が必要なら、OpenSearchの外側にアプリケーション処理を置きます。

OpenSearch Serverlessの管理範囲は[Serverlessの概要](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless.html)、コレクション typeは[Serverless collections](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-overview.html)、ハイブリッド検索は[Neural・Hybrid Searchの設定](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-configure-neural-search.html)、セキュリティポリシーは[Serverless data access control](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-security.html)を参照します（確認日：2026年9月5日）。

## S3 VectorsとOpenSearch Serverlessを選ぶ
**表10-7 S3 VectorsとOpenSearch Serverlessの比較**

| 比較軸 | S3 Vectors | OpenSearch Serverless |
|---|---|---|
| 主な検索要件 | 意味検索 | キーワード、ベクトル、ハイブリッド、フィルター |
| キーワード・完全一致 | Knowledge Bases連携では担当しない | BM25、解析器、項目 queryで対応 |
| メタデータ | Knowledge Bases連携は1Vector当たり1KB・35 key | インデックス対応付けと検索文で柔軟に設計 |
| ベクトル型 | Knowledge Bases連携はfloat | 構成によりfloat・binaryを選択可能 |
| 検索頻度・応答時間 | 低頻度を含む大規模意味に基づく用途を比較 | 高い検索頻度、低応答時間要求を比較 |
| 費用の主な費用の要因 | ベクトルの保存、PUT、検索文、処理データ量 | OCU時間、保存容量、データ transfer |
| 運用範囲 | ベクトルバケット・インデックス・メタデータ設計 | コレクション、インデックス、解析器、セキュリティポリシー、OCU設計 |
| 向く例 | FAQ、意味類似中心、大量ベクトル保管 | 型番、条文、エラーコード、全文・ハイブリッド検索 |
| 再作成要因 | 次元数、指標、non-filterable key | コレクション type、互換性のないMappingやベクトル設定 |


費用は単価ではなく、検索頻度、保存量、メタデータ量、検索文で処理するデータ量、必要な待機Capacityでモデル化します。
[S3 Vectors pricing](https://aws.amazon.com/s3/pricing/)と[OpenSearch Service pricing](https://aws.amazon.com/opensearch-service/pricing/)を使い、第8章の利用量想定を同じ期間・同じ検索件数へ換算します（確認日：2026年9月5日）。
