# Batch Layerを構成する

Batch Layerは、質問を受ける前に、信頼できる原文を検索可能な索引へ変換します。第3章の文書解析、Chunking、Embedding、索引作成をAWSリソースへ対応づけます。各設定の良し悪しは単体では決まらないため、原文、Chunk、Vector、Indexの版を関連づけ、第7章の同じ評価データで比較します。

```text
原文・Metadata
    │
    ▼
Amazon S3 / Data Source
    │ Ingestion Job・増分同期
    ▼
Parser ──→ Chunking ──→ Bedrock Embedding Model
                              │
                              ▼
                 S3 Vectors / OpenSearch Serverless
                              │
                              ▼
                 検証済みIndexをReal-time Layerへ公開
```

**図10-6 Batch Layerの取り込みフロー**

## Amazon S3――原文とData Source

**1. RAGでの目的**

検索結果から戻れる原文・正本を保持し、Knowledge Baseへ取り込む対象範囲をBucketとPrefixで定義します。S3 Vectorsとは別の役割です。

**2. 四工程・二層の位置**

Batch Layerの文書側検索前処理の入口です。生成時の引用先としてReal-time LayerからLocationを参照することはありますが、S3自体が検索や生成を行うわけではありません。

**3. AWSリソース**

General purpose S3 Bucket、Object、Prefix、任意のVersioning、Lifecycle、Object Tag、Metadata sidecar、Bucket Policy、KMS Keyを使います。Knowledge Base側にはS3 Data Sourceを作ります。

**4. 接続先**

S3 Data SourceをManagedまたはCustomer-managed Knowledge Baseへ接続します。BucketはKnowledge Baseと同じRegionに置き、service roleへ読み取り権限と、必要ならKMS復号権限を与えます。原文更新後はIngestion Jobで同期します。

**5. AWSが管理する範囲**

S3はObject Storageの耐久性、可用性、暗号化機能、Versioning、Lifecycleを提供します。Knowledge Basesは同期時に追加・変更・削除を検出し、対応する取り込み処理を実行します。

**6. 利用者が選択する項目**

Bucket・Prefixの境界、原文形式、Object Key、Versioning、暗号化Key、保持期間、削除方針、文書所有者、公開状態、更新日、版、出典URLなどのMetadataを選びます。Metadata sidecarを使う場合は埋め込み対象に含めるFieldとFilter専用Fieldも選びます。

**7. 評価する項目**

対象文書の網羅率、誤ったPrefix混入、正本と索引の一致、更新・削除反映時間、Metadata欠損、古い版の残存、引用Locationの再現性、Storage・Request・転送費を評価します。

**8. 制約**

Knowledge BasesのS3 Data SourceはGeneral purpose Bucketを使用し、同じRegionに置きます。Metadata sidecarは対応形式とサイズ上限に従います。S3を正本にした構成でKnowledge Baseへ直接投入した変更はS3へ逆反映されず、次回同期で上書きされる可能性があります。したがって、更新経路を一つに定めます。

**9. 他の選択肢との使い分け**

原文をS3で統制できるなら、版、暗号化、Lifecycle、再取り込みを設計しやすい構成です。SharePointなどを正本にするManaged Knowledge Baseでは、S3への複製が必須とは限りません。S3 Vectorsは原文の代替ではなく、検索用Vector Storeとして別に選びます。

**10. 個別実装が必要になる条件**

外部システムからの収集、承認Workflow、正本判定、文書信頼度付与、ウイルス検査、独自Data分類が必要ならBatch LayerのLambda、ECS、EKS、Step Functionsなどへ配置します。

S3 Data Sourceの対象、Metadata、増分同期は[S3 Data Source connector](https://docs.aws.amazon.com/bedrock/latest/userguide/s3-data-source-connector.html)、直接投入との整合は[Knowledge Baseへの直接取り込み](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-direct-ingestion.html)を参照します（確認日：2026年8月22日）。

## Parser

**1. RAGでの目的**

PDF、Office文書、HTMLなどから、検索単位を作れるText、表、図、Layout情報を抽出します。

**2. 四工程・二層の位置**

Batch Layerの文書側検索前処理で、Chunkingより前に置きます。

**3. AWSリソース**

Knowledge Base Data SourceのParsing Configuration、Default parser、Bedrock Data Automation（BDA）parser、Foundation Model parser、任意のCustom transformation Lambdaを使います。

**4. 接続先**

Data Sourceから読み取った文書をParserへ渡し、抽出結果をChunkingへ渡します。Custom transformationはIngestion PipelineからLambdaを呼びます。

**5. AWSが管理する範囲**

AWSは選択したParserの実行、Bedrock ModelまたはBDAの推論基盤、Knowledge Basesへの結果受け渡しを管理します。高度なParserが失敗した場合、対応する構成ではDefault parserへFallbackすることがあります。

**6. 利用者が選択する項目**

文書のLayout、表、図、画像の必要性からParserを選びます。Foundation Model parserでは対応ModelとParsing Prompt、BDAではOutputやMultimodalの要件、Custom transformationではLambdaと出力Schemaを選びます。

**7. 評価する項目**

見出し階層、表の行列対応、ページ位置、画像内Text、脚注、文字化け、読み順、抽出漏れを第3章の抽出評価と検索Recallで確認します。ページ当たりまたはToken当たり費用、同期Latencyも比較します。

**8. 制約**

Default parserはText中心で、複雑な表・図・画像の意味を十分に保持しない場合があります。高度なParserには対応形式、Region、Model、Quota、追加費用があります。Data SourceのParsing Configuration変更は再取り込みと比較評価を伴います。

**9. 他の選択肢との使い分け**

Text主体ならDefaultをBaselineにします。表、図、段組み、画像が回答根拠になるときだけBDAまたはFoundation Model parserを比較します。業務固有のHeader、帳票、OCR後補正が必須ならCustom transformationを比較します。

**10. 個別実装が必要になる条件**

独自OCR、表の業務Schema化、帳票分類、機密情報の事前除去、独自の正規化が必要ならCustom transformation Lambdaまたは上流のBatch処理へ置きます。

| 選択肢 | AWSが行うこと | 利用者が選ぶ主な項目 | 選択条件 | 第7章で評価する項目 |
|---|---|---|---|---|
| Default parser | 対応文書からTextを抽出 | 原則追加設定なし | Text主体のBaseline | Text欠落、読み順、検索Recall |
| BDA parser | Layout、表、図、画像を含む解析 | BDA利用、出力要件 | Visual情報が根拠になる | 表・図の忠実性、費用、Latency |
| Foundation Model parser | 指定Modelで高度な解析 | Model、Parsing Prompt | 文書構造に合わせた抽出 | Domain文書の抽出品質、Token費用 |
| Custom transformation | LambdaをIngestionから実行 | Function、出力Schema | 業務固有の変換が必須 | Schema適合、失敗率、再現性 |

**表10-4 Parserの選択**

Parserごとの機能と課金単位は[高度なParsing](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-advanced-parsing.html)、Custom transformationは[Knowledge BasesのCustom transformation](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-custom-transformation.html)を参照します（確認日：2026年8月22日）。

## Chunking

**1. RAGでの目的**

Parserの出力を、検索時に見つけやすく、生成時に意味を解釈できる単位へ分けます。第3章の「検索単位」と「読解単位」をAWS設定へ対応づけます。

**2. 四工程・二層の位置**

Batch Layerの文書側検索前処理で、Parsingの後、Embeddingの前に置きます。

**3. AWSリソース**

Knowledge Base Data SourceのChunking Configurationを使います。Customer-managed KBではDefault、Fixed-size、Hierarchical、Semantic、No chunkingを選べます。Managed KBではサービスが公開するBuilt-in/DefaultやFixed-sizeなど、その時点で利用可能な方式から選びます。

**4. 接続先**

Parser出力を受け、各ChunkをEmbedding Modelへ渡します。HierarchicalではChildをVector検索し、返却時に広いParentへ置換します。No chunkingでは上流で検索単位に分割済みのObjectを渡します。

**5. AWSが管理する範囲**

AWSは方式に従う分割、Overlap、Chunkと原文Locationの関連づけ、HierarchicalのChild検索・Parent返却、Semanticの意味境界計算を実行します。

**6. 利用者が選択する項目**

`maxTokens`、`overlapPercentage`、Parent/ChildのToken数、Semanticの`bufferSize`と境界Thresholdを選びます。値は第3章の仮説を比較するBaselineであり、文書形式と質問で評価して調整します。

**7. 評価する項目**

Chunk単体の意味完結性、Boundary跨ぎ、Recall@k、Parent返却後のPrecision、Context Token量、同一文書への偏り、Citation粒度、Storage・Embedding量を評価します。

**8. 制約**

Data Source接続後にChunking Strategyを変更できない構成があるため、比較と変更は新しいData SourceまたはIndexを前提にします。Hierarchicalは複数Childが同じParentへ統合されるため、返却件数が`numberOfResults`より少なくなることがあります。No chunkingではページ番号など一部のLocation情報を失うことがあります。

**9. 他の選択肢との使い分け**

Defaultを最初のBaseline、Fixed-sizeを再現可能な比較対象、Semanticを意味境界が重要な文書、Hierarchicalを小さく検索して広く読ませる文書、No chunkingを上流分割済み文書に使います。

**10. 個別実装が必要になる条件**

Recursive、Table-aware、見出し・条文・会話Turn単位、独自Parent-child、特殊なOverlapが必要ならCustom transformationを使います。詳細ロジックは第3章で定義し、Batch LayerのLambdaなどで実行します。

| 方式 | AWSで選択する項目 | 主な選択理由 | 注意点 |
|---|---|---|---|
| Default | 原則として追加設定なし | 最初のBaseline。約300 tokenを目安に文境界を考慮 | 文書構造に最適とは限らない |
| Fixed-size | `maxTokens`、`overlapPercentage` | 比較実験を再現しやすい | 意味境界を跨ぐ場合がある |
| Hierarchical | Parent、Child、Overlap | 小さく検索し、広い文脈を返す | Parent統合で返却件数が減る場合がある |
| Semantic | `maxTokens`、`bufferSize`、境界Threshold | 意味の切れ目を優先 | 処理時間・費用と境界品質を評価する |
| No chunking | 分割なし | 上流で検索単位へ分割済み | Locationと粒度を上流で保証する |

**表10-5 Chunkingの選択**

方式、設定値、変更制約は[IngestionのChunking設定](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-data-source-customize-ingestion.html)と[Chunkingの動作](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html)を参照します（確認日：2026年8月22日）。

## Bedrock Embedding Model

**1. RAGでの目的**

文書Chunkと質問を同じVector空間へ変換し、第4章のDense Retrievalを可能にします。

**2. 四工程・二層の位置**

Batch Layerで文書ChunkをEmbeddingし、Real-time Layerの検索前処理で質問をEmbeddingします。同じIndexを検索する両側で互換なModel、Dimension、Vector Typeを使います。

**3. AWSリソース**

Bedrock Embedding Model、Model accessまたはInference Profile、Knowledge BaseのEmbedding Configuration、Vector StoreのIndex schemaを使います。Managed KBのservice-managed EmbeddingはModelリソースの選択が隠蔽されます。

**4. 接続先**

Knowledge BasesのIngestionとRetrieveから呼び、出力VectorをS3 VectorsまたはOpenSearch Serverlessへ保存・照会します。Knowledge Basesを使わない場合はBedrock RuntimeのModel inferenceをアプリケーションから呼びます。

**5. AWSが管理する範囲**

AWSはModel hosting、推論Endpoint、基盤拡張、Model固有の推論APIを管理します。Customer-managed KBでは選択ModelをKnowledge Basesが呼び、Managed KBの既定ではservice-managed EmbeddingをAWSが選択・運用します。

**6. 利用者が選択する項目**

Customer-managed KBではModel、言語、Dimension、floatまたはbinaryのVector Type、Throughput方式を選びます。日本語、日本語・英語混在、Cross-language、Domain用語を候補Modelで比較します。Dimensionは品質だけでなくStorage、検索Memory、費用、Latencyへ影響します。

**7. 評価する項目**

同じ正解データでRecall@k、MRR、言語別・質問型別Recall、Cross-language Retrieval、Query Embedding Latency、Token/Request費用、Index容量を比較します。

**8. 制約**

Modelが出すDimension・Vector TypeをStore schemaと一致させます。ModelまたはDimension変更時は既存Vectorと互換ではないため、全Chunkを再Embeddingして新Indexを作ります。対応Model、Dimension、Vector Type、Region、Quotaは変わり得ます。Managed KBでcustom Embeddingを選ぶ場合はfloat32・1024次元というManaged固有条件にも従います。

**9. 他の選択肢との使い分け**

service-managed EmbeddingはManaged KBの運用を減らすBaselineです。Modelを固定して比較可能性を高める、特定言語・Domainを改善する、Vector TypeやDimensionを選ぶ場合はcustom EmbeddingまたはCustomer-managed KBを選びます。

**10. 個別実装が必要になる条件**

AWSが対応しないEmbedding Model、複数Embeddingの並列Index、独自前処理、用途別Routingが必要ならBatch/Real-time両側に同じ変換契約を持つ実装が必要です。

| 選択観点 | 比較内容 | 第7章での確認 |
|---|---|---|
| 言語 | 日本語、英語、混在、Cross-language | 言語別Recall@k |
| Domain | 型番、略語、専門語、長い節 | 質問型・Document型別Recall |
| Dimension | 表現力とStorage・MemoryのTrade-off | 品質、Index容量、Latency、費用 |
| Vector Type | floatの精度とbinaryの容量・対応Store | Recall低下と資源削減の比較 |
| Throughput | Batch取り込みとQuery推論 | 同期時間、P95 Latency、Throttle |
| 変更影響 | 再Embedding・新Index・Rollback | 旧新Indexの同条件回帰評価 |

**表10-6 Embedding Modelの選択観点**

対応Model、Dimension、Vector Typeは[Knowledge Bases対応ModelとStore](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-supported.html)、EmbeddingとVector検索の関係は[Knowledge Basesの仕組み](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-how-it-works.html)を参照します（確認日：2026年8月22日）。

## Amazon S3 Vectors

**1. RAGでの目的**

大量のVectorとMetadataを保存し、Semantic SearchとMetadata Filteringで近い根拠候補を取得します。原文用S3 Bucketとは別のVector Storeです。

**2. 四工程・二層の位置**

Batch LayerではEmbedding Vectorの保存・索引、Real-time Layerの検索工程ではQuery Vectorの近傍検索を担います。

**3. AWSリソース**

Vector Bucket、Vector Index、Vector Key、Vector Data、Metadata、Vector Bucket Policy、任意のKMS Keyを使います。Customer-managed Knowledge Baseから使う場合はVector BucketとIndexをKnowledge Baseへ関連づけます。

**4. 接続先**

Knowledge BasesがBedrock Embedding Modelの出力をVector Indexへ書き、`Retrieve`から照会します。Knowledge Basesを使わない構成ではアプリケーションが`QueryVectors`を直接呼びます。必要に応じてOpenSearchとの連携・移行経路を設計します。

**5. AWSが管理する範囲**

AWSはVectorのDurable Storage、Indexの最適化、Semantic similarity query、Metadata Filter、基盤拡張、Vector BucketのBlock Public Accessを管理します。

**6. 利用者が選択する項目**

Index名、Dimension、Distance Metric、filterableとnon-filterable Metadata、Vector Key、`topK`、Filter、返却Metadataを選びます。Knowledge Bases連携ではMetadata schemaを1Vector当たりの上限内に収めます。

**7. 評価する項目**

Recall@k、Filter適用後Recall、返却件数、Query Latency、検索頻度別の性能、Vector・Metadata容量、PUT・Query・処理データ量による費用、同期時間を評価します。

**8. 制約**

Semantic Search中心で、Knowledge Bases連携ではHybrid Searchに対応しません。IndexのDimensionは1〜4096、Distance Metricは作成時に選び、Dimension、Metric、non-filterable Metadata keyは後から変更できないため新Indexが必要です。Knowledge Bases連携ではfloat Vectorのみ、custom Metadataは1Vector当たり1KB・35 keyまでです。大きなHierarchical Parentや豊富なMetadataは上限へ影響します。検索頻度とIndex状態によりLatency特性が変わります。

**9. 他の選択肢との使い分け**

Semantic Searchで要件を満たし、Metadata制約内で、大量Vectorを低い運用負担と費用特性で保持したい場合に比較します。Keyword、型番、条文番号、柔軟な全文・Hybrid Search、高QPS・低Latency、集計やFacetingが重要ならOpenSearch Serverlessを比較します。

**10. 個別実装が必要になる条件**

Keyword検索との独自Fusion、複数Vector IndexのRRF、Score正規化、Metadata上限を超える外部参照、独自ACL変換が必要ならアプリケーション処理を追加します。

S3 Vectorsの役割は[Amazon S3 Vectors](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors.html)、Index不変項目は[Vector Index](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-indexes.html)、Filterは[Metadata filtering](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-metadata-filtering.html)、Knowledge Bases固有上限は[Knowledge Base用Vector Storeの前提条件](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-setup.html)を参照します（確認日：2026年8月22日）。

```text
Amazon S3（原文）
    │ Data Source
    ▼
Customer-managed Knowledge Base
    ├─ Parser / Chunking
    ├─ Bedrock Embedding Model
    └─ Vector write / Retrieve
            │
            ▼
      S3 Vector Bucket
        └─ Vector Index ── Semantic Search + Metadata Filter
```

## Amazon OpenSearch Serverless

**1. RAGでの目的**

第4章のBM25/Keyword、Vector、Hybrid RetrievalとMetadata Filterを一つの検索エンジンで扱い、型番、条文番号、エラーコードなどの語彙一致と意味類似を組み合わせます。

**2. 四工程・二層の位置**

Batch LayerではText・Vector・Metadata fieldのIndexing、Real-time Layerの検索工程ではKeyword、Vector、Hybrid、Filterを担います。

**3. AWSリソース**

Serverless Collection、Collection Group、Index、Text field、Vector field、Metadata field、Search Pipeline、Encryption Policy、Network Policy、Data Access Policy、VPC Endpointを使います。Knowledge Bases接続ではKnowledge Base service roleも必要です。

**4. 接続先**

Customer-managed Knowledge BaseからCollectionとIndexへ接続するか、アプリケーションからOpenSearch Query APIを直接呼びます。Knowledge BasesではVector・Text・Metadata field mappingを指定します。Private接続ではNetwork PolicyへBedrockのPrivate accessとVPC Endpointを設計します。

**5. AWSが管理する範囲**

AWSはCluster Provisioning、Software、ShardとCapacityの多く、Indexing/Search OCUの拡張、Collection暗号化、Service availabilityを管理します。利用者はNodeを直接管理しません。

**6. 利用者が選択する項目**

Collection type、Collection Groupの容量範囲、Index schema、Analyzer、Keyword/Text mapping、Vector Dimension・Engine・Space type、Search Query、Hybrid Search Pipelineの正規化・結合、Filter field、Encryption Key、Network Policy、Data Access Policyを選びます。低レベルのHNSW、Faiss、Lucene設定は、必要な場合だけCustomer-managed Indexの補足として扱います。

**7. 評価する項目**

BM25、Vector、HybridごとのRecall@k・MRR・nDCG、型番・完全一致の成功率、Filter精度、Indexing/Search P95 Latency、OCU、Storage、Throttle、Scale-to-zero後のCold start、検索頻度別費用を評価します。

**8. 制約**

Collection typeは作成後に変更できません。Collectionは暗号化され、Encryption Policy、Network Policy、Data Access Policyを正しく組み合わせる必要があります。IAM許可だけではData Access Policyの代わりになりません。Knowledge Basesから`HYBRID`を使うには対応するfilterable text fieldが必要です。Scale-to-zeroを使う構成はIdle後の最初のQueryに追加Latencyが生じます。

**9. 他の選択肢との使い分け**

KeywordとVectorの併用、柔軟なMetadata、Analyzer、検索分析、高い検索頻度や安定した低Latencyが重要なら比較します。Semantic Search中心で検索頻度が比較的低く、S3 VectorsのMetadata制約内で運用対象と費用を抑えたいならS3 Vectorsを比較します。どちらも常に標準とはしません。

**10. 個別実装が必要になる条件**

複数Collection・IndexのRouting、独自RRF、業務別Score統合、複雑なACL変換、候補の採否理由記録が必要なら、OpenSearchの外側にアプリケーション処理を置きます。

OpenSearch Serverlessの管理範囲は[Serverlessの概要](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless.html)、Collection typeは[Serverless collections](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-overview.html)、Hybrid Searchは[Neural・Hybrid Searchの設定](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-configure-neural-search.html)、Security Policyは[Serverless data access control](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-security.html)を参照します（確認日：2026年8月22日）。

```text
Amazon S3（原文）
    │ Data Source
    ▼
Customer-managed Knowledge Base
    ├─ Parser / Chunking
    ├─ Bedrock Embedding Model
    └─ Index write / Retrieve
            │
            ▼
OpenSearch Serverless Collection
    └─ Index: Text field + Vector field + Metadata field
             ├─ Keyword
             ├─ Vector
             ├─ Hybrid
             └─ Filter
```

**図10-4 Customer-managed Knowledge BaseとOpenSearch Serverlessの構成**

## S3 VectorsとOpenSearch Serverlessを選ぶ

| 比較軸 | S3 Vectors | OpenSearch Serverless |
|---|---|---|
| 主な検索要件 | Semantic Search | Keyword、Vector、Hybrid、Filter |
| Keyword・完全一致 | Knowledge Bases連携では担当しない | BM25、Analyzer、Field queryで対応 |
| Metadata | Knowledge Bases連携は1Vector当たり1KB・35 key | Index mappingとQueryで柔軟に設計 |
| Vector Type | Knowledge Bases連携はfloat | 構成によりfloat・binaryを選択可能 |
| 検索頻度・Latency | 低頻度を含む大規模Semantic用途を比較 | 高い検索頻度、低Latency要求を比較 |
| 費用の主なDriver | Vector Storage、PUT、Query、処理データ量 | OCU時間、Storage、Data transfer |
| 運用範囲 | Vector Bucket・Index・Metadata設計 | Collection、Index、Analyzer、Security Policy、OCU設計 |
| 向く例 | FAQ、意味類似中心、大量Vector保管 | 型番、条文、Error code、全文・Hybrid検索 |
| 再作成要因 | Dimension、Metric、non-filterable key | Collection type、互換性のないMappingやVector設定 |
