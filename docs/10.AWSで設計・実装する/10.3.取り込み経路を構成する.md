# 10.3. 取り込みとchunkingを設定する

## 10.3.1. Parserを資料の構造で選ぶ

標準経路は、`S3 → Knowledge Bases data source sync → parser → chunking → embedding → vector store`です。text中心のPDF、HTML、Office文書はdefault parserを基準にします。表、図、複雑なlayoutを検索対象にする場合は、[高度な文書解析](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-advanced-parsing.html)のBedrock Data Automationまたはfoundation model parserを比較します。

高度なparserを選ぶと、そのdata source内のすべてのPDFへ適用され、追加費用が発生します。資料群をtext中心と複雑layoutに分け、parse成功率、表セルの保持、見出し階層、ページ位置、1ページ当たり費用を同じ文書で比較します。標準処理で出典位置や業務上の検索単位を保てない場合は、[custom transformation Lambda](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-custom-transformation.html)でchunkとmetadataを返します。

## 10.3.2. Chunkingの初期値を置く

[Knowledge Basesのchunking](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html)方式はdefault、fixed-size、hierarchical、semantic、no chunkingを候補集合とし、選択した方式をdata source単位で固定します。最初はdefaultの約300 tokenを基準にし、想定質問が複数段落を必要とする場合はfixed-sizeの最大tokenを増やします。overlapは0%と10%程度を比較し、境界をまたぐ正解根拠のRecallと重複率で選びます。

semantic chunkingは`maxTokens`、`bufferSize`、`breakpointPercentileThreshold`を設定します。API上の範囲は、`maxTokens=1..8192`、`bufferSize=0..1`、threshold `50..99`です。初期比較では`maxTokens=300`、`bufferSize=1`、threshold `90`を置き、default chunkingに対するRecall、平均chunk長、chunk数、追加費用を測ります。

hierarchical chunkingは、短いchildで検索し、広いparentを回答へ返したい場合に使います。親子関係はmetadataを増やすため、S3 Vectorsでは1 KBのcustom metadata上限を超えないことを先に確認します。事前に独自分割したファイルをそのまま登録するときだけno chunkingを選びます。

## 10.3.3. Metadataと同期結果を検査する

S3 data sourceでは、文書と同名の`.metadata.json` sidecarへ、`document_id`、`version`、`valid_from_epoch`、`valid_to_epoch`、`status`、`source_uri`、検索時のfilter属性を持たせます。型は`STRING`、`NUMBER`、`BOOLEAN`、`STRING_LIST`を用途に合わせます。日時を範囲filterへ使う場合は、`valid_from_epoch: 1785164400`のような**UTC（Coordinated Universal Time、協定世界時）**のUnix epoch秒を`NUMBER`で保存し、日時文字列よりも数値として確実に比較します。

同期APIの成功だけで公開しません。対象document数、生成chunk数、parse失敗、metadata欠損、削除反映、固定queryのRecallを記録し、[Publish前ゲート](../3.回答に使う資料を準備する/3.8.Publish前ゲート.md)と[Pre-retrieval・Batch評価](../7.品質を評価し改善する/7.3.Pre-retrieval・Batch評価.md)の基準を満たしたindexだけを検索先にします。
