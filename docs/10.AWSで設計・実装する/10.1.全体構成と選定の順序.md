# 全体構成と選定の順序

AWSリソースを選ぶ前に、質問より前に作るものと、質問ごとに動かすものを分けます。四工程と二層は一対一ではありません。文書解析、Chunking、Embedding、索引作成はBatch Layerに置き、質問理解、検索、検索後処理、生成はReal-time Layerに置きます。

| 区分 | 役割 | 主なAWS機能 |
|---|---|---|
| Batch Layer | 質問前に索引を作る | S3、Knowledge Bases、Embedding、Vector Store |
| Real-time Layer | 質問ごとに根拠を探し、回答する | Knowledge Bases、Rerank、生成モデル、アプリ |
| 管理面 | 両層を安全に運用する | IAM、KMS、CloudWatch、評価、Budgets |

![四工程と二層にAWSサービスとリソースを対応付けた構成図](../../assets/images/v4/44-aws-four-stages-two-layers.png)

**図10-1 四工程・二層とAWSサービスの全体対応**

Batch Layerの成果物は、単なるVectorではありません。原文、Chunk、Metadata、Embedding、索引の版を結び、検証済みの索引としてReal-time Layerへ公開します。Real-time Layerの成果物も、単なる文章ではありません。採用根拠、引用、利用した設定版、回答保留理由を追跡できる回答です。

工程の境界では、最低限次の情報を残します。

- **Batch→Real-time**：原文ID、Chunk ID、Metadata、Embedding版、索引版
- **検索前処理→検索**：原質問、検索Query、Filter、検証済み利用者Context
- **検索→検索後処理**：候補本文、Location、Metadata、Score、Retriever
- **検索後処理→生成**：Evidence、出典、採否理由、矛盾、回答可能性
- **生成→利用者**：回答、引用、保留理由、Model・Prompt・Guardrail版

この境界を残すと、検索品質と生成品質を分けて評価できます。`RetrieveAndGenerate`のように複数工程を一つのAPIへまとめる場合も、評価上の論理境界は残します。[Knowledge Basesの仕組み](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-how-it-works.html)と[Knowledge Basesの評価](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-kb.html)も、この分離に沿って利用します（確認日：2026年8月22日）。

## AWSリソースを選ぶ順序

![運用範囲、文書、検索、生成の順にAWSリソースを選ぶ図](../../assets/images/v4/45-aws-resource-selection.png)

**図10-2 要件からAWSリソースを選ぶ四つの問い**

選択は次の順で行います。

1. **どこまで運用を委ねるか**：検索基盤を隠蔽するならManaged Knowledge Base、EmbeddingとStoreを選ぶならCustomer-managed Knowledge Baseを比較します。
2. **文書に何が含まれるか**：Text中心ならDefault parser、表・図・画像が根拠になるならBDAまたはFoundation Model parserを比較します。
3. **何を検索したいか**：意味類似中心ならS3 Vectors、語彙一致と意味類似を組み合わせるならOpenSearch Serverlessを比較します。
4. **生成と根拠制御をどう分けるか**：標準経路なら`RetrieveAndGenerate`、Evidence Setを制御するなら`Retrieve`＋`Converse`、質問分解と反復検索が必要なら`AgenticRetrieveStream`を比較します。

最初から最も高機能な構成を選びません。管理範囲が大きい構成をBaselineにし、要件を満たせない工程だけを分離します。

## AWSサービスを役割で読む

RAGで使うAWSサービスは、同じ責任を持つ代替製品ではありません。

- **正本を保持する**：Amazon S3は原文、版、Metadataを保持します。検索や回答生成は行いません。
- **取り込みと検索を仲介する**：Bedrock Knowledge Basesは、Data Source、Chunk、出典、Embedding、Vector Store、検索APIを接続します。Knowledge Base自体をVector Databaseとは扱いません。
- **索引を保持して検索する**：S3 VectorsはSemantic Search、OpenSearch ServerlessはKeyword・Vector・Hybrid Searchを担います。
- **推論する**：Bedrock Embedding、Rerank、生成モデル、Guardrailsは、変換、並べ替え、回答生成、入出力Policyをそれぞれ担います。
- **アプリケーションを動かす**：Lambda、ECS、EKSまたはAgentCore Runtimeが、認証済みRequestから検索・生成・Tool実行をつなぎます。

Amazon Bedrockを一つの箱として扱うと、権限、費用、版、評価の境界を失います。Knowledge Bases、Embedding、Rerank、Generation、Guardrailsは、構成図と実行記録でも分けます。[Amazon Bedrock Knowledge Bases](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base.html)、[Rerank](https://docs.aws.amazon.com/bedrock/latest/userguide/rerank.html)、[Guardrails](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html)を参照します（確認日：2026年8月22日）。

## 比較する五つの構成パターン

![要件別に五つのAWS RAGリファレンス構成を比較した図](../../assets/images/v4/54-aws-reference-architectures.png)

**図10-3 要件別のAWS RAGリファレンス構成**

| 構成 | 選ぶ主な条件 | 避ける主な条件 |
|---|---|---|
| A 最大限マネージド | 運用対象を減らしAWS標準へ寄せる | Indexや検索方式を細かく固定したい |
| B Semantic中心 | 意味類似中心でS3 Vectorsの制約内 | Keyword・完全一致が重要 |
| C Hybrid中心 | 型番・条文・固有語と意味類似を併用 | 検索運用を最小化したい |
| D 制御重視 | 独自Fusion、Evidence、ACL、検証が必須 | 標準経路で要件を満たせる |
| E Agentic | Tool、Memory、複数Stepが必要 | 一巡の検索・生成で完了する |

**表10-2 要件別Reference Architectureの選択**

構成Aの根拠は[Managed Knowledge Base](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-build-managed.html)、構成Bは[S3 VectorsとKnowledge Bases](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-bedrock-kb.html)、構成Cは[OpenSearch ServerlessのNeural・Hybrid Search](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-configure-neural-search.html)、構成Eは[AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html)を参照します（確認日：2026年8月22日）。

構成は一度決めて終わりではありません。第7章のEvaluation datasetと第8章の非機能要件を固定し、管理範囲が大きいBaselineから始めます。Keyword、Metadata、Latency、費用、制御性で不足する工程だけを分離し、変更前後を同じ基準で再評価します。
