# Batch Layerを構成する

Batch Layerは、信頼できる原文を検索可能な索引へ変換します。最初にKnowledge Baseの管理範囲を決め、次にS3、Parser、Chunking、Embedding、Vector Storeを順に選びます。

## Knowledge Baseの管理範囲を選ぶ

![Managed Knowledge Base、Customer-managed Knowledge Base、直接構成の管理境界を比較した図](../../assets/images/v4/46-aws-kb-management-boundary.png)

**図10-4 Knowledge Baseの管理範囲**

| 方式 | AWSへ任せる範囲 | 選ぶ主な条件 |
|---|---|---|
| Managed Knowledge Base | 取り込み、保存、索引、Hybrid検索、既定Embedding・Rerank | Vector Store運用を減らす |
| Customer-managed Knowledge Base | 取り込みと検索API | Embedding、Store、Schemaを選ぶ |
| Knowledge Basesなし | AWSのStorage・Search・Model・Runtime | PipelineとEvidenceを全面制御する |

**表10-3 Knowledge Base方式の違い**

### Managed Knowledge Base

Managed Knowledge Baseでは、内部StorageとIndexをAWSが管理します。利用者はVector Storeを作成せず、Data Source、Parser、同期、Filter、ACL awareness、検索件数、Reranking方式を選びます。

検索境界は`Retrieve`または`AgenticRetrieveStream`です。`RetrieveAndGenerate`は使いません。`AgenticRetrieveStream`は質問分解、反復検索、十分性判断を行えますが、単純な質問でもLatencyと費用が増え得るため、必要な質問型に限定して評価します。

内部Indexへ直接アクセスできず、Embedding方式は作成後に変更できません。custom Embeddingを選ぶ場合は、現行仕様のfloat32・1024次元などの条件と、service-managed Rerankingとの組み合わせ制約を確認します。ACL awarenessは認証の代替ではなく、アプリケーションが検証済み`userContext`を渡します。

[Managed Knowledge Baseの概要](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-build-managed.html)、[agentic retrieval](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-agentic-retrieve.html)、[ACL awareness](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-retrieve-acl.html)を参照します（確認日：2026年8月22日）。

### Customer-managed Knowledge Base

Customer-managed Knowledge Baseでは、Knowledge BasesがIngestion Job、Parser、Chunking、Embedding呼び出し、Chunkと出典の対応、Storeへの書き込み、検索APIを管理します。利用者はEmbedding Model、Dimension、Vector Type、Vector Store、Index schema、Metadata、Distance Metricを選びます。

検索には`Retrieve`を使えます。標準的な検索・生成・引用を一体化する場合は`RetrieveAndGenerate`、工程を分離する場合は`Retrieve`＋`Converse`を使います。Embedding Model、Dimension、Vector Typeを変えると既存Vectorと互換ではなくなるため、全Chunkの再Embeddingと新Indexが必要です。

[Customer-managed Knowledge Baseの作成](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-create.html)、[対応StoreとVector Type](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-setup.html)、[Knowledge Baseからの情報取得](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-retrieve.html)を参照します（確認日：2026年8月22日）。

### Knowledge Basesを使わない構成

次の要件が必須なら、アプリケーションからS3 VectorsまたはOpenSearchを直接呼ぶ構成を比較します。

- 複数Index・Retrieverを独自RRFや重み付きFusionで統合する
- 独自Chunk schema、Parent-child、表、節、ACLを完全に制御する
- 候補ごとの採否理由とEvidence Setを必ず記録する
- 検索、圧縮、Packing、生成、Claim検証を個別にTraceする

これはAWSを使わない構成ではありません。S3、S3 Vectors、OpenSearch Serverless、Bedrock Model、Lambda、ECS、EKS、AgentCore Runtimeを部品として使い、結合ロジックを利用者が持つ構成です。

## 原文から公開索引までをつなぐ

![Batch Layerで原文を解析し、分割、埋め込み、索引公開する流れ](../../assets/images/v4/47-aws-batch-ingestion-flow.png)

**図10-5 Batch Layerの取り込みと公開フロー**

### Amazon S3を正本にする

S3は原文、版、取り込み対象、Metadataを保持します。S3 Vectorsとは別の役割です。BucketとPrefixで対象範囲を固定し、Object Key、Versioning、暗号化Key、保持期間、所有者、公開状態、更新日、出典URLを管理します。

原文更新後はIngestion Jobで同期し、追加・変更・削除が索引へ反映されたことを確認します。S3を正本にするなら更新経路を一つに定め、Knowledge Baseへ直接投入した変更と競合させません。[S3 Data Source connector](https://docs.aws.amazon.com/bedrock/latest/userguide/s3-data-source-connector.html)と[Knowledge Baseへの直接取り込み](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-direct-ingestion.html)を参照します（確認日：2026年8月22日）。

### Parserを選ぶ

| 選択肢 | 向く文書 | 確認すること |
|---|---|---|
| Default | Text主体 | 欠落、読み順、検索Recall |
| BDA | 表、図、画像、複雑なLayout | 構造の忠実性、費用、Latency |
| Foundation Model | Domain固有の文書構造 | Model、Prompt、抽出品質 |
| Custom transformation | 独自OCR・正規化・業務Schema | Schema適合、失敗率、再現性 |

**表10-4 Parserの選択**

DefaultをBaselineにし、表・図・画像が回答根拠になる場合だけBDAまたはFoundation Model parserを比較します。独自OCR、帳票分類、機密情報の事前除去が必要ならCustom transformationを上流へ置きます。[高度なParsing](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-advanced-parsing.html)と[Custom transformation](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-custom-transformation.html)を参照します（確認日：2026年8月22日）。

### Chunkingを選ぶ

| 方式 | 選ぶ主な条件 | 注意点 |
|---|---|---|
| Default | 最初のBaseline | 文書構造に最適とは限らない |
| Fixed-size | 再現しやすい比較が必要 | 意味境界をまたぐ場合がある |
| Hierarchical | 小さく検索し、広く読ませる | Parent統合で返却件数が減り得る |
| Semantic | 意味の切れ目が重要 | 処理時間・費用も比較する |
| No chunking | 上流で検索単位へ分割済み | Locationと粒度を上流で保証する |

**表10-5 Chunkingの選択**

比較では、Chunkの意味完結性、Recall@k、Parent返却後のPrecision、Context Token量、Citation粒度、Embedding量を確認します。Strategyを変更できないData Sourceでは、新しいData SourceまたはIndexを作って比較します。[Chunking設定](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-data-source-customize-ingestion.html)と[Chunkingの動作](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-chunking.html)を参照します（確認日：2026年8月22日）。

### Embeddingを選ぶ

文書Chunkと質問は、互換なModel、Dimension、Vector Typeで同じVector空間へ変換します。候補Modelは次の軸で比較します。

- **言語とDomain**：日本語、英語混在、型番、略語、専門語ごとのRecall@k
- **DimensionとVector Type**：品質、Index容量、Memory、Latency、費用
- **Throughput**：同期時間、Query EmbeddingのP95 Latency、Throttle
- **変更影響**：全Chunk再Embedding、新Index、旧新比較、Rollback

Model、Dimension、Vector TypeをStore schemaと一致させます。変更時は既存Indexへ上書きせず、新Indexを作って同じ評価データで比較します。[Knowledge Bases対応ModelとStore](https://docs.aws.amazon.com/bedrock/latest/userguide/knowledge-base-supported.html)を参照します（確認日：2026年8月22日）。

## Vector Storeを選ぶ

![S3 VectorsとOpenSearch Serverlessを検索要件から選び分ける図](../../assets/images/v4/48-aws-vector-store-choice.png)

**図10-6 S3 VectorsとOpenSearch Serverlessの選び分け**

| 比較軸 | S3 Vectors | OpenSearch Serverless |
|---|---|---|
| 検索 | Semantic | Keyword、Vector、Hybrid |
| Metadata | KB連携上限内で設計 | MappingとQueryを柔軟に設計 |
| 運用・費用 | Vector Storage、PUT、Query中心 | OCU、Storage、待機Capacity中心 |
| 向く例 | FAQ、意味類似、大量Vector | 型番、条文、Error code、全文検索 |

**表10-6 Vector Storeの比較**

S3 VectorsはSemantic Search中心で、Knowledge Bases連携ではHybrid Searchに対応しません。Dimension、Distance Metric、non-filterable Metadata keyは作成後に変えられないため、新Indexが必要です。Knowledge Bases連携ではfloat Vector、custom Metadata 1Vector当たり1KB・35 keyなどの上限を確認します。[S3 Vectors](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors.html)と[Metadata filtering](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-metadata-filtering.html)を参照します（確認日：2026年8月22日）。

OpenSearch ServerlessはKeyword、Vector、Hybrid、Filterを一つの検索エンジンで扱えます。Collection type、Index schema、Analyzer、Vector field、Search Pipeline、Encryption Policy、Network Policy、Data Access Policyを利用者が設計します。IAM許可だけではData Access Policyの代わりになりません。[Serverlessの概要](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless.html)、[Hybrid Search](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-configure-neural-search.html)、[Data access control](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-security.html)を参照します（確認日：2026年8月22日）。

費用は単価だけで決めません。同じ保存量、検索件数、Metadata量、Latency要件、評価データで、品質と総費用を比較します。

## 検証済みの索引だけを公開する

公開単位には、Source版、Parser、Chunking、Embedding Model・Dimension・Vector Type、Index schema、Metadata schemaを含めます。新しい索引は第7章のRetrieve-only評価、ACLテスト、Latency、費用の基準を満たしてからReal-time Layerへ切り替えます。旧索引はRollback期間中保持します。
