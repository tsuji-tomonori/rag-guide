# 生成・引用・回答保留を構成する

生成工程の入力は、検索結果の羅列ではなく、質問を支える根拠と出典です。
第6章の根拠に基づく生成、引用、回答保留をBedrock生成モデル、`RetrieveAndGenerate`、`Converse`、Guardrailsへ対応づけます。
引用が返ることと、引用が主張を正しく支えることは分けて評価します。

## Bedrock生成モデル

### 1. RAGでの目的

質問と根拠から、根拠に忠実な回答、要約、表、構造化出力を生成し、根拠が不足する場合は回答を保留します。

### 2. 四工程・二層の位置

Real-time Layerの生成工程に置きます。
質問の書き換えやコンテキスト圧縮へ同じモデルを使う場合は、それぞれ質問側検索前処理・検索後処理として別の呼び出しと版を記録します。

### 3. AWSリソース

Bedrock 基盤モデルまたはカスタムモデル、推論プロファイル、Bedrock Runtimeのエンドポイント、Knowledge Base 生成設定、Prompt managementのプロンプトと版、任意のGuardrailを使います。

### 4. 接続先

Customer-managed KBでは`RetrieveAndGenerate`または`RetrieveAndGenerateStream`から接続できます。
検索と生成を分ける場合、およびManaged KBでは、アプリケーションが`Retrieve`または`AgenticRetrieveStream`の結果を整形し、`Converse`または`ConverseStream`へ接続します。

### 5. AWSが管理する範囲

AWSはモデルホスティング、推論、ストリーミング、実行環境指標を管理します。
`RetrieveAndGenerate`では検索結果のプロンプトへの挿入、生成モデル呼び出し、引用と取得した参照資料の関連情報、セッション IDの管理も提供します。

### 6. 利用者が選択する項目

モデル/推論プロファイル、リージョン、プロンプトテンプレート、システム指示、温度、top-p、出力トークン上限、生成を止める文字列、ストリーミング、セッション保持、回答形式、回答保留条件を選びます。
Knowledge BasesのCustom プロンプトでは検索結果を渡す`$search_results$`が必要です。
引用を返す構成では`$output_format_instructions$`を維持し、プロンプト変更で引用情報を失わないようにします。

### 7. 評価する項目

第7章でFaithfulness、Answer correctness、Completeness、引用 precision、引用 coverage、回答保留のPrecision/Recall、形式適合、応答時間、最初のトークンまでの時間、入力・出力トークン数、回答当たりの費用を評価します。
モデルを大きくする前に検索と根拠の不足を切り分けます。

### 8. 制約

モデルごとに入力の上限、対応API、ストリーミング、ツール use、Structured output、リージョン、処理量、Lifecycleが異なります。
モデルは根拠の正しさ、ACL、引用 correctnessを自動保証しません。
`RetrieveAndGenerate`はManaged KBでは利用しません。
プロンプト、モデル、Inference パラメーター変更は回答分布を変えるため、回帰評価が必要です。

### 9. 他の選択肢との使い分け

Customer-managed KBで標準的な検索・生成・引用を一体化するなら`RetrieveAndGenerate`を基準構成にできます。
根拠集合、独自プロンプト、会話、複数モデル、検証、回答保留を細かく制御するなら`Retrieve`＋`Converse`へ分離します。
Managed KBでは後者、またはManaged専用のエージェント型検索を使います。

### 10. 個別実装が必要になる条件

独自回答スキーマ、複数回答候補の比較、主張単位の検証、引用再検証、業務固有の回答保留、人による確認への引き継ぎが必要なら、生成前後にアプリケーション処理を置きます。

`Converse`の共通要求は[Conversation inference](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html)、モデルごとのAPI対応は[Model API compatibility](https://docs.aws.amazon.com/bedrock/latest/userguide/models-api-compatibility.html)、Knowledge Basesのプロンプト変数は[Retrieve and generate configuration](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-config.html)、モデルのLifecycleは[Model lifecycle](https://docs.aws.amazon.com/bedrock/latest/userguide/model-lifecycle.html)を参照します（確認日：2026年9月5日）。

## RetrieveAndGenerateとRetrieve＋Converseを分ける

| 観点 | `RetrieveAndGenerate` | `Retrieve`＋`Converse` |
|---|---|---|
| 対象KB | Customer-managed | Managed / Customer-managed |
| 検索・生成境界 | API内で一体 | アプリケーションで分離 |
| 引用 | AWSが引用と取得した参照資料を返す | アプリケーションが引用 IDと表示を設計 |
| 根拠集合 | API内部のコンテキスト構築が中心 | 採否理由、矛盾、回答可能性を明示可能 |
| プロンプト | Knowledge Base 生成プロンプト | ConverseのSystem・Messageを全面制御 |
| 再順位付け | KB 設定へ組み込み可能 | 単体再順位付けや独自処理を選択 |
| 評価 | システム全体評価が容易 | 検索・検索後処理・生成を工程別に評価可能 |
| 向く条件 | 標準経路で責任を減らす | 監査、独自制御、複数検索器・モデル、厳密な保留 |

どちらを選んでも、取得した参照資料の存在だけで正しい回答とは判定しません。
回答中の主張ごとに、その引用が主張を支持するかを第7章の引用評価で確認します。
[RetrieveAndGenerateのResponse](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_RetrieveAndGenerate.html)（確認日：2026年9月5日）。

## セッションとストリーミング

`RetrieveAndGenerate`は最初の応答でセッション IDを返し、継続Turnで同じIDを使います。
アプリケーションの利用者・ConversationとAWS セッションの対応、保持期間、終了、監査を設計します。
セッション IDを認可境界に使わず、各要求で利用者を認証・認可します。

ストリーミングは体感応答時間を改善しますが、総処理時間やトークン費用を必ず減らすわけではありません。
回答途中でGuardrailが介入する場合、引用の表示順、UIの確定状態、途中結果を業務処理へ使わない制御を設計します。

## Bedrock Guardrails

### 1. RAGでの目的

利用者入力と生成結果に、有害内容、禁止トピック、機密情報、単語フィルターなどのポリシーを適用し、許可、ブロック、マスキングなどの動作を統制します。

### 2. 四工程・二層の位置

主にReal-time Layerの質問側検索前処理と生成に置きます。
二つの層と四工程を横断する安全管理の一部ですが、文書ACLや情報源の管理方針の代替ではありません。

### 3. AWSリソース

Bedrock Guardrail、DRAFT、数値版、任意のCross-リージョン inference設定、Guardrail ID、Guardrail 版を使います。
`Converse`、`RetrieveAndGenerate`など対応APIへ関連づけます。

### 4. 接続先

生成モデル呼び出し、Knowledge Baseの生成設定、または独立した`ApplyGuardrail`へ接続します。
アプリケーションはGuardrailの処理結果とトレースを受け、回答、ブロック、代替処理を決めます。

### 5. AWSが管理する範囲

AWSは設定したポリシーの入力・出力評価、検出結果、処理結果、トレースを返します。
Managed ポリシーで更新されるフィルターもありますが、利用者の要件に対する適合は自動保証されません。

### 6. 利用者が選択する項目

ポリシー種別、分類、しきい値、禁止トピック、機密情報のEntityとマスキング/ブロック、Blocked message、版、適用API、トレース、代替処理を選びます。
本番ではDRAFTではなく評価済み数値版を記録します。

### 7. 評価する項目

危険入力・出力に対する検出率、正常質問の誤ブロック率、PII マスキングの漏れ、言語別挙動、プロンプト injectionテスト、応答時間、費用、版変更時の回帰を評価します。

### 8. 制約

Knowledge Basesの実行環境で取得した参照資料本文そのものにはGuardrailsが適用されません。
入力と生成応答へ適用されても、悪意ある文書、権限外文書、古い文書、誤った情報源を自動除外しません。
Managed KBのエージェント型検索ではMASKに対応せずBLOCKを使うなど、APIごとの対応差があります。

### 9. 他の選択肢との使い分け

Guardrailsはモデル入出力の共通安全ポリシーに使います。
文書の公開状態・ACLはデータソースとメタデータフィルター、悪意ある文書は取り込み審査と情報源許可リスト、主張の根拠性は根拠・引用評価、ツール認可はAgentCore PolicyやIAMで扱います。

### 10. 個別実装が必要になる条件

取得した参照資料の検査、業務固有の機密分類、文書単位の プロンプト injection検知、主張単位の検証、人による確認、利用者別代替処理が必要なら別処理を追加します。

Guardrailsの評価順序とポリシーは[Guardrailsの仕組み](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-how.html)、Converseへの接続は[Converse APIでGuardrailsを使う](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-use-converse-api.html)、Knowledge Bases 参照資料に適用されない制約は[Knowledge Base retrieval configuration](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-config.html)を参照します（確認日：2026年9月5日）。

## 回答保留を設計する

回答保留はモデルの気分に任せず、少なくとも次のSignalを評価対象にします。

- 必須のメタデータフィルター適用後に候補がない
- 検索・再順位付けで正解を支える根拠が閾値を満たさない
- 根拠同士が矛盾し、版・信頼度規則で解消できない
- 引用が主要主張を支えない
- Guardrailが入力または出力をブロックした
- 対象外の業務判断、権限外操作、人の承認が必要である

閾値は絶対解にせず、答えるべき質問と答えるべきでない質問を含む第7章の評価データで、誤回答と過剰保留のTrade-offを確認します。

## AWS標準だけでは完結しない生成後処理

- **独自回答形式**：業務スキーマ、画面、後続APIが厳密な形式を要求する場合に必要。Real-time Layerの生成へ配置。Lambda、ECS、EKS、AgentCore RuntimeとBedrock モデルを利用可能。第6章の出力契約を参照。
- **主張単位の検証**：高リスク回答、複数根拠の統合、引用 correctnessを主張単位で保証したい場合に必要。Real-time Layerの生成後へ配置。Lambda、ECS、EKS、AgentCore RuntimeとBedrock モデルを利用可能。第6章の検証と第7章を参照。
- **引用再検証**：引用の存在ではなく、主張を本当に支持するか確認する場合に必要。Real-time Layerの生成後へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第6・7章を参照。
- **複数回答候補の比較**：一つの生成で品質要件を安定して満たせない場合に必要。Real-time Layerの生成へ配置。Lambda、ECS、EKS、AgentCore RuntimeとBedrock モデルを利用可能。第6・7章を参照。
- **業務固有の回答保留**：規制、承認、契約、金額などモデル外の決定的条件がある場合に必要。Real-time Layerの生成前後へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第6・8章を参照。
- **人による確認への引き継ぎ**：自動回答が許されない、矛盾や高リスクを人が判断する場合に必要。Real-time Layerの生成後と業務ワークフローへ配置。Lambda、ECS、EKS、AgentCore Runtime、Step Functions、EventBridgeを利用可能。第8・9章を参照。
