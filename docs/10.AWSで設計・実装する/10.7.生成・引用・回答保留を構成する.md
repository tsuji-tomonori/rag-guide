# 生成・引用・回答保留を構成する

生成工程の入力は、検索結果の羅列ではなく、質問を支えるEvidenceと出典です。第6章のGrounded Generation、Citation、回答保留をBedrock生成モデル、`RetrieveAndGenerate`、`Converse`、Guardrailsへ対応づけます。引用が返ることと、引用が主張を正しく支えることは分けて評価します。

## Bedrock生成モデル

**1. RAGでの目的**

質問とEvidenceから、根拠に忠実な回答、要約、表、構造化出力を生成し、根拠が不足する場合は回答を保留します。

**2. 四工程・二層の位置**

Real-time Layerの生成工程に置きます。Query rewritingやContext Compressionへ同じModelを使う場合は、それぞれ質問側検索前処理・検索後処理として別の呼び出しとVersionを記録します。

**3. AWSリソース**

Bedrock Foundation ModelまたはCustom Model、Inference Profile、Bedrock Runtime endpoint、Knowledge Base Generation Configuration、Prompt ManagementのPromptとVersion、任意のGuardrailを使います。

**4. 接続先**

Customer-managed KBでは`RetrieveAndGenerate`または`RetrieveAndGenerateStream`から接続できます。検索と生成を分ける場合、およびManaged KBでは、アプリケーションが`Retrieve`または`AgenticRetrieveStream`の結果を整形し、`Converse`または`ConverseStream`へ接続します。

**5. AWSが管理する範囲**

AWSはModel hosting、推論、Streaming、Runtime Metricsを管理します。`RetrieveAndGenerate`では検索結果のPromptへの挿入、Generation Model呼び出し、CitationとRetrieved Referenceの関連情報、Session IDの管理も提供します。

**6. 利用者が選択する項目**

Model/Inference Profile、Region、Prompt Template、System instruction、Temperature、Top-p、Max tokens、Stop sequence、Streaming、Session保持、回答形式、回答保留条件を選びます。Knowledge BasesのCustom Promptでは検索結果を渡す`$search_results$`が必要です。Citationを返す構成では`$output_format_instructions$`を維持し、Prompt変更で引用情報を失わないようにします。

**7. 評価する項目**

第7章でFaithfulness、Answer correctness、Completeness、Citation precision、Citation coverage、回答保留のPrecision/Recall、形式適合、Latency、First-token latency、Input/Output token、Cost per answerを評価します。Modelを大きくする前にRetrievalとEvidenceの不足を切り分けます。

**8. 制約**

ModelごとにContext window、対応API、Streaming、Tool use、Structured output、Region、Throughput、Lifecycleが異なります。ModelはEvidenceの正しさ、ACL、Citation correctnessを自動保証しません。`RetrieveAndGenerate`はManaged KBでは利用しません。Prompt、Model、Inference Parameter変更は回答分布を変えるため、回帰評価が必要です。

**9. 他の選択肢との使い分け**

Customer-managed KBで標準的な検索・生成・Citationを一体化するなら`RetrieveAndGenerate`をBaselineにできます。Evidence Set、独自Prompt、会話、複数Model、検証、回答保留を細かく制御するなら`Retrieve`＋`Converse`へ分離します。Managed KBでは後者、またはManaged専用のagentic retrievalを使います。

**10. 個別実装が必要になる条件**

独自回答Schema、複数回答候補の比較、Claim-level Verification、Citation再検証、業務固有の回答保留、Human reviewへのEscalationが必要なら、生成前後にアプリケーション処理を置きます。

`Converse`の共通Requestは[Conversation inference](https://docs.aws.amazon.com/bedrock/latest/userguide/conversation-inference.html)、ModelごとのAPI対応は[Model API compatibility](https://docs.aws.amazon.com/bedrock/latest/userguide/models-api-compatibility.html)、Knowledge BasesのPrompt変数は[Retrieve and generate configuration](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-config.html)、ModelのLifecycleは[Model lifecycle](https://docs.aws.amazon.com/bedrock/latest/userguide/model-lifecycle.html)を参照します（確認日：2026年8月22日）。

## RetrieveAndGenerateとRetrieve＋Converseを分ける

| 観点 | `RetrieveAndGenerate` | `Retrieve`＋`Converse` |
|---|---|---|
| 対象KB | Customer-managed | Managed / Customer-managed |
| 検索・生成境界 | API内で一体 | アプリケーションで分離 |
| Citation | AWSがCitationとRetrieved Referenceを返す | アプリケーションがCitation IDと表示を設計 |
| Evidence Set | API内部のContext構築が中心 | 採否理由、矛盾、回答可能性を明示可能 |
| Prompt | Knowledge Base Generation Prompt | ConverseのSystem・Messageを全面制御 |
| Reranking | KB Configurationへ組み込み可能 | 単体Rerankや独自処理を選択 |
| 評価 | End-to-end評価が容易 | 検索・検索後処理・生成を工程別に評価可能 |
| 向く条件 | 標準経路で責任を減らす | 監査、独自制御、複数Retriever・Model、厳密な保留 |

どちらを選んでも、Retrieved Referenceの存在だけで正しい回答とは判定しません。回答中のClaimごとに、そのCitationが主張を支持するかを第7章のCitation評価で確認します。[RetrieveAndGenerateのResponse](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_RetrieveAndGenerate.html)（確認日：2026年8月22日）。

## SessionとStreaming

`RetrieveAndGenerate`は最初の応答でSession IDを返し、継続Turnで同じIDを使います。アプリケーションのUser・ConversationとAWS Sessionの対応、保持期間、終了、監査を設計します。Session IDをAuthorization境界に使わず、各Requestで利用者を認証・認可します。

Streamingは体感Latencyを改善しますが、総処理時間やToken費用を必ず減らすわけではありません。回答途中でGuardrailが介入する場合、Citationの表示順、UIの確定状態、途中結果を業務処理へ使わない制御を設計します。

## Bedrock Guardrails

**1. RAGでの目的**

利用者入力と生成結果に、有害Content、Denied topic、Sensitive information、Word filterなどのPolicyを適用し、許可、Block、Maskなどの動作を統制します。

**2. 四工程・二層の位置**

主にReal-time Layerの質問側検索前処理と生成に置きます。二つのLayerと四工程を横断する安全管理の一部ですが、Document ACLやSource governanceの代替ではありません。

**3. AWSリソース**

Bedrock Guardrail、DRAFT、数値Version、任意のCross-Region inference設定、Guardrail ID、Guardrail Versionを使います。`Converse`、`RetrieveAndGenerate`など対応APIへ関連づけます。

**4. 接続先**

Generation Model呼び出し、Knowledge BaseのGeneration Configuration、または独立した`ApplyGuardrail`へ接続します。アプリケーションはGuardrailのActionとTraceを受け、回答、Block、Fallbackを決めます。

**5. AWSが管理する範囲**

AWSは設定したPolicyの入力・出力評価、検出結果、Action、Traceを返します。Managed Policyで更新されるFilterもありますが、利用者の要件に対する適合は自動保証されません。

**6. 利用者が選択する項目**

Policy種別、Category、Threshold、Denied topic、Sensitive informationのEntityとMask/Block、Blocked message、Version、適用API、Trace、Fallbackを選びます。ProductionではDRAFTではなく評価済み数値Versionを記録します。

**7. 評価する項目**

危険入力・出力に対する検出率、正常質問の誤Block率、PII Maskの漏れ、言語別挙動、Prompt injectionテスト、Latency、費用、Version変更時の回帰を評価します。

**8. 制約**

Knowledge BasesのRuntimeで取得したReference本文そのものにはGuardrailsが適用されません。入力と生成応答へ適用されても、悪意ある文書、権限外文書、古い文書、誤ったSourceを自動除外しません。Managed KBのagentic retrievalではMASKに対応せずBLOCKを使うなど、APIごとの対応差があります。

**9. 他の選択肢との使い分け**

GuardrailsはModel入出力の共通安全Policyに使います。文書の公開状態・ACLはData SourceとMetadata Filter、悪意ある文書はIngestion審査とSource allowlist、Claimの根拠性はEvidence・Citation評価、Tool認可はAgentCore PolicyやIAMで扱います。

**10. 個別実装が必要になる条件**

Retrieved Referenceの検査、業務固有の機密分類、Document-level Prompt injection検知、Claim-level Verification、Human review、利用者別Fallbackが必要なら別処理を追加します。

Guardrailsの評価順序とPolicyは[Guardrailsの仕組み](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-how.html)、Converseへの接続は[Converse APIでGuardrailsを使う](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails-use-converse-api.html)、Knowledge Bases Referenceに適用されない制約は[Knowledge Base retrieval configuration](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-test-config.html)を参照します（確認日：2026年8月22日）。

## 回答保留を設計する

回答保留はModelの気分に任せず、少なくとも次のSignalを評価対象にします。

- 必須のMetadata Filter適用後に候補がない
- Retrieval・Rerankで正解を支えるEvidenceが閾値を満たさない
- Evidence同士が矛盾し、版・信頼度規則で解消できない
- Citationが主要Claimを支えない
- Guardrailが入力または出力をBlockした
- 対象外の業務判断、権限外操作、人の承認が必要である

閾値は絶対解にせず、答えるべき質問と答えるべきでない質問を含む第7章の評価データで、誤回答と過剰保留のTrade-offを確認します。

## AWS標準だけでは完結しない生成後処理

- **独自回答形式**：業務Schema、画面、後続APIが厳密な形式を要求する場合に必要。Real-time Layerの生成へ配置。Lambda、ECS、EKS、AgentCore RuntimeとBedrock Modelを利用可能。第6章の出力契約を参照。
- **Claim-level Verification**：高リスク回答、複数根拠の統合、Citation correctnessをClaim単位で保証したい場合に必要。Real-time Layerの生成後へ配置。Lambda、ECS、EKS、AgentCore RuntimeとBedrock Modelを利用可能。第6章の検証と第7章を参照。
- **Citation再検証**：Citationの存在ではなく、Claimを本当に支持するか確認する場合に必要。Real-time Layerの生成後へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第6・7章を参照。
- **複数回答候補の比較**：一つの生成で品質要件を安定して満たせない場合に必要。Real-time Layerの生成へ配置。Lambda、ECS、EKS、AgentCore RuntimeとBedrock Modelを利用可能。第6・7章を参照。
- **業務固有の回答保留**：規制、承認、契約、金額などModel外の決定的条件がある場合に必要。Real-time Layerの生成前後へ配置。Lambda、ECS、EKS、AgentCore Runtimeを利用可能。第6・8章を参照。
- **Human reviewへのEscalation**：自動回答が許されない、矛盾や高リスクを人が判断する場合に必要。Real-time Layerの生成後と業務Workflowへ配置。Lambda、ECS、EKS、AgentCore Runtime、Step Functions、EventBridgeを利用可能。第8・9章を参照。
