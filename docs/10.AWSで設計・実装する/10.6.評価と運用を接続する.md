# 10.6 評価とRAG運用を接続する

## 10.6.1 Knowledge Base評価を工程別に実行する

評価データをS3へ置き、[Knowledge BaseのRAG評価](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-kb.html)で検索だけの評価と、検索から生成までの評価を分けます。Bedrock Evaluationsの結果に加え、[品質評価](../7.品質を評価し改善する/序文.md)で定義したgold evidence、回答保留、citation correctnessを同じdataset IDへ結び付けます。

比較単位には、Knowledge Base ID、data source sync job、embedding modelとdimension、chunking設定、vector storeとindex、検索方式、`numberOfResults`、reranker、prompt、生成modelを含めます。二つ以上の主要設定を同時に変えると原因を特定できないため、評価runごとに一つずつ変更します。

## 10.6.2 RAG固有のmetricを記録する

online経路では、少なくとも次の値を処理段階別に記録します。

| 段階 | metric |
|---|---|
| Retrieve | candidate数、zero-result率、filter前後件数、Recall@k、検索latency |
| Rerank・Evidence | rerank前後順位、採用件数、重複率、Evidence sufficiency、処理latency |
| Generation | input/output token、answerable率、citation correctness、claim support、生成latency |
| End-to-end | p50・p95 latency、質問当たり費用、error率、fallback率 |

CloudWatchへ送るdimensionは、modelやdocument IDのような高cardinality値を避け、`knowledge_base_id`、`index_version`、`pipeline_version`、`result_type`など集計に使う項目へ限定します。詳細な候補とcitationはアプリケーションtraceへ分け、同じtrace IDで結び付けます。

## 10.6.3 公開と切り戻しを評価結果へ結び付ける

初期の公開基準例は、gold evidenceに対するRecall@20、rerank後の上位5件のcoverage、citation correctness、answerable判定、p95 latency、質問当たり費用です。閾値そのものは対象業務の評価データから決め、固定値を他のシステムへ流用しません。

新しいindex、embedding、prompt、modelは別の`pipeline_version`として評価します。いずれかの必須指標が基準を下回る場合は検索先を切り替えません。限定trafficで回帰が確認された場合は、旧indexと旧prompt/modelの組み合わせへ戻します。
