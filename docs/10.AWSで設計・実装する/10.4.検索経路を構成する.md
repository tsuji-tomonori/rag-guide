# 10.4. 検索経路を設定する

## 10.4.1. Retrieveの候補数と検索方式を設定する

検索と生成を分ける場合は、Bedrock Agent Runtimeの`Retrieve`を呼び出します。Knowledge Baseの管理方式によって、`retrievalConfiguration`へ渡す設定を分けます。

カスタマーマネージド型では`vectorSearchConfiguration`を使います。`numberOfResults`は1から100まで指定できます。初期値は20とし、5、10、20、50でRecall@k、reranking後の採用率、p95 latencyを比較します。生成へ渡す件数ではなく、初段検索が返すcandidate数として扱います。

`overrideSearchType`は`SEMANTIC`または`HYBRID`です。filterable text fieldを使うKnowledge Bases構成では、OpenSearch Serverless、Aurora PostgreSQL、MongoDB Atlasを候補表へ分けて登録し、実装するstoreだけを接続試験します。一方、[KnowledgeBaseVectorSearchConfiguration API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_KnowledgeBaseVectorSearchConfiguration.html)にはOpenSearch Serverlessだけを挙げる記述が残る差異を想定し、実装時は採用するAPIの公式仕様と実行結果を一致させます。記述差があるため、対応storeを本文だけで固定せず、同一日にユーザーガイド、API Reference、リリース情報を確認し、対象リージョンの最小indexへ`HYBRID`を送る疎通試験で確定します。確認日、region、store種別、index schema、request、responseを証跡へ残します。S3 Vectorsなど疎検索を提供しないstoreでは`SEMANTIC`を使います。

OpenSearch Serverlessで`HYBRID`を使う場合は、利用時点のKnowledge Bases公式仕様で対応を確認し、`faiss` engine、埋め込みモデルと同じ次元のvector field、filterableな本文field、filter対象metadata field、Bedrock管理metadata fieldをmanifestへ固定します。たとえば、`bedrock-knowledge-base-default-vector`をvector field、`AMAZON_BEDROCK_TEXT_CHUNK`をfilterableなtext field、`AMAZON_BEDROCK_METADATA`をBedrock metadata fieldとしてKnowledge Base作成時に対応付けます。field名は任意ですが、index mappingとKnowledge Baseの設定を一致させます。Aurora PostgreSQLまたはMongoDB Atlasでは、それぞれの公式手順に従ってvector fieldとfilterableなtext fieldを構成し、同じrequestで動作を確認します。

```json
{
  "retrievalConfiguration": {
    "vectorSearchConfiguration": {
      "numberOfResults": 20,
      "overrideSearchType": "SEMANTIC"
    }
  }
}
```

Managed Knowledge Baseでは`managedSearchConfiguration`を使います。Managed Knowledge Baseの検索はhybrid searchとして提供され、`overrideSearchType`で検索方式を上書きしません。`numberOfResults`は1から100までの範囲で、カスタマーマネージド型と同じ評価データを使って調整します。

```json
{
  "retrievalConfiguration": {
    "managedSearchConfiguration": {
      "numberOfResults": 20
    }
  }
}
```

## 10.4.2. S3 Vectorsで疎検索を補う

Bedrock Knowledge BasesでS3 Vectorsを使う構成はsemantic searchとmetadata filterに対応し、hybrid searchには対応しません。固有名詞や識別子の取りこぼしがある場合は、S3 VectorsへHYBRID指定を送るのではなく、次のいずれかを選びます。

1. vector storeをOpenSearch Serverlessなど、Knowledge Basesの`HYBRID`へ対応するstoreへ変更します。
2. S3 Vectorsのsemantic結果とOpenSearchのBM25結果を別々に取得し、LambdaでRRFを適用します。
3. sparse結果とdense結果をまとめてBedrock rerankerへ渡します。
4. Managed Knowledge Baseを同じ評価条件で比較し、検索品質、権限反映、更新遅延、trace、costを確認します。

複数検索器のscoreは尺度が異なるため直接加算せず、正規化、順位統合、または再順位付けのいずれかを事前に定めて用います。RRFでは各検索器の順位を使い、rerankerでは統合後のcandidate本文を再評価します。実装根拠と評価方法は[Hybrid retrieval](../4.質問に合う根拠を探す/4.5.Hybrid retrieval.md)を参照します。

疎検索器と密検索器には同じ安定したchunk IDを登録し、本文、文書版、filter metadata、アクセス制御属性を一対一で対応付けます。更新と削除は両方へ伝播させ、片方だけに残ったchunkを定期的に検出します。初期比較ではdenseとBM25を各20件、統合後を20件、rerank後を5件とし、各retrieverのcandidate数、timeout、zero-result、失敗時の扱いを独立に記録します。これらの値は固定仕様ではなく、Recallとonline latency budgetを測るための開始値です。

## 10.4.3. Metadata filterを必須条件として渡す

次の例は、カスタマーマネージド型の`retrievalConfiguration.vectorSearchConfiguration.filter`へ検索条件を指定するものです。公開状態と版を同時に限定します。

```json
{
  "andAll": [
    {"equals": {"key": "status", "value": "published"}},
    {"equals": {"key": "version", "value": "2026-07"}}
  ]
}
```

`equals`、`in`、`greaterThan`、`listContains`などの候補は[RetrievalFilter API](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_RetrievalFilter.html)で確認します。`startsWith`条件を使うqueryはOpenSearch Serverless経路へだけrouteし、他のstoreへは同じoperatorを送信しません。それ以外のoperatorもvector storeごとに実装範囲が異なるため、Bedrock APIに列挙されているだけで同じ式を全storeへ流用できるとは判断しません。S3 Vectorsを直接queryする場合は、[S3 Vectorsのmetadata filter](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-metadata-filtering.html)に記載されたoperatorだけを使います。filter後の候補不足を見落とさないように、filter前後の件数とzero-result率を記録します。

Managed Knowledge Baseでは、接続元の権限とサービスが提供するpermission-aware filteringの境界を確認します。カスタマーマネージド型のfilter式をそのまま流用せず、権限のある利用者とない利用者を使ったnegative testで、検索結果と引用に機密情報が混入しないことを確認します。

## 10.4.4. Rerankingを設定する

rerankerを使うときは、初段の`numberOfResults`をrerank後の件数より大きくします。初期値は20件を取得して5件へrerankし、10→5、20→5、50→10を比較します。[Bedrock reranker](https://docs.aws.amazon.com/bedrock/latest/userguide/rerank-use.html)の`numberOfResults`は、rerank後に返す件数です。

初段Recallが不足している場合、rerankerは見つからなかった根拠を復元できません。Recall@20、rerank後nDCGまたはMRR、生成に採用した件数、追加latencyを分けて評価します。
