# 要件別リファレンス構成を選ぶ

最後に、要件から責任分界を選びます。以下はAWS公式の単一推奨構成ではなく、本章で整理した機能を要件別に組み合わせた比較用のReference Architectureです。設定値はBaselineとし、第7章の同じDataset、第8章の非機能要件、第9章の失敗分析で選定します。

## 構成A――最大限マネージド

```text
Data Sources
    ▼
Bedrock Managed Knowledge Base
    ├─ Ingestion / Storage / Indexing
    ├─ Service-managed Embedding
    ├─ Hybrid Retrieval
    └─ Service-managed Reranking
    ▼
Retrieve / AgenticRetrieveStream
    ▼
Application / AgentCore
    ▼
Evidence・Bedrock Generation Model・Guardrails
```

向く条件は、検索基盤の管理対象を減らしたい、Vector Storeを直接運用しない、AWS標準のHybrid Retrievalへ寄せられる、agentic retrievalが必要、複数の対応Data Sourceを接続したい場合です。内部Index、Embedding、Rerankingを細かく固定・直接操作する要件には向きません。`RetrieveAndGenerate`は使わず、`Retrieve`または`AgenticRetrieveStream`を使います。

利用者は、Data Source、Parser/Chunking、同期、Filter/ACL、検索件数、agentic retrieval設定、Evidence、Generation、Guardrails、評価を担当します。Managedであっても文書品質と回答品質の責任は残ります。

## 構成B――Semantic Search中心

```text
Amazon S3（原文）
    ▼
Customer-managed Knowledge Base
    ├─ Parser / Chunking
    └─ Bedrock Embedding Model
    ▼
Amazon S3 Vectors
    ▼
Retrieve / RetrieveAndGenerate
```

向く条件は、Semantic Searchで要件を満たせる、大量Vectorを保存する、Keyword Searchが主要件ではない、Metadataを1Vector当たり1KB・35 keyのKnowledge Bases連携上限内に設計できる、検索頻度・Latency・費用特性が要件に合う場合です。

利用者はEmbedding Model、Dimension、Distance Metric、Metadataのfilterable/non-filterable、Index versionを担当します。型番・条文・Error codeの完全一致が重要になったら、OpenSearchとの比較または別Retrieverの追加を行います。

## 構成C――Hybrid Search中心

```text
Amazon S3（原文）
    ▼
Customer-managed Knowledge Base
    ├─ Parser / Chunking
    └─ Bedrock Embedding Model
    ▼
OpenSearch Serverless
    ├─ Keyword / BM25
    ├─ Vector
    ├─ Hybrid
    └─ Metadata Filter
    ▼
Retrieve / RetrieveAndGenerate
```

向く条件は、型番、条文番号、固有語、Error codeを扱う、全文検索が重要、SemanticとKeywordを組み合わせる、柔軟なMetadata Filter、Analyzer、検索分析、高い検索頻度・低Latencyが必要な場合です。

利用者はCollection/Index、Text/Vector/Metadata field、Analyzer、Search type、Security Policy、OCUとScale設定を担当します。S3 Vectorsより運用・容量設計が増える代わりに、検索制御の範囲が広がります。

## 構成D――検索・Evidence制御重視

```text
Application
    ├─ OpenSearch / S3 Vectorsを直接検索
    ├─ 複数Retriever・独自Fusion / RRF
    ├─ 重複排除・MMR・業務規則
    ├─ Evidence Set・Context Compression / Packing
    └─ Bedrock Converse・Claim-level Verification
```

向く条件は、複数Retriever、独自RRF、複雑なACL、独自Chunk schema、採否理由、Claim単位の検証、検索と生成の完全なTraceが必須な場合です。

AWSはS3、S3 Vectors、OpenSearch Serverless、Bedrock Model、Lambda/ECS/EKS/AgentCore Runtimeなどの実行基盤を管理します。利用者はPipeline、Schema、Failure handling、再処理、評価の範囲を広く担当します。制御性と引き換えに、実装・運用・監査対象が最も増えます。

## 構成E――Agentic RAG

```text
利用者
    ▼
AgentCore Identity / Runtime
    ├─ Gateway → Managed Knowledge Base
    ├─ Gateway → 社内API / Lambda / MCP
    ├─ Memory
    ├─ Policy
    └─ Observability / Evaluations
```

向く条件は、回答だけで業務が完了しない、複数Step、複数回検索、検索先選択、API/Tool実行、MCP、Memory、長時間処理、Tool単位Policy、Agent step Traceが必要な場合です。

Knowledge BaseとVector Storeは引き続き検索を担当します。AgentCoreはそれらを利用するAgentアプリケーションを実行・統制します。Native Gateway targetでKnowledge Baseを公開する経路はManaged KBが対象です。通常の一問一答RAGには構成A〜Dの通常Applicationで十分な場合があります。

## Reference Architectureを比較する

| 構成 | AWSへ任せる主な範囲 | 利用者が制御する主な範囲 | 向く要件 | 主な再評価点 |
|---|---|---|---|---|
| A 最大限マネージド | Ingestion、Storage、Index、Hybrid、既定Embedding/Rerank | Source、Filter/ACL、Evidence、Generation | 運用対象削減、agentic retrieval | Managed設定、ACL、Latency、費用 |
| B Semantic中心 | KB Pipeline、Embedding hosting、S3 Vector基盤 | Model、Dimension、Metadata、Semantic Top-k | 大量Vector、Semantic中心 | Recall、Metadata上限、検索頻度別費用 |
| C Hybrid中心 | KB Pipeline、Embedding hosting、Serverless検索基盤 | Schema、Analyzer、Hybrid、Security、OCU | Keyword＋Vector、柔軟なFilter | Hybrid品質、Latency、OCU費用 |
| D 制御重視 | AWSのStorage・Search・Model・Runtime | Pipeline、Fusion、Evidence、検証 | 独自RRF、ACL、監査、Claim検証 | 全工程の回帰、運用負担 |
| E Agentic | Agent Runtime、Gateway、Identity、Memory、Policy、Observability | Agent logic、Tool、停止条件、許可Policy | Tool、Memory、複数Step | Task success、Trajectory、Tool認可、費用 |

**表10-12 要件別Reference Architectureの選択**

構成Aの根拠は[Managed Knowledge Base](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-build-managed.html)、構成Bは[S3 VectorsとKnowledge Bases](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-bedrock-kb.html)、構成Cは[OpenSearch ServerlessのNeural・Hybrid Search](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-configure-neural-search.html)、構成Eは[AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html)を参照します（確認日：2026年8月22日）。

## 要件から選ぶ

```text
文書QAは一巡の検索・生成で完了するか
├─ はい ────────────────────────────────┐
└─ いいえ：Tool / Memory / 複数Stepが必要か      │
          ├─ はい → E Agentic RAG                 │
          └─ いいえ → 通常Applicationで分解       │
                                                   ▼
Storage・Index・検索基盤をAWSへ隠蔽できるか
├─ はい → A Managed Knowledge Base
└─ いいえ
    │
    ├─ Keyword / 型番 / 条文 / Flexible Metadataが重要
    │      └─ C KB＋OpenSearch Serverless
    │
    └─ Semantic中心・S3 Vectors制約内
           └─ B KB＋S3 Vectors

どの分岐でも独自RRF・Evidence・ACL・Claim検証が必須か
└─ はい → Dの処理を必要な工程だけ追加
```

**図10-10 要件から構成を選ぶDecision Tree**

Decision Treeの分岐は一度決めて終わりではありません。次の順序で小さな比較を行います。

1. 第7章のEvaluation datasetと非機能要件を固定する
2. Managed範囲を最大にしたBaselineを評価する
3. Keyword、Metadata、Latency、費用、制御性で不足する工程だけを分離する
4. S3 VectorsとOpenSearch Serverlessを同じTraffic・品質基準で比較する
5. AWS標準で満たせない処理だけを個別実装として追加する
6. Tool、Memory、反復処理が必要な場合だけAgentCoreを比較する
7. 変更前後でRetrieve-only、Rerank、End-to-end、Security、Costの回帰評価を行う

## 設計成果物を完成させる

本章の完成条件はAWSリソースを作ることではなく、次の判断を説明・再現できることです。

- 四工程・二層の各処理と入出力
- Batch LayerとReal-time Layerの責任者
- Managed KB、Customer-managed KB、Knowledge Basesなしの選定理由
- Amazon S3を正本にするか、外部Data Sourceを正本にするか
- S3 VectorsまたはOpenSearch Serverlessの選定理由
- Parser、Chunking、Embedding、Retrieval、Rerank、Generationの比較候補
- `Retrieve`、`AgenticRetrieveStream`、`RetrieveAndGenerate`、`Converse`の使い分け
- AWSが管理する範囲と利用者が実装する範囲
- IAM主体、KMS Key、Network、ACL/Filter、Tool Policyの境界
- Monitoring、Evaluation、Version、Cost allocationの対応
- 変更時の再取り込み、再Embedding、再索引、回帰評価、Rollback
- AgentCoreの採否と、採用する各Moduleの理由

最後にArchitecture Decision Record（ADR）へ、採用案だけでなく比較した案、棄却理由、評価Dataset、Metric、合格基準、費用前提、再検討条件を残します。これにより、第1〜9章のRAG設計が、AWSサービス名の一覧ではなく、責任分界と検証可能な設定へ翻訳されます。
