# 要件別リファレンス構成を選ぶ

最後に、要件から責任分界を選びます。
以下はAWS公式の単一推奨構成ではなく、本章で整理した機能を要件別に組み合わせた比較用の参照構成です。
設定値は基準構成とし、第7章の同じDataset、第8章の非機能要件、第9章の失敗分析で選定します。

## 構成A――最大限マネージド

```text
Data Sources
    ▼
Bedrock Managed Knowledge Base
    ├─ Ingestion / Storage / Indexing
    ├─ Service-managed Embedding
    ├─ Hybrid Retrieval
    └─ Service-managed Reranking
    ▼
Retrieve / AgenticRetrieveStream
    ▼
Application / AgentCore
    ▼
Evidence・Bedrock Generation Model・Guardrails
```

向く条件は、検索基盤の管理対象を減らしたい、ベクトルストアを直接運用しない、AWS標準のハイブリッド検索へ寄せられる、エージェント型検索が必要、複数の対応データソースを接続したい場合です。
内部インデックス、埋め込み、再順位付けを細かく固定・直接操作する要件には向きません。
`RetrieveAndGenerate`は使わず、`Retrieve`または`AgenticRetrieveStream`を使います。

利用者は、データソース、解析器/チャンク分割、同期、フィルター/ACL、検索件数、エージェント型検索設定、根拠、生成、Guardrails、評価を担当します。
Managedであっても文書品質と回答品質の責任は残ります。

## 構成B――意味検索中心

```text
Amazon S3（原文）
    ▼
Customer-managed Knowledge Base
    ├─ Parser / Chunking
    └─ Bedrock Embedding Model
    ▼
Amazon S3 Vectors
    ▼
Retrieve / RetrieveAndGenerate
```

向く条件は、意味検索で要件を満たせる、大量ベクトルを保存する、キーワード検索が主要件ではない、メタデータを1Vector当たり1KB・35 keyのKnowledge Bases連携上限内に設計できる、検索頻度・応答時間・費用特性が要件に合う場合です。

利用者は埋め込みモデル、次元数、距離指標、メタデータのfilterable/non-filterable、インデックス versionを担当します。
型番・条文・エラーコードの完全一致が重要になったら、OpenSearchとの比較または別検索器の追加を行います。

## 構成C――ハイブリッド検索中心

```text
Amazon S3（原文）
    ▼
Customer-managed Knowledge Base
    ├─ Parser / Chunking
    └─ Bedrock Embedding Model
    ▼
OpenSearch Serverless
    ├─ Keyword / BM25
    ├─ Vector
    ├─ Hybrid
    └─ Metadata Filter
    ▼
Retrieve / RetrieveAndGenerate
```

向く条件は、型番、条文番号、固有語、エラーコードを扱う、全文検索が重要、意味に基づくとキーワードを組み合わせる、柔軟なメタデータフィルター、解析器、検索分析、高い検索頻度・低応答時間が必要な場合です。

利用者はコレクション/インデックス、テキスト/ベクトル/メタデータ項目、解析器、検索方式、セキュリティポリシー、OCUと規模調整設定を担当します。
S3 Vectorsより運用・容量設計が増える代わりに、検索制御の範囲が広がります。

## 構成D――検索・根拠制御重視

```text
Application
    ├─ OpenSearch / S3 Vectorsを直接検索
    ├─ 複数Retriever・独自Fusion / RRF
    ├─ 重複排除・MMR・業務規則
    ├─ Evidence Set・Context Compression / Packing
    └─ Bedrock Converse・Claim-level Verification
```

向く条件は、複数検索器、独自RRF、複雑なACL、独自チャンクスキーマ、採否理由、主張単位の検証、検索と生成の完全なトレースが必須な場合です。

AWSはS3、S3 Vectors、OpenSearch Serverless、Bedrock モデル、Lambda/ECS/EKS/AgentCore Runtimeなどの実行基盤を管理します。
利用者は処理の流れ、スキーマ、Failure handling、再処理、評価の範囲を広く担当します。
制御性と引き換えに、実装・運用・監査対象が最も増えます。

## 構成E――エージェント型RAG

```text
利用者
    ▼
AgentCore Identity / Runtime
    ├─ Gateway → Managed Knowledge Base
    ├─ Gateway → 社内API / Lambda / MCP
    ├─ Memory
    ├─ Policy
    └─ Observability / Evaluations
```

向く条件は、回答だけで業務が完了しない、複数Step、複数回検索、検索先選択、API/ツール実行、MCP、記憶管理、長時間処理、ツール単位ポリシー、エージェント step トレースが必要な場合です。

Knowledge Baseとベクトルストアは引き続き検索を担当します。
AgentCoreはそれらを利用するエージェントアプリケーションを実行・統制します。
Native Gateway targetでKnowledge Baseを公開する経路はManaged KBが対象です。
通常の一問一答RAGには構成A〜Dの通常アプリケーションで十分な場合があります。

## 参照構成を比較する
**表10-12 要件別参照構成の選択**

| 構成 | AWSへ任せる主な範囲 | 利用者が制御する主な範囲 |
|---|---|---|
| A 最大限マネージド | 取り込み、保存容量、インデックス、ハイブリッド、既定埋め込み/再順位付け | 情報源、フィルター/ACL、根拠、生成 |
| B 意味に基づく中心 | KB 処理の流れ、埋め込みホスティング、S3 ベクトル基盤 | モデル、次元数、メタデータ、意味に基づく Top-k |
| C ハイブリッド中心 | KB 処理の流れ、埋め込みホスティング、Serverless検索基盤 | スキーマ、解析器、ハイブリッド、セキュリティ、OCU |
| D 制御重視 | AWSの保存容量・検索・モデル・実行環境 | 処理の流れ、統合、根拠、検証 |
| E Agentic | エージェント実行環境、Gateway、識別情報、記憶管理、ポリシー、実行状態の観測 | エージェントの処理ロジック、ツール、停止条件、許可ポリシー |

| 構成 | 向く要件 | 主な再評価点 |
|---|---|---|
| A 最大限マネージド | 運用対象削減、エージェント型検索 | Managed設定、ACL、応答時間、費用 |
| B 意味に基づく中心 | 大量ベクトル、意味に基づく中心 | Recall、メタデータ上限、検索頻度別費用 |
| C ハイブリッド中心 | キーワード＋ベクトル、柔軟なフィルター | ハイブリッド品質、応答時間、OCU費用 |
| D 制御重視 | 独自RRF、ACL、監査、主張検証 | 全工程の回帰、運用負担 |
| E Agentic | ツール、記憶管理、複数Step | Task success、実行履歴、ツール認可、費用 |


構成Aの根拠は[Managed Knowledge Base](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-build-managed.html)、構成Bは[S3 VectorsとKnowledge Bases](https://docs.aws.amazon.com/AmazonS3/latest/userguide/s3-vectors-bedrock-kb.html)、構成Cは[OpenSearch ServerlessのNeural・Hybrid Search](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/serverless-configure-neural-search.html)、構成Eは[AgentCore](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/what-is-bedrock-agentcore.html)を参照します（確認日：2026年9月5日）。

## 要件から選ぶ

```text
文書QAは一巡の検索・生成で完了するか
├─ はい ────────────────────────────────┐
└─ いいえ：Tool / Memory / 複数Stepが必要か      │
          ├─ はい → E Agentic RAG                 │
          └─ いいえ → 通常Applicationで分解       │
                                                   ▼
Storage・Index・検索基盤をAWSへ隠蔽できるか
├─ はい → A Managed Knowledge Base
└─ いいえ
    │
    ├─ Keyword / 型番 / 条文 / Flexible Metadataが重要
    │      └─ C KB＋OpenSearch Serverless
    │
    └─ Semantic中心・S3 Vectors制約内
           └─ B KB＋S3 Vectors

どの分岐でも独自RRF・Evidence・ACL・Claim検証が必須か
└─ はい → Dの処理を必要な工程だけ追加
```

**図10-10 要件から構成を選ぶ判断の流れ**

判断の流れは、要件と評価結果の変化に合わせて見直します。
次の順序で小さな比較を行います。

1. 第7章のEvaluation datasetと非機能要件を固定する
2. Managed範囲を最大にした基準構成を評価する
3. キーワード、メタデータ、応答時間、費用、制御性で不足する工程だけを分離する
4. S3 VectorsとOpenSearch Serverlessを同じ利用量・品質基準で比較する
5. AWS標準で満たせない処理だけを個別実装として追加する
6. ツール、記憶管理、反復処理が必要な場合だけAgentCoreを比較する
7. 変更前後でRetrieve-only、再順位付け、システム全体、セキュリティ、費用の回帰評価を行う

## 設計成果物を完成させる

本章の完成条件はAWSリソースを作ることではなく、次の判断を説明・再現できることです。

- 四工程・二層の各処理と入出力
- Batch LayerとReal-time Layerの責任者
- Managed KB、Customer-managed KB、Knowledge Basesなしの選定理由
- Amazon S3を正本にするか、外部データソースを正本にするか
- S3 VectorsまたはOpenSearch Serverlessの選定理由
- 解析器、チャンク分割、埋め込み、検索、再順位付け、生成の比較候補
- `Retrieve`、`AgenticRetrieveStream`、`RetrieveAndGenerate`、`Converse`の使い分け
- AWSが管理する範囲と利用者が実装する範囲
- IAM主体、KMS キー、ネットワーク、ACL/フィルター、ツールポリシーの境界
- Monitoring、Evaluation、版、費用 allocationの対応
- 変更時の再取り込み、再埋め込み、再索引、回帰評価、切り戻し
- AgentCoreの採否と、採用する各Moduleの理由

最後にArchitecture Decision Record（ADR）へ、採用案だけでなく比較した案、棄却理由、評価Dataset、指標、合格基準、費用前提、再検討条件を残します。
これにより、第1〜9章のRAG設計が、AWSサービス名の一覧ではなく、責任分界と検証可能な設定へ翻訳されます。
