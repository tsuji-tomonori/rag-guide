# 10. AWSでRAGアプリケーションを設計する

本章では、第1章から第9章までに説明したRAGの設計を、AWS上のサービス、リソース、API、設定項目へ対応づけます。

AWSには、原文を保管する仕組み、文書を検索可能にする仕組み、候補を並べ直す仕組み、根拠から回答を作る仕組みがあります。しかし、サービス名から構成を選ぶだけでは、RAGのどの工程を誰が担い、利用者が何を決めて評価するのかが曖昧になります。本章では、まず工程と責任を定め、その責任に合うAWS機能を選びます。

第2章の論理構成を引き継ぎ、RAGを「検索前処理・検索・検索後処理・生成」の四工程と、「Batch Layer・Real-time Layer」の二層で整理します。本章のBatch Layerは第2章のオフライン層、Real-time Layerはオンライン層に対応します。ただし、Batch Layerでも増分同期は起こり、Real-time Layerでも非同期処理はあり得ます。名称は実行方式ではなく、質問より前に準備する責任と、質問ごとに実行する責任の境界を表します。

IAM、KMS、監視、評価、版管理、コスト管理は第三のLayerではありません。二層と四工程のすべてに通す管理面です。また、本章に示す設定値や構成例は絶対解ではなく、Baselineまたは比較対象です。第7章の同じ評価データと指標で検証し、品質、性能、費用、運用性の制約に合わせて調整します。

本章は構築手順を扱いません。コンソール操作、AWS CLI、プログラム、サンプル文書、成功確認、リソース削除、所要時間は `handson/aws-rag-application/` のハンズオン資料へ分離しています。

AWS固有の仕様はAWS公式資料を根拠とし、本文中にリンクを示します。特に断りがない限り、確認日は**2026年8月22日**です。サービス、モデル、リージョン、クォータ、料金は変わり得るため、設計・導入時にはリンク先の最新情報を再確認してください。

本章を読み終えると、次のことができるようになります。

- 四工程・二層の各責任をAWSリソースへ配置できる
- Managed Knowledge BaseとCustomer-managed Knowledge Baseの責任分界を選べる
- S3 VectorsとOpenSearch Serverlessを検索要件、Metadata要件、費用、検索頻度、運用範囲から比較できる
- AWSへ任せる設定と、利用者が実装・評価する処理を分離できる
- 通常の一問一答RAGとAgentCoreを使うAgentic RAGを使い分けられる
- IAM、KMS、監視、評価、版管理、コスト管理を全工程へ通せる
