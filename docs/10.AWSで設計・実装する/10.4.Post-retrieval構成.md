# 10.4. Post-retrieval構成

Post-retrievalでは、Retrievalが返した候補を回答へ渡せる根拠集合へ変えます。
再順位付けだけでなく、重複排除、版の優先、権限の再確認、context量の制御もこの工程に含みます。

## 10.4.1. 対応するAWSサービス

**Amazon Bedrockのreranker model**は、質問と候補本文をまとめて評価し、Knowledge Basesの初期順位を上書きします。
東京リージョンではAmazon Rerank 1.0とCohere Rerank 3.5を候補にできます。

**`Retrieve`と`RetrieveAndGenerate`**

Bedrock Agent Runtimeの二つのAPIは、`retrievalConfiguration`の中でrerankerを呼び出せます。
別のreranking serviceを構築せず、検索APIの一部として適用できます。

**AWS Lambda**は、重複排除、版の優先、禁止sourceの除外、独自scoreの統合、token予算に合わせたcontext packingなど、決定的な業務ルールを実装する場合に使います。

**Amazon CloudWatch**は、reranker前後の候補数、latency、error、採用sourceの分布を監視します。
本文を記録する場合は機密情報の複製を避けるlog設計が必要です。

## 10.4.2. 処理を追加するかの判断

最小構成ではreranker、重複排除、圧縮を追加しません。
`Retrieve`の上位5件を目視し、問題がある工程だけを追加します。

**rerankerを追加する条件**

- 正解chunkは上位20件にあるが、上位5件へ入らない場合
- semantic similarityは高いものの、質問へ直接答えないchunkが先に来る場合
- 生成へ渡す件数を減らしながら、正解を残したい場合

**Lambdaなどの独自処理を追加する条件**

- 同じ本文や同じsectionが複数versionから重複して返る場合
- 公開版を下書き版より優先するなど、業務規則がある場合
- sourceごとの上限、文書種別の優先、厳密なcontext token上限がある場合
- 複数retrieverの結果をRRFなどで統合する場合

**処理を追加しない条件**

- 上位候補だけで安定して回答できる場合
- 評価データが少なく、改善か悪化かを判定できない場合
- 追加latencyとmodel費用が要件を超える場合

rerankerは、Retrievalに存在しない正解chunkを作れません。
正解が候補にない場合は、Pre-retrievalまたはRetrievalへ戻ります。

## 10.4.3. reranker modelの選び方

Amazon Rerank 1.0とCohere Rerank 3.5を、同じ候補集合で比較します。
model名だけで選ばず、日本語、domain用語、質問長、候補長を含む評価データでNDCG、MRR、正解chunkの採用率、latency、費用を測ります。

Knowledge Basesへ組み込む場合は、次の値を決めます。

- **初期候補数**：rerankerへ渡す前の`numberOfResults`
- **rerank後の件数**：`numberOfRerankedResults`
- **model ARN**：利用regionのreranker
- **metadata selection**：rerankerへ全metadataを渡すか、必要なfieldだけにするか

metadataが短く、順位判断に役立つ場合は`ALL`から始められます。
長い説明、内部ID、順位判断に不要な属性が多い場合は`SELECTIVE`で対象fieldを限定し、input量とnoiseを減らします。
対応modelとregionは[Bedrock rerankingの対応表](https://docs.aws.amazon.com/bedrock/latest/userguide/rerank-supported.html)で確認できます。

## 10.4.4. rerankerの設定値

本章のbaselineは次の設定です。

```yaml
initial_candidates: 5
reranker: disabled
selected_chunks: 5
score_threshold: disabled
deduplication: observation_only
```

baselineで順位の問題が確認できた場合は、次を比較対象にします。

```yaml
initial_candidates: 20
reranker:
  model_id: amazon.rerank-v1:0
  output_results: 5
  metadata_selection: ALL
selected_chunks: 5
score_threshold: disabled
```

候補を20件に広げる値とrerank後5件は出発点です。
評価で正解を含む最小候補数と、生成に必要な最小採用数へ調整します。
`numberOfRerankedResults`は1から100まで指定でき、通常は`numberOfResults`以下にします。

Pythonでは`vectorSearchConfiguration`へ次を追加します。

```python
{
    "numberOfResults": 20,
    "overrideSearchType": "SEMANTIC",
    "rerankingConfiguration": {
        "type": "BEDROCK_RERANKING_MODEL",
        "bedrockRerankingConfiguration": {
            "numberOfRerankedResults": 5,
            "modelConfiguration": {
                "modelArn": (
                    "arn:aws:bedrock:ap-northeast-1::foundation-model/"
                    "amazon.rerank-v1:0"
                )
            },
            "metadataConfiguration": {
                "selectionMode": "ALL"
            }
        }
    }
}
```

reranker modelの呼び出し権限をアプリケーションroleへ追加します。
Knowledge Base service roleとAPIを呼ぶアプリケーションroleを混同しないようにします。

付属クライアントでは環境変数で同じ比較を実行できます。

```bash
export RETRIEVAL_RESULTS=20
export RERANKED_RESULTS=5
export RERANKER_MODEL_ARN=\
"arn:aws:bedrock:${AWS_REGION}::foundation-model/amazon.rerank-v1:0"

python \
  'docs/10.AWSで設計・実装する/samples/rag_api.py' \
  --mode retrieve \
  'スタンダードプランのサポート受付時間と問い合わせ方法を教えてください。' \
  | tee /tmp/rag-reranked-result.json
```

比較後にbaselineへ戻す場合は、三つの環境変数を解除します。

```bash
unset RETRIEVAL_RESULTS RERANKED_RESULTS RERANKER_MODEL_ARN
```

## 10.4.5. 重複排除と版の扱い

重複排除は、何を同一とみなすかを先に決めます。

- 完全に同じ`source_uri + chunk位置`は一件へまとめます。
- 同じ正規化本文を別URIから取得した場合は、正本、公開状態、更新日時で残す側を決めます。
- 類似しているだけのchunkは、異なる条件や例外を含む可能性があるため、自動削除する前に評価します。

新版を常に優先するなら、`document_id`、`version`、`status`、`valid_from`をmetadataとして持たせます。
可能ならRetrieval filterで`status=published`と対象版へ絞り、Post-retrievalの選別だけに依存しません。

Lambdaへ実装する場合は、inputとoutputを次のように固定します。

```yaml
input:
  query: string
  candidates: [content, metadata, location, score]
output:
  selected: [content, metadata, location, retrieval_score, final_rank]
  rejected: [location, reason_code]
```

`reason_code`を`duplicate`、`superseded`、`unauthorized`、`over_budget`のように構造化すると、候補が消えた理由を追跡できます。

## 10.4.6. score thresholdの決め方

固定のscoreを資料から転記してthresholdにしません。
scoreはembedding、vector store、文書集合、質問分布で変わります。

thresholdを使う場合は、根拠がある質問と根拠がない質問を用意し、次を測ります。

1. top-1とtop-kのscore分布を取得します。
2. 低いscoreを除外したときの正解除外率を測ります。
3. 回答保留率と誤回答率のtrade-offを確認します。
4. model、index、chunkingを変えたら再調整します。

候補を0件にするthresholdを設けた場合、Generationへ空のcontextを渡してモデル知識だけで答えさせません。
回答保留または追加検索へ分岐します。

## 10.4.7. context packingの設定

独自に`Converse`へcontextを渡す構成では、順位順に連結するだけでなく、上限を明示します。

```yaml
max_chunks: 5
max_chunks_per_source: 2
max_total_context_tokens: <generation modelと応答要件から算出>
preserve_fields:
  - citation_id
  - source_uri
  - document_id
  - version
  - text
```

一文書が候補を独占する場合は`max_chunks_per_source`を設けます。
ただし、複数chunkを連続して読まないと答えられない手順書では、上限が回答を分断しないか確認します。

要約や圧縮で短くする場合も、生成用の短縮本文と引用用の原文位置を分けて保持します。

## 10.4.8. 効果を確認する

baselineとreranker有効時の結果を同じ質問で保存し、次を比較します。

- 正解chunkの最終順位
- 上位5件に含まれる正解chunk数
- 重複chunk数
- `Retrieve`のlatency
- rerankingのmodel費用
- 後段の回答正確性と引用正確性

このハンズオンでは、代表質問で`support-policy.md`が1位ならrerankerなしを採用します。
処理を増やさずに完了条件を満たすためです。
