# 四工程・二層をAWSへ対応づける

AWSリソースを選ぶ前に、質問より前に作るものと、質問ごとに動かすものを分けます。四工程と二層は一対一ではありません。検索前処理のうち、文書解析、Chunking、Embedding、索引作成はBatch Layerに置き、質問理解、質問変換、検索条件作成はReal-time Layerに置きます。検索、検索後処理、生成は主にReal-time Layerで動きます。

| 区分 | 役割 | 主なAWS機能 |
|---|---|---|
| Batch Layer | 質問前に索引を作る | S3、Knowledge Bases、Bedrock Embedding、S3 Vectors・OpenSearch |
| Real-time Layer | 質問ごとに根拠を探し、回答する | アプリ、Knowledge Bases、Bedrock Rerank・生成モデル |
| 管理面 | 両層を安全に運用する | IAM、KMS、CloudWatch、AWS Budgets |

Batch Layerの終点は、単にベクトルが保存された状態ではありません。原文の版、Chunkの由来、Metadata、Embedding Modelと次元、索引版を関連づけ、公開可能な索引としてReal-time Layerへ引き渡せる状態です。Real-time Layerの終点も、単にモデルの文章を返す状態ではありません。採用根拠、引用、利用した設定版、回答保留理由を追跡できる状態です。

## 入力と出力の境界を固定する

工程間の境界を固定すると、検索品質と生成品質を分けて評価できます。検索の出力は取得候補、検索後処理の出力はEvidence Set、生成の出力は根拠付き回答です。`RetrieveAndGenerate`のように複数工程をまとめるAPIを使う場合でも、この論理境界は評価上残します。

| 境界 | 最低限保持する情報 | 第3〜7章との対応 |
|---|---|---|
| Batch→Real-time | 原文ID、Chunk ID、Metadata、索引版、Embedding版 | 第3章の分割・埋め込み、第7章の評価再現性 |
| 検索前処理→検索 | 原質問、検索Query、Filter、利用者Context | 第4章のQuery理解とMetadata Filter |
| 検索→検索後処理 | 候補本文、Location、検索Score、Retriever | 第4章のSparse・Dense・Hybrid Retrieval |
| 検索後処理→生成 | Evidence、出典、採否理由、矛盾、回答可能性 | 第5章のEvidence SetとContext設計 |
| 生成→利用者 | 回答、引用、保留理由、Model・Prompt・Guardrail版 | 第6章のGrounded Generation、第7章の回答評価 |

AWSが運用する基盤が増えても、検索品質や回答品質が自動的に保証されるわけではありません。設定はBaselineから始め、第7章の評価で工程別に比較します。[Knowledge Basesの仕組み](https://docs.aws.amazon.com/bedrock/latest/userguide/kb-how-it-works.html)と[Knowledge Basesの評価](https://docs.aws.amazon.com/bedrock/latest/userguide/evaluation-kb.html)も、この分離を前提に利用します（確認日：2026年8月22日）。
