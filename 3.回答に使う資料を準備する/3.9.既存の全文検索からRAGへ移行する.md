# 3.9. 既存の全文検索からRAGへ移行する

既存の全文検索を止めてからRAGを作る必要はありません。旧検索を基準として残し、新しい検索と生成を横に構築し、同じ質問で差を測って段階的に切り替えます。移行の目的はベクトル検索への置換ではなく、既存の語彙一致、認可、監視を保ちながら、根拠付き回答を安全に追加することです。

## 3.9.1. 既存資産と基準性能を固定する

最初に、Elasticsearchなどの既存検索から次の資産を採取します。

- index mapping、field型、analyzer、tokenizer、同義語辞書、利用者辞書
- BM25の`k1`と`b`、field boost、minimum should match、完全一致規則
- 文書ID、版、更新・削除イベント、ACL、検索時filter
- 代表query、クリックではなく人が確認した正解文書、zero-result query
- p50・p95・p99遅延、timeout率、更新反映時間、運用SLO

既存の検索ログだけから正解を作ると、旧方式が返せた文書へ評価が偏ります。頻出queryに加えて、問い合わせ記録や業務担当者から旧検索が失敗した質問を集めます。旧検索のRecall@k、nDCG@k、遅延、権限違反件数を基準値として保存します。

表3-4は、既存資産をRAGの契約へ移すときの判断を示します。

**表3-4　既存全文検索の資産とRAGでの扱い**

| 既存資産 | 原則として残すもの | RAG向けに追加するもの |
|---|---|---|
| mapping | 安定ID、版、日時、状態、ACL | chunk ID、原文位置、embedding版 |
| analyzer・辞書 | 日本語分割、型番、略語、同義語 | query変換との差分と版 |
| BM25設定 | `k1`、`b`、field boostの基準 | dense・hybridとの比較結果 |
| 更新処理 | 作成、更新、削除のイベント | chunk・vector・派生要約への伝播 |
| 認可 | 検索前filterと監査規則 | 生成前の再検査とcitation検査 |
| 監視 | 遅延、error、zero-result | model error、token、回答保留、費用 |

## 3.9.2. 別indexへbackfillする

旧indexを上書きせず、RAG用の新しいindexを別名で構築します。原文のスナップショットと変更基準時刻を固定し、すべての文書に安定した`document_id`を付けます。新しいchunk、vector、metadataから元の文書と版へ戻れることを確認します。

backfillの完了はジョブ成功だけで判断しません。対象文書数、除外数、parse失敗数、chunk数、embedding失敗数、ACL欠損数、削除済み文書の混入数を照合します。失敗文書を黙って欠落させず、隔離台帳へ理由と再処理状態を残します。

変更基準時刻より後の更新は、変更ログまたはdual writeで旧indexと新indexへ伝播させます。dual writeでは、片方の成功だけで業務更新を完了とみなさず、再試行可能なイベントIDを残します。両indexの文書版が一致しない状態を検知し、差分を修復できるようにします。

## 3.9.3. shadow readと比較ログ

利用者への回答は旧検索のままにし、同じqueryを新経路へも送るshadow readを行います。新経路の結果は画面へ出さず、候補ID、順位、適用filter、処理時間、timeout、構成版だけを比較ログへ残します。機密本文をログへ複製せず、監査に必要な安定IDから権限付きで原文へ戻します。

比較では、旧BM25、新しいBM25、dense、hybrid、rerank後を分けます。一度に複数の変更を混ぜると改善原因が分からないため、analyzerの移植、chunking、embedding、fusion、生成を段階的に有効化します。旧検索よりRecallが下がったqueryは、語彙、解析、filter、chunk、embedding、fusionのどこで最初に正解を失ったか分類します。

## 3.9.4. canary、切り替え、rollback

shadow readで合格した後、内部利用者または低riskなqueryからcanary公開します。検索だけを切り替える段階と、根拠付き生成まで切り替える段階を分けます。各段階で、品質、遅延、費用、回答保留、権限違反、問い合わせ増加を旧経路と比較します。

切り替え前に、次をrelease gateへ置きます。

1. 全体と重要スライスでRecall@kとnDCG@kが合格しています。
2. ACL negative testと削除反映試験の違反が0件です。
3. p95遅延、timeout率、質問当たり費用が上限内です。
4. model失敗時に検索結果だけへ戻す経路を試験済みです。
5. 旧indexへ戻すrouterまたはalias変更を演習済みです。

rollbackは新indexの削除ではなく、参照先を旧経路へ戻す操作です。error率、権限違反、重大queryの回帰、遅延超過、費用超過を発動条件として定めます。旧indexを保持する期間にも、現在のACL、文書削除、緊急修正を適用します。古い旧indexへ戻すことで削除済み情報が復活してはいけません。

切り替え後も一定期間は比較ログを残し、新経路にない機能、検索結果の変化、利用者の再質問を確認します。安定後に旧経路を廃止するときは、依存system、保存データ、監視、runbook、担当者を棚卸しし、復旧に必要なスナップショットだけを保持方針に従って保存します。
